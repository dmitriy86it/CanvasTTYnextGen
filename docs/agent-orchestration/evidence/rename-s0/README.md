# S0 для переименования в Raoden Loom: доказательства (macOS, 2026-09-28)

Контракт и выводы: [rename-raoden-loom.md](../../implementation/rename-raoden-loom.md) §4.

Здесь лежат обезличенные результаты, диагностические скрипты, команды и полные контрольные суммы. Реальных
профилей, секретов и полных журналов сессий здесь нет.

При обезличивании пути заменены так:

| Было | Стало |
|---|---|
| временный каталог сессии | `<S0>` |
| checkout | `<REPO>` |
| домашний каталог | `~` |
| системный временный каталог | `<TMPDIR>` |

Чтобы запустить скрипты, верните реальные пути.

- `checksums.txt` — SHA-256 исполняемых файлов и `app.asar` всех сборок, входов упаковки, CDHash и подписи.
- `evidence-sha256.txt` — SHA-256 файлов `scripts/` и `results/`.

## Прогоны и различия между ними

### Диагностическое приложение (`scripts/diag-main.js`, `results/diag/`)

- **Замеры путей** `m1-switch`, `m2-env`, `m3-both`, `m4-default`, `m5-beta-same-profile`, `m1b-switch`,
  `m2b-env`. Сделаны **первой** версией `main.js`, в которой не было обработчика `window-all-closed`. На замеры путей
  это не влияет: приложение выходило после записи результата.
- **Недействительные замеры единственного экземпляра** `si-exec-*`, `x-*`, `y-*` (тоже первая версия). Без
  обработчика Electron завершал первый экземпляр, как только закрывалось его скрытое окно, то есть раньше старта
  второго. Поэтому второй получал блокировку. Эти результаты **не** являются замером блокировки и оставлены как
  журнал ошибки стенда.
- **Действительные замеры** `si2-*`: вторая версия `main.js` с одной добавленной строкой
  `app.on("window-all-closed", () => {})`, 4 случая через `scripts/si-diag.sh`. Печать итоговой строки в
  `si-diag.sh` падала на опечатке (`firstStillRunning`); файлы `si2-*.json` записаны самим приложением и читались
  отдельно.

### Реальные сборки

- **`results/real-run1.json`** — `scripts/s0-real.mjs`, первая полная версия. Профили в `/tmp/cto-s0-*`: из-за
  предела пути сокета агентского браузера (100 байт) два более ранних запуска упали на старте 1.5.3 с ошибкой
  «runtime directory is too long», результатов у них нет.
  - Прошли: U1–U4, F, PR, Keychain, `Application Support`.
  - **Не прошли** все 4 SI. Причины:
    - поле `sameEntries: false` — в профиле появился `Local State`;
    - поле `procs: [0,0]` — ошибка стенда: `pgrep -f --user-data-dir=…` принимал шаблон за ключ.
- **`results/real-si-rerun.json`** — повтор только SI (`ONLY_SI=1`) с исправленным `pgrep -f -- …` и выводом
  добавленных записей.
  - **Все 4 SI снова `ok: false`**: добавлен `Local State`.
  - Остальные поля: хранилища без изменений (размер и mtime), процессы 1 → 1, первый отвечает.
- **`results/si-control.json`** — `scripts/si-control.mjs`: один экземпляр без второго, те же паузы. `Local State` до
  выхода не появлялся.
- **`results/local-state.json`** — `scripts/s0-localstate.mjs`, разбор `Local State`, 6
  случаев:

  | Случай | Что сравнивалось |
  |---|---|
  | A | один экземпляр без второго |
  | B | то же приложение поверх работающего |
  | C, D | переименованное поверх работающего, оба порядка |
  | E, F | C и D, но `Local State` заранее заменён каталогом |

  Хранилища здесь сравнивались по SHA-256.

### Заполненный синтетический профиль (`scripts/si-filled*.mjs`, `results/si-filled/`)

**Профиль.** Основа — временный профиль, оставленный `scripts/e2e-orchestration.mjs` с подставными CLI (38 проверок
пройдено, 0 ошибок, `seed-e2e-report-summary.json`). В нём 4 запуска оркестрации с журналами. К нему добавлены:

- тестовый плагин `s0.data-probe` с правом `storage` и значением в `plugin-storage` (через API приложения, без секретов
  и Keychain);
- браузерные данные: встроенный браузер dev «Raoden Loom» открыл локальную страницу `127.0.0.1`, она записала cookie,
  `localStorage` и IndexedDB;
- после этого приложение закрывалось.

Непустота проверяется самим скриптом, иначе он падает:

| Категория | Файлов |
|---|---|
| `Partitions/`: Local Storage | 6 |
| `Partitions/`: IndexedDB | 5 |
| `Partitions/`: Cookies | 1 |
| `plugin-storage` | 1 |
| запуски | 4 |
| журналы запусков | 4 |

Всего в профиле 290 файлов, `Local State` уже есть.

**Метод.** Каждый случай выполняется на своей копии профиля:

1. Запуск первого приложения и снимок всех файлов профиля.
2. Второй запуск (или пауза 2 с в контрольном прогоне) плюс 1,5 с, затем снимок — это «окно второго запуска».
3. Выход первого и снимок.
4. Повторное открытие: приложение отвечает, данные плагина читаются, 4 запуска на месте.

Контрольные прогоны без второго запуска (по 2 на каждое первое приложение) показывают штатные записи первого процесса.
Второму запуску приписывается только то, чего нет в контрольных.

**Прогоны.** Исторические версии сохранены:

| Прогон | Скрипт | Что сравнивалось | Замечание |
|---|---|---|---|
| run1, run2 | `si-filled.v1-hash-only.mjs` | только SHA-256 | Перезапись теми же байтами не видна |
| run3 | `si-filled.v2-mtime-bad-quit-baseline.mjs` | SHA-256 и mtime | Сравнение «до выхода» **некорректно**: база сравнения — исходный профиль, а `cpSync` не сохраняет mtime, отсюда ложные «rewritten, same bytes». Окно второго запуска корректно: оба снимка в одном каталоге |
| run4 | `si-filled.mjs` | SHA-256 и mtime, база — снимок копии до запуска | — |

**Результат.** Случаи B (то же приложение), C и D (переименованное, оба порядка):

- Второй экземпляр завершился с кодом 0 за 0,23–0,49 с.
- За окно второго запуска в профиле **не изменился ни один файл**: 4 прогона по SHA-256, из них run3 и run4 также по
  mtime. Это относится и к `Partitions/`, `plugin-*`, `orchestration/runs`, и к `Local State`.
- При выходе первого меняются одни и те же файлы с запуском и без: журналы LevelDB, индексы кешей, `browser-state.json`,
  5 файлов `Partitions/`, перезапись без изменения содержимого одного файла плагинов и одного хранилища приложения.
  Отличий, приписываемых второму запуску, нет.
- Данные плагина, 4 запуска и браузерные данные после повторного открытия на месте.

**Ограничения.**

- Снимки делаются в две точки: файл, созданный и удалённый внутри окна, не виден.
- По одному прогону каждого случая на версию скрипта.
- Порты второго процесса не измерялись.
- Результат относится к профилю, где `Local State` уже есть. На профиле без него `Local State` появляется при втором
  запуске (S0-9, ниже).

## Local State: что установлено и что нет

**Установлено:**

- Без второго экземпляра `Local State` появляется только при выходе (A и контроль).
- При любом втором запуске на работающий профиль он появляется сразу — и при запуске того же приложения (B), и
  при запуске переименованного (C, D). Значит, это не следствие переименования.
- Содержимое во всех случаях — 57 байт, единственный ключ `uninstall_metrics` (служебные счётчики Chromium). Это
  тот же ключ, который первый экземпляр пишет при выходе. Значения отличаются, хэши разные.
- После выхода первого и повторного открытия профиля приложение запускается и отвечает. Хранилища совпадают с
  исходными по SHA-256.

**Не установлено: кто пишет файл.**

- Приём с каталогом (E, F) ничего не показал: ни stderr второго процесса, ни вывод первого не содержат ошибки
  записи, в каталоге ничего не появилось.
- Трассировка файловых операций (`fs_usage`, `eslogger`) требует root и не применялась.

**Критерий.**

- Строгий критерий «второй экземпляр ничего не записывает в профиль» **не подтверждён**.
- Предлагаемый критерий безопасности данных (не замена строгого, а отдельный) — выполнены все четыре условия:
  1. второй экземпляр не получает блокировку и завершается, не создав окна и служб;
  2. файлы данных приложения побайтово не меняются: `settings.json`, `workspaces.json`, `browser-state.json`,
     `plugins.json`, `orchestration/canvas.json`, `terminal-sessions.json`, каталоги `Partitions/`, `plugin-*`,
     `orchestration/runs`;
  3. изменения допускаются только в служебных файлах Chromium из закрытого списка, сейчас это `Local State` с
     ключом `uninstall_metrics`;
  4. первый экземпляр работает, а профиль после его выхода открывается снова без потерь.
- Что уже есть для этого критерия:
  - (1) диагностика, 4 случая; реальные сборки, 4 + 4 случая; заполненный профиль, 3 случая × 4 прогона;
  - (2) на заполненном профиле все файлы (в том числе `Partitions/`, `plugin-*`, `orchestration/runs`) за окно второго
    запуска побайтово не изменились; раньше — 4 JSON-хранилища по SHA-256 и 6 файлов по размеру и mtime;
  - (3) содержимое `Local State` в 6 случаях на пустом профиле; на заполненном он не менялся;
  - (4) повторное открытие: 6 случаев на пустом профиле и 7 на заполненном (включая контрольные).
- Строгий критерий на заполненном профиле в измеренном объёме выполнен: записей за окно нет, включая перезапись теми же
  байтами. В общем виде он **не подтверждён**: на профиле без `Local State` второй запуск его создаёт, и автор записи не
  установлен.

## safeStorage (S0-5): не проверено, подготовлено

`scripts/safe-storage-scenario.mjs`:

- **Итог.** Вычисляется чистыми функциями:
  - `seedingVerdict`: каждая сборка показывает плагин с `secrets`, файла секрета нет;
  - `runVerdict`: каждый вызов успешен; каждое чтение вернуло ожидаемый секрет; после каждой записи файл есть;
    ни одно чтение не изменило байты файла (SHA-256 до и после чтения).
- **Код выхода:** 0 — все обязательные проверки прошли; 1 — хотя бы одна не прошла или сценарий прервался; 2 — неверный
  вызов.
- **Прежняя версия** (до 2026-09-28, 14:30) считала итог только по возвращённым значениям (`allReadable`), не учитывала
  `sha256Unchanged` и всегда выходила с кодом 0. Она заменена. Отдельно её результаты не сохранялись: `--run` она не
  выполняла.
- **`--self-test`** проверяет итоги на подставном стенде без приложения и Keychain. 9 случаев:
  - подготовка: норма; нет плагина; нет права; файл секрета уже есть;
  - `--run`: норма; другой ключ у новой сборки; сбой записи; запись без файла; чтение, переписавшее файл.
  Все дают ожидаемый код. Проверка на мутации: без всех трёх сравнений байтов случай «чтение переписало файл» проходит
  как успех, то есть self-test это ловит.
- **`--validate-seeding`** повторно выполнен на этой машине с новой версией (1.5.3 и dev «Raoden Loom»): оба
  показывают `s0.secret-probe` с `["secrets"]`, файла секрета нет, код выхода 0. Записей `canvastty Safe Storage` и
  `Raoden Loom Safe Storage` до и после нет (только метаданные).
- `--run` здесь **не** запускался: он читает и создаёт записи в связке ключей.

**Статус: BLOCKED.** Что нужно от владельца:

1. Отдельная учётная запись macOS (или отдельная машина), в которой можно создавать записи Keychain.
2. Копии сборок 1.5.3 и dev «Raoden Loom» и checkout этого репозитория в ней.
3. Запуск из этого каталога `scripts/`:
   `OLD_APP=… NEW_APP=… node safe-storage-scenario.mjs --validate-seeding`, затем
   `S0_ISOLATED_ACCOUNT=yes OLD_APP=… NEW_APP=… node safe-storage-scenario.mjs --run`.
4. Отдельно записать, запрашивала ли macOS доступ к Keychain на каком-либо шаге, и передать полученный JSON.
