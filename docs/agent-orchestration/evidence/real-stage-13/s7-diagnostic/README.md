Один запуск исходного драйвера: `scripts/real-autopilot-series.mjs --real --only S7 --diag-link --project <repo>`.
- Окно 1280×800, новый временный userData.
- `codex-cli 0.155.1`, `2.1.282 (Claude Code)`.
- Модельных запросов 0, ходов 0, вмешательств 0. S3–S6 и проверочные вызовы совместимости не запускались.

**Итог: связь создана, S7 прошёл.** Это успешный диагностический прогон, но не доказательство устранения причины
сбоев попыток 1 и 2: сбой не воспроизвёлся, журнала неудачного прогона нет.

## Изменения перед запуском

- `scripts/orchestration-app-kit.mjs`:
  - `waitFor` (`waitForValue`): исключение больше не считается успехом (раньше текст ошибки возвращался как
    успешное ожидание), `false` — не успех; тест `tests/orchestration-app-kit.test.mjs` 3/3;
  - `launch`: DevTools-порт должен слушать именно запущенный процесс (`lsof`, pid == `child.pid`), и в его
    аргументах должен быть этот userData; иначе отказ и остановка только собственного процесса.
- `scripts/real-autopilot-series.mjs`:
  - `--diag-link`: журнал `link-diag.json` при успехе и при отказе;
  - успех связывания проверяется по паре `agentId` лид → исполнитель;
  - `pkill -f remote-debugging-port=N` заменён на завершение только собственного процесса.
- Renderer: `linkTrace.ts` — инертные точки трассировки в `AgentScene.tsx` и `useAgentCanvasUi.ts`. Они пишут
  только если драйвер заранее создал `window.__canvasTTYLinkTrace`.

## Что этот прогон показывает о попытках 1 и 2

Успешный прогон показывает только, что эта геометрия может работать: жест и обработчик в раскладке 1280×800 с
теми же точками доходят до main и создают связь. Прошлые сбои он **не исключает**. Остаются возможными:
- временное перекрытие точки сброса или порта в момент жеста;
- перерисовка или перемонтирование карточки между измерением и отпусканием;
- потеря захвата или `pointercancel`;
- отказ main: текст отказа живёт на карточке 8 с, а снимок делался после 20 с ожидания;
- управление чужим окном при совпадении портов. Теперь это закрывает проверка владельца.

Старый `waitFor` значение `timeout: link (false)` сам по себе не объясняет: оно значит, что main успешно отвечал без
нужной связи. Различить варианты может только журнал `--diag-link` неудачного прогона.
