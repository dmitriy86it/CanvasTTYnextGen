# План реальной серии этапа 13: S3–S7

Состояние: **подготовлено и отрепетировано на поддельных CLI; на реальных CLI не запускалось.** Это план. Результатов
реального запуска здесь нет. Серии N и L уже пройдены ([README.md](README.md)), S1 и S2 закрыты ими, их не повторяем.

Драйвер тот же, что у N/L: `scripts/real-autopilot-series.mjs`. Лимиты, остановки, правило ответов на запросы и
анонимизация отчёта у него общие для всех сценариев. Сценарии S3–S7 выбираются через `--only` и с N/L не смешиваются:

```
node scripts/real-autopilot-series.mjs --rehearse --only S7,S3,S4,S5,S6 --out <dir>     # поддельные CLI
node scripts/real-autopilot-series.mjs --real --only S7,S3,S4,S5,S6 --project <проект S7> \
     [--s4-dir <новая папка S4>] --out docs/agent-orchestration/evidence/real-stage-13/s3-s7
```

Нужна development-сборка (`npm run build`), без упаковки. Установленное приложение, `~/.claude` и `~/.codex`
драйвер не трогает. userData и проекты S3–S6 создаются во временном каталоге. Проект S7 драйвер только читает.

## 2. Общие условия серии

| | |
|---|---|
| Сборка | development `out/` и временный userData, как у N/L |
| CLI | только `codex-cli 0.155.1` и `2.1.281 (Claude Code)`. Другие версии драйвер отклоняет до старта |
| Лимиты на сценарий | 8 ходов, 2 раунда на этап, 1 перепланирование, 20 минут (вводятся в диалоге цели) |
| Лимиты на серию | 32 хода (по 8 на S3–S6, у S7 ходов нет), 100 минут. Бюджет ходов резервируется до старта сценария |
| Деньги (оценка) | N/L: 8 ходов, 2 из них у Claude, $0,51 по отчёту Claude CLI. S3–S6 в репетиции: по 4 хода, 1 из них у Claude. Реально ожидается 1–3 хода Claude на сценарий, итого **$1,5–3**. При исчерпании лимитов (≈16 ходов Claude) — около **$6**. Это **оценка, а не денежный потолок**: приложение и драйвер ограничивают ходы и время, но не деньги, и цена хода зависит от модели и контекста. Codex отчитывается только токенами, его стоимость неизвестна (это не ноль). S7 моделей не вызывает |
| Порядок | **S7 → S3 → S4 → S5 → S6.** S7 бесплатен и показывает, что CLI загружают у человека. S6 идёт последним, потому что дважды перезапускает приложение |
| Стоп-условия | неожиданный запрос; `protocol_error`; пауза, которой нет в списке сценария; любой лимит; невыполненный критерий. S4: Claude не показывает `release-form` в «Проверить окружение» (до первого хода). S6: единственный путь дальше — «Повторить» (`finish_retry`). Сценарий не повторяется, лимиты не поднимаются |
| Правило ответов | «Разрешить один раз» ставится только на тестовую или читающую команду либо на правку внутри проекта сценария (`allowedByAssignment`, как у N/L; в S6 внутри worktree). Плановые действия сценария (формы S4, план S5, «Продолжить» S3/S6) записываются как вмешательства с причиной. Всё остальное (вопрос, чужая форма, команда вне проекта, сеть) останавливает серию. Решения «на запуск» и «на проект» не сохраняются |
| Свидетельства | `report.json`, `series.log`, `shots/`, `mcp-elicit.jsonl` (S4). Пути анонимизированы (`<tmp>`, `~`) |

**«Загружено» и «использовано» различаются во всех сценариях.** «CLI сообщил» — это `system/init`, ответ на
`thread/start`, «Проверить окружение» или строка `initialize` в журнале MCP-сервера. «Возможность использована» —
только наблюдаемое последствие: процесс запущен с флагом (список процессов), сервер записал вызов, в проекте
появился маркер, которого без вызова быть не могло.

## 3. Что нужно от пользователя

1. Разрешить запуск `--real` (реальные запросы к моделям, оценка выше).
2. **S7:** путь к обычному проекту (`--project`). После прогона сравнить в терминале в той же папке: `claude` →
   `/mcp`, `/skills`; `codex` → `/mcp`. В отчёт записать «совпадает» или «отличается: что именно».
3. **S4, часть Codex:** выбрать, как Codex получит тестовый сервер. Вариант А: `--s4-dir <постоянная новая папка>`.
   До серии человек один раз открывает `codex` в этой папке и доверяет ей (запись в его `~/.codex/config.toml`
   делает он сам). Вариант Б: временно добавить `[mcp_servers.release-form]` в свой конфиг. Без этого часть Codex
   пропускается, и это видно в отчёте (`codexServerLoaded: false`). Часть Claude от выбора не зависит: проектные
   `.mcp.json` и `.claude/settings.json` с `enabledMcpjsonServers`.
4. **S6:** коммит идёт в login shell человека. Если в глобальном git настроены подпись или хуки, которым нужен
   ввод (пароль, касание ключа), человек должен быть рядом. Иначе серия остановится на коммите.

## 4. Сценарии

### S3. «По шагам», права Claude `acceptEdits` / Codex `workspace`

- **Проверяет:** выбранные режимы доходят до CLI, CLI сообщают, что их применили, и запуск останавливается на
  плане и после каждого принятого этапа.
- **Проект и задача:** как N (Node без `node_modules`, `toMs` на `ms`, приёмочный тест не менять). Проверка — `npm test`.
- **Действия в интерфейсе:**
  1. ПКМ по холсту → «Агент Codex (лид)» и «Агент Claude (исполнитель)» на проект; связь перетаскиванием порта.
  2. «Новая цель» → «Настройки проекта»: Claude «acceptEdits», Codex «workspace». Под каждым выбором показано, во
     что он превращается. «Сохранить».
  3. Режим «По шагам», лимиты в «Дополнительно», «Начать».
  4. Пауза «план» → прочитать план → «Продолжить». Пауза «этап готов» → «Продолжить».
- **Ожидаемые факты:**
  - применено: у каждого процесса Claude-сессии в argv есть `--permission-mode acceptEdits` (список процессов
    приложения раз в секунду);
  - сообщено CLI: `system/init.permissionMode = acceptEdits`; в ответе на `thread/start` `approvalPolicy on-request`,
    `sandbox workspaceWrite` (факты сессии в панели);
  - нет `[data-orch-access-mismatch]`;
  - в журнале есть `run.status(paused/plan_review)` и `paused/stage_done`; прогон завершается `completed`;
  - `npm test` проходит в shell человека.
- **Участие пользователя:** нет. Запросы Claude на Bash (в `acceptEdits` они возможны) обрабатываются по правилу.
- **Репетиция:** пройдена. Статус `completed`, 4 хода (Codex 3 / Claude 1), 15,8 с, паузы `plan_review` и
  `stage_done`. argv поддельного Claude: `--permission-mode acceptEdits`. Параметры потока, полученные поддельным
  Codex: `on-request / workspace-write`.
- **Без реальных CLI не проверить:** сообщит ли настоящий Claude `acceptEdits`, а не свой режим по умолчанию
  (у человека это `auto`); примет ли настоящий Codex `workspace-write` при его управляемой конфигурации.

### S4. Форма MCP-сервера: ответ, отказ, проверка полей

- **Проверяет:** настоящий `elicitation` от MCP-сервера доходит до человека через оба CLI, недопустимые значения до
  сервера не доходят, отказ передаётся серверу, а инструмент именно используется, а не только загружается.
- **Сервер:** `tests/fixtures/orchestration/mcp-elicit-server.mjs` (stdio, Node, без зависимостей). Инструмент
  `release_ticket` спрашивает форму `ticket` (4–20 символов, обязательное), `env` (`qa` или `stage`,
  обязательное), `reviewers` (1–5), `urgent`. Каждое действие сервер пишет в `MCP_ELICIT_LOG`: `initialize` (кто
  запустил, заявлена ли поддержка форм), `call` (компонент, одноразовый nonce, ответ, собственная проверка сервера),
  `call_failed`. Самопроверка: `node tests/fixtures/orchestration/mcp-elicit-server.mjs --self-check`. Проходит
  3 из 3: ответ, отказ, недопустимый ответ помечен `valid:false`.
- **Проект:** Node, приёмочный тест `tests/receipts.accept.test.mjs` требует в `release/receipts.txt` строки
  `RELEASE-FORM nonce=<12 hex> component=api|web`. Конфигурация: `.mcp.json`; `.claude/settings.json` с
  `enabledMcpjsonServers` (только проект); `.codex/config.toml`.
- **Задача:** лид вызывает `release_ticket(component="plan")` и переносит строку в задачу этапа. Исполнитель вызывает
  `api`, потом `web` и записывает строки дословно.
- **Действия в интерфейсе:**
  1. Связь агентов → «Новая цель» → «Настройки проекта» → «Дополнительно» → «Проверить окружение».
     **Ворота:** Claude должен показать `release-form`, иначе сценарий не стартует и ходы не тратятся. Если сервер
     не показывает Codex, фраза для лида удаляется из задачи, и это записывается.
  2. «Сохранить», лимиты, «Начать».
  3. Первая заполняемая форма: `ticket=AB` → «Отправить» (должна остаться); `reviewers=9` → «Отправить» (должна
     остаться); затем `REL-<компонент>`, `qa`, `2` → «Отправить».
  4. Форма `web` → «Отклонить». Запрос прав на сам инструмент `release_ticket` (если Claude его задаст) →
     «Разрешить один раз».
- **Ожидаемые факты:**
  - загружено: `initialize` от клиента Claude (и Codex, если настроен) в журнале сервера и `release-form` в
    «Проверить окружение»;
  - использовано: записи `call` с `action=accept` (api) и `decline` (web). У каждой строки в
    `release/receipts.txt` nonce, который сервер выдал на вызов, а угадать nonce нельзя. Строка лида в файле с
    nonce вызова Codex доказывает, что результат Codex использован, а не только то, что вызов был;
  - сервер получил только `valid:true`. Для недопустимых значений записано, кто остановил: панель (правила поля
    браузера) или main (`command.completed invalid_form`);
  - `npm test` проходит.
- **Участие пользователя:** §3 п. 3 (Codex).
- **Репетиция:** пройдена. `completed`, 4 хода, 18,6 с. Недопустимые значения не отправлены: `short ticket` main
  отклонил (`invalid_form`), `reviewers over 5` заблокировала панель. Журнал сервера: `mock-codex` → plan
  accept; `mock-claude` → api accept, web decline; все `valid`. В репетиции поддельные CLI **по-настоящему**
  запускают сервер из `.mcp.json` и передают его `elicitation/create` через протокол приложения
  (`mcpToolCall` в `mock-common.mjs`).
- **Без реальных CLI не проверить:** передаёт ли Claude 2.1.281 в режиме `-p --permission-prompt-tool stdio`
  `elicitation` хосту, а не отклоняет его сам; заявляют ли CLI поддержку форм серверу; читает ли Codex 0.155.1
  проектный `.codex/config.toml` и пересылает ли `elicitation` клиенту app-server, объявившему `capabilities: null`;
  не спрашивает ли Codex подтверждение вызова MCP-инструмента своей формой (такую чужую форму драйвер не заполняет
  и останавливается). Ворота в репетиции не показательны: списки «Проверить окружение» у поддельных CLI фиксированы.

  - использовано: существует `tests/clamp-feedback.test.mjs` с `5, 5, 5`. Этого файла нет в задаче, он есть только

### S6. Worktree, коммит, push в локальный bare, локальный QA, выход во время и после QA

- **Проверяет:** действия после успеха подтверждаются отдельной проверкой. После выхода во время QA и перезапуска
  деплой не повторяется, запускается только проверка. После выхода, когда QA завершён, ничего не запускается.
- **Проект:** Node (как N), remote `origin` = `<tmp>/s6-remote.git` (`git init --bare`), в bare уже есть `main`.
  «Окружение QA» — каталог `<tmp>/qa` вне проекта.
- **Настройки проекта:** место работы «worktree»; push `origin` → ветка `canvastty-s6`; QA `qa-local`:
  - команда: `echo "$CANVASTTY_COMMIT" >> qa/deploys.log && echo … > qa/deployed && sleep 45 && echo done >> qa/deploy-finished.log`;
  - проверка: `echo x >> qa/verify.log && test -s qa/deployed && cat qa/deployed > "$CANVASTTY_QA_RESULT"`;
  - включено «проверка сообщает версию».
- **Действия в интерфейсе:**
  1. «Настройки проекта» (всё выше) → «Сохранить».
  2. В цели отмечены «Коммит», «Push», «QA», в «Дополнительно» выбран worktree. «Начать».
  3. Когда `deploys.log` получил строку и шаг QA активен → выход из приложения (SIGTERM, как Quit), запуск снова.
     20 секунд ничего не трогать → «Открыть запуск» → «Продолжить» (пауза `app_closed`) → «Продолжить» (пауза
     `finish_unconfirmed`, `data-orch-resume=finish_check`: только проверка).
