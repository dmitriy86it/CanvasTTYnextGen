# reviewer-main: отчёт независимого ревью (main, данные, миграция, владение)

Дата: 2026-09-28. Отчёт пришёл сообщениями: субагенту запрещено писать файлы-отчёты, поэтому его сохранил
координатор без смысловых изменений. Репро лежат рядом, каждое запускается командой `node --test <файл>`.

## 1. Находки

### R-M01. Частично невалидный файл

- **Сценарий.** В `workspaces.json` (`v:1`) у одной записи нет `createdAt`. Так бывает после ручной правки или записи
  другой сборкой. Затем выполняется любое изменение, например `setCamera("common")`.
- **Ожидаемое (§3 п.2).** Файл, который не удалось принять, отодвигается как `.damaged-<uuid>`. Данные молча не
  заменяются.
- **Фактическое.** `parseFile` (`WorkspaceStore.ts:52-59`) пропускает такую запись через `continue` и считает файл
  корректным. Первая же запись `change()` перезаписывает файл без неё, копии исходных байтов нет. Так же ведёт себя
  обрезка до 64 записей.
- **Последствия.** Имя, папка и камера пространства пропадают навсегда. Разложение карточек по пространствам не
  восстановить (сами карточки видны в `common`).

### R-M02. Запись без id

- **Фактическое.** `ID.test(undefined)` проверяет строку `"undefined"`, и она проходит regex. В состоянии появляется
  пространство с `id: undefined`. При записи поле теряется, и при каждом старте всё повторяется.
- **Последствия.** В переключателе появляется пространство без id; действия с ним заканчиваются `workspace_not_found`
  или ошибкой IPC.

### R-M03. Неизвестный id и `link_workspaces`

- **Сценарий.** У карточки в `canvas.json` указано `workspaceId: "ghost"`. По §1 она видна в `common`. Пользователь
  связывает её с карточкой из `common`.
- **Фактическое.** `canvasStore.createLink` сравнивает сырые значения (`canvasStore.ts:28,178`) и отказывает с
  `link_workspaces`.
- **Последствия.** Карточки на одном холсте, а приложение отвечает, что они в разных пространствах.
- **Замечание.** `ownersFixed` и `startOnLink` пишут в `owners` сырое `"ghost"`. На поведение это не влияет:
  `runOwners` отображает его в `common`.

### R-M05. `folder_busy` без `runId`

- **Сценарий.** Запуск в beta держит папку. Пользователь в alpha запускает связь на той же папке.
- **Фактическое.**
  - Main отдаёт только код `folder_busy` и фиксированный текст (`canvasStore.ts:228`).
  - `readiness` возвращает `busy: boolean` (`manager.ts:511-528`).
  - Renderer восстанавливает запуск сам (`WorkspaceCanvas.tsx:257-264`), но смотрит только последний `runId` каждой
    связи и только при наличии снимка. Правило main (`manager.ts:138-145`) шире: учитываются все `runIds`, а
    нечитаемый журнал считается занятым.
- **Последствия.** Когда правила расходятся, пользователь видит «В этой папке уже работает другой запуск» без
  «Открыть» и без названия пространства.

### R-M04. Покрытие M5

- Репро выполняет `git archive HEAD src`. `SettingsStore` и `normalizePersistedTerminalSessions` из HEAD читают
  файлы новой сборки. Результат совпадает с §3.
- Теста в `tests/` нет.

## 2. Что проверено и оказалось верным

Проверялось чтением кода. Пункты с пометкой «(скретч)» дополнительно прогнаны скриптом во временном каталоге.

- **Миграция:**
  - выполняется до создания хранилищ и после блокировки единственного экземпляра;
  - порядок шагов соответствует контракту: partial → копия со сверкой sha256 → manifest → rename → атомарная запись;
  - ошибки, отличные от ENOENT, не дают записать файл (скретч: backup-файл даёт EEXIST, каталог вместо
    `settings.json` — EISDIR);
  - прерывание повторяется с шага 3; повторный старт копию не делает (скретч);
  - файл `v:2` не трогается (скретч);
  - повреждённый JSON отодвигается; если отодвинуть не удалось, пространства недоступны.
- **Владение.**
  - Владелец не выводится ни из cwd, ни из активного пространства. Активное пространство используется только при
    создании терминала без `workspaceId` (§4).
  - `terminal:setWorkspace` меняет только метаданные.
  - `createAgent` проверяет, что пространство открыто.
- **Перенос группы:**
  - `group_changed` определяется по компоненте связности;
  - занятая группа учитывает `paused` и нечитаемый журнал;
  - `owners` фиксируются в той же записи.
- **Удаление карточек и связей:** фиксирует `owners`, история остаётся доступна по `runId`.
- **`startOnLink`:**
  - резервирование и владелец пишутся атомарно;
  - при сбое записи — `store_failed`;
  - при сбое создания — откат;
  - повтор с тем же `requestId` владельца не меняет.
- **Удаление и закрытие пространства:**
  - `common` не удаляется;
  - последнее открытое пространство нельзя закрыть (скретч);
  - непустое пространство отклоняется, каскада нет;
  - нечитаемый canvas даёт отказ;
  - закрытие ничего не останавливает (скретч).
- **IPC:** `setCamera` отклоняет NaN, Infinity, zoom вне диапазона, null, строку и неизвестный id (скретч).

## 3. Не проверено

- **«Остановить и скрыть»:** этот путь целиком в renderer, это область reviewer-ui.
- **Две гонки с `remove()`, без репро.** Пока пространство удаляется, терминал без `workspaceId` берёт `active()` и
  не проверяет `removing`; сохранение настроек из renderer не проверяет `isOpen`. Карточка не теряется: после удаления
  она попадает в `common`. Как находки не заносятся.
- **`canvas.json` при откате:** исключено контрактом (§3).
- **Electron:** не запускался.
