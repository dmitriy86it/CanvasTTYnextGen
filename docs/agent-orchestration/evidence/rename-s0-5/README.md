# S0-5: safeStorage при переходе CanvasTTY 1.5.3 → Raoden Loom 1.5.4 (кандидат)

Продолжение [rename-s0](../rename-s0/README.md), раздел «safeStorage (S0-5)». Контракт:
[rename-raoden-loom.md](../../implementation/rename-raoden-loom.md) §2, §4, §5.

**Статус: пройдено 2026-09-29 (попытка 2), с ограничением: настоящий отказ доступа («Запретить») не проверен.**
Попытка 1 недействительна — см. «Попытка 1». Итог — в «Результат».

## Среда

- Отдельная учётная запись macOS `test` (UID 502, без прав администратора) на той же машине. Она уже существовала;
  системные настройки и связка ключей основной учётной записи не менялись. Запуск выполняет владелец: вход в `test`
  требует её пароля и графического входа.
- Записи `<имя> Safe Storage` создаются только в связке ключей `test`. Сценарий записи связки ключей не удаляет и не
  меняет; тестовые профили не удаляет.

суммами; после пересборки его нельзя переносить на новую сборку.

## Сценарий

Синтетический секрет пишется и читается через API секретов плагинов (`s0.secret-probe` с правом `secrets`) — тот же
ключ safeStorage, что у сохранённого входа GitHub. Профиль временный (`/tmp/rs0-*`), PATH без CLI агентов. HOME —
собственный HOME учётной записи `test`: через него macOS находит связку ключей (см. «Попытка 1»). Сценарий сам
повторяет проверку связки ключей по умолчанию (`security default-keychain`) и без неё не запускает приложения.

| Шаг | Сборка | Действие | Указание оператору при запросе macOS |
|---|---|---|---|
| 1 | 1.5.3 | пишет s1, читает | — |
| 2 | 1.5.4 | читает s1 впервые | «Запретить» — проверка отказа |
| 2b | 1.5.4, новый запуск | читает s1 | «Разрешить всегда» |
| 3 | 1.5.3 | читает s1 | «Разрешить всегда» |
| 4 | 1.5.4 | пишет s2 | «Разрешить всегда» |
| 5 | 1.5.3 | читает s2 (откат после записи новой сборкой) | «Разрешить всегда» |
| 6 | 1.5.4, новый запуск | читает s2 | «Разрешить всегда» |

После каждого шага записываются SHA-256 файла секрета и ответ оператора: `n` запроса не было, `d` «Запретить», `a`
«Разрешить», `w` «Разрешить всегда», `x` появилось другое системное окно. Любое другое окно (например «Связка ключей
не найдена») — нажать **«Отменить»**, никогда «Вернуть по умолчанию» (это создаёт новую связку ключей по умолчанию и
убирает прежнюю из использования), ответить `x`. Ответ `x` делает итог отрицательным: такой прогон не считается ни
успехом, ни проверкой отказа. При прерывании (Ctrl-C, закрытое окно Терминала) записанное сохраняется в
`safe-storage-release.json` с шагом `interrupted`.

**Итог** (`verdict`, код 0 только если все пункты выполнены):
- 1.5.3 пишет и читает свой секрет;
- первое чтение новой сборкой: либо читает s1, либо (если оператор нажал «Запретить») завершается ошибкой, а файл
  секрета побайтово прежний и не удалён;
- после перезапуска новая сборка читает s1; ни одно чтение не меняет байты файла;
- 1.5.3 снова читает s1; новая сборка пишет s2; 1.5.3 читает s2; новая сборка после перезапуска читает s2;
- после всех шагов есть одна запись `canvastty Safe Storage`, записей `Raoden Loom`/`CanvasTTY Safe Storage` нет —
  новая сборка не завела отдельный ключ;
- ни на одном шаге не было другого системного окна (`x`).

`--self-test` проверяет итог на подставном стенде без приложения и связки ключей, 9 случаев: норма; «Запретить», затем
«Разрешить всегда»; «Запретить» удаляет файл; «Запретить» переписывает файл; другой ключ у новой сборки; чтение
переписывает файл; новая сборка не может записать; вторая запись связки ключей; другое системное окно. Все дают
ожидаемый итог.

Отличия от прежнего `rename-s0/scripts/safe-storage-scenario.mjs` (он сохранён без изменений): тестовые данные не
удаляются (копия профиля кладётся в результат), добавлены повторный запуск новой сборки, настоящий отказ через
«Запретить», запись ответов оператора по шагам и проверка единственной записи связки ключей.

## Попытка 1 (2026-09-29 12:52, недействительна)

Каталог результата `results/20260929-125254` в наборе: только `codesign.txt`, `MANIFEST-sha256.txt`, `system.txt`
(macOS 27.0 26A428, учётная запись `test`). `safe-storage-release.json` и `exit-code.txt` нет: сценарий прерван, а
прежняя версия при прерывании ничего не записывала. Рабочие данные `/tmp/rs0-9zemQI` (владелец `test`, режим 700)
оставлены без изменений до разбора. Процессов приложений, Node и Терминала `test` после попытки нет; остались только
системные агенты сеанса `test`.

На шаге 1 macOS показала не запрос доступа, а окно «Связка ключей не найдена. Для хранения “canvastty Key” не
найдена связка ключей» с кнопками «Отменить» и «Вернуть по умолчанию». Инструкция n/d/a/w этот случай не покрывала.
Попытка не считается ни успехом, ни проверкой отказа.

Причина — в наборе, не в кандидате: прежняя версия сценария передавала приложениям временный HOME
(`/tmp/rs0-*/home`), а Security.framework ищет связку ключей по умолчанию через HOME. Воспроизведено только чтением,
в основной учётной записи, без обращения к её записям:

```
HOME=<настоящий>  security default-keychain  →  "…/Library/Keychains/login.keychain-db"
HOME=<временный>  security default-keychain  →  security: SecKeychainCopyDefault: A default keychain could not be found.
```

Chromium при первом обращении к safeStorage не нашёл связку ключей, и macOS предложила создать связку по умолчанию.
Тот же временный HOME был в прежнем `rename-s0/scripts/safe-storage-scenario.mjs`.

Исправлено (контрольные суммы приложений прежние, изменились только `scripts/safe-storage-release.mjs` и `run.sh`,
новый `MANIFEST-sha256.txt`): приложения получают собственный HOME `test`; предпроверка в `run.sh` и в сценарии
(только чтение) останавливает запуск без связки ключей по умолчанию, при чужом HOME и без графического сеанса;
ответ `x`; запись результата при прерывании. Предпроверка проверена с временным HOME: код 2, приложения не
запускались, каталоги не создавались.

Не установлено: какую кнопку нажали в окне, и был ли `run.sh` запущен из графического сеанса `test`.

## Результат (попытка 2, 2026-09-29 13:47–13:50)

Запуск владельцем в графическом сеансе `test` из Терминала, `run.sh`, код 0, `ok: true`. Копия каталога результата
вне репозитория: `release/1.5.4/verification/s0-5/20260929-134753/` (там же `files-sha256.txt`).

**Соответствие кандидату.** Сумма `MANIFEST-sha256.txt` в результате совпадает с манифестом набора (`4b4f155b…`), все
11 строк манифеста после прогона `OK`. Бинарь `c5193b8a…`, `app.asar` `aad6b185…`, `Info.plist` `1a4d1e99…`, CDHash
`9afa6e3a…` — те же, что в `release/1.5.4/SHA256SUMS` и в выпущенном `Raoden Loom.app`; `codesign --verify --deep
--strict` проходит. Старая сборка — 1.5.3 (`9be00e2c…`, `38918727…`). Обе с `Identifier=io.github.howdeploy.canvastty`,
подпись ad-hoc. Результат относится только к этим суммам.

**Предпроверка** (`preflight.txt`): HOME — домашняя папка `test`, сеанс `Aqua`, связка ключей по умолчанию —
`login.keychain-db` учётной записи `test`.

| Шаг | Сборка | Действие | Чтение/запись | SHA-256 файла секрета | Окно macOS, ответ оператора |
|---|---|---|---|---|---|
| 1 | 1.5.3 | пишет s1, читает | ok, совпадает | `b8d0917f…` | не было |
| 2 | 1.5.4 | читает s1 | ok, совпадает | `b8d0917f…` | запрос, «Разрешить» |
| 2b | 1.5.4, новый запуск | читает s1 | ok, совпадает | `b8d0917f…` | запрос, «Разрешить» |
| 3 | 1.5.3 | читает s1 | ok, совпадает | `b8d0917f…` | не было |
| 4 | 1.5.4 | пишет s2 | ok | `57fdfc3a…` | запрос, «Разрешить» |
| 5 | 1.5.3 | читает s2 | ok, совпадает | `57fdfc3a…` | не было |
| 6 | 1.5.4, новый запуск | читает s2 | ok, совпадает | `57fdfc3a…` | запрос, «Разрешить» |

Связка ключей `test`: до прогона записей `<имя> Safe Storage` для пяти имён нет; после — есть только
`canvastty Safe Storage`, записей `CanvasTTY`, `Raoden Loom`, `Raoden`, `raoden-loom` нет. Все 14 пунктов итога
выполнены. Копия профиля в `work/` содержит файл секрета с `57fdfc3a…` — тем же, что после шага 6.

**Подтверждено:** секрет, записанный 1.5.3, Raoden Loom 1.5.4 читает сразу и после перезапуска; чтение не меняет
байты файла; 1.5.3 после 1.5.4 читает прежний секрет и секрет, записанный 1.5.4 (откат); обе сборки пользуются одной
записью `canvastty Safe Storage`, отдельный ключ не заводится.

**Наблюдение.** 1.5.3, создавшая запись, запроса не получала; Raoden Loom получала запрос при каждом запуске, потому
что оператор нажимал «Разрешить» (однократно), а не «Разрешить всегда». Подпись ad-hoc: доверие записи привязано к
конкретной сборке, после пересборки запрос появится снова.

**Не проверено: настоящий отказ доступа.** На шаге 2 нажато «Разрешить», а не «Запретить» (`denyExercised: false`).
Поэтому на настоящей связке ключей не проверено, что при отказе или ошибке расшифровки файл секрета не удаляется и не
переписывается. Опора только косвенная и проверку не заменяет: в коде ошибка расшифровки даёт исключение
(`PluginSecretsService.read`) или состояние «недоступен» (`GithubAuthService`) без записи в файл; этот случай
покрыт `--self-test` на подставном стенде и модульными тестами сохранённого входа GitHub.

Тестовые данные оставлены: запись `canvastty Safe Storage` в связке ключей `test`, рабочие каталоги `/tmp/rs0-9zemQI`
(попытка 1) и `/tmp/rs0-8W8fqd` (попытка 2), каталоги результатов в наборе.
