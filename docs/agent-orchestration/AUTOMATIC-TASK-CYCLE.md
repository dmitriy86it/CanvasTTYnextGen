# Автоматический цикл задач

Статус: согласованное направление развития CanvasTTY (2026-09-28). Документ архитектурный: он задаёт цель и границы
будущих этапов. Рабочие пространства ([workspaces-spec](implementation/workspaces-spec.md)) приняты владельцем для macOS
2026-09-28 с открытыми ограничениями ([ROADMAP](ROADMAP.md)); текущий этап — A
([контракт](implementation/acceptance-review-spec.md)), подэтап A0. Связанные документы:

- [ROADMAP](ROADMAP.md);

## Целевой сценарий

Пользователь задаёт цель и выбирает режим работы (автопилот или по шагам) и права. Дальше приложение само ведёт каждую
задачу по циклу:

```
цель → план и условия приёмки → исполнение → исполняемые проверки → независимое ревью → исправления ↺ → подтверждённое завершение
```

Пользователь видит:

- кто работает и над какой задачей;
- что проверено;
- какие замечания остались;
- сколько попыток использовано;
- почему работа остановилась.

Переносить отчёты и замечания между агентами вручную не нужно. Рабочее пространство объединяет проектную работу, доска
показывает задачи этого цикла.

## Принципы

1. **Отдельные контексты.**
   - *Планировщик* определяет результат и условия приёмки.
   - *Исполнитель* свободен в технических решениях внутри согласованной задачи, но не уменьшает её объём.
   - *Проверяющий* работает в отдельном контексте. Он получает требования, изменения, результаты проверок и историю
     замечаний. Полную переписку исполнителя ему не передают.
2. **Условия приёмки и доказательства.**
   - У каждой задачи есть проверяемые условия приёмки.
   - Каждое условие закрывается доказательством: результатом исполняемой проверки на проверенном коде, конкретным
     изменением или ответом человека.
   - Результат, написанный агентом в файле или отмеченный галочкой, сам по себе доказательством не является.
3. **Замечания.**
   - У замечания есть постоянный идентификатор, доказательство и условие закрытия.
   - Обычные исправления возвращаются исполнителю автоматически.
   - Новые пожелания и косметика оформляются отдельно и не блокируют исходную задачу бесконечно.
4. **Успех определяет приложение, а не агент.** Задача готова, только если выполнены все три условия:
   - обязательные проверки прошли на том же коде, который проверялся;
   - условия приёмки выполнены;
   - блокирующие замечания закрыты.
5. **Три разных исхода:**
   - *успех* — пункт 4;
   - *блокировка* — нужны данные, решение или разрешение человека;
   - *исчерпание бюджета или отсутствие прогресса* — пауза с объяснением.

   Ни блокировка, ни исчерпание не показываются как успех.
6. **Человек участвует только по необходимости:**
   - нужны его данные;
   - нужно значимое решение;
   - нужно разрешение за пределами выданных прав.
7. **Права не расширяются.**
   - Автоматизация сохраняет выбранные пользователем права, навыки и возможности CLI.
   - Автоматизация не расширяет права.
   - Режим автоматизации отделён от прав (stage-13 §1).
8. **Один источник состояния.**
   - Доска, карточки агентов, виджет активности и итоги читают одно состояние: журнал запуска и состояние приложения
     в main.
   - Отдельного «статуса задачи», который мог бы разойтись с оркестрацией, нет.
9. **Перепланирование не ослабляет требования.**
   - Перепланирование может менять способ реализации и разбиение работы.
   - Оно не вправе молча удалять обязательные требования пользователя или ослаблять приёмочные проверки.
   - Удаление или ослабление требования возможно только с явного решения человека, и это видно в журнале.

## Прослеживаемость: от требования до приёмки

```
требование пользователя → задача → проверка → доказательство → решение о приёмке
```

- **Требование** записано так, как его задал пользователь, и имеет постоянный идентификатор.
- **Задача** ссылается на требования, которые она закрывает. Каждое обязательное требование покрыто хотя бы одной
  задачей. Перепланирование сохраняет это покрытие (принцип 9).
- **Проверка** — исполняемая проверка или ревью, привязанная к условию приёмки задачи.
- **Доказательство** — результат проверки на том же коде, конкретное изменение или ответ человека (принцип 2).
- **Решение о приёмке** принимает приложение по принципу 4. В итоге видна вся цепочка: для каждого требования —
  задачи, проверки, доказательства и решение. Требование без доказательства делает итог незавершённым, а не
  «успешным».

## Связи сущностей

```
Рабочее пространство ─┬─ связи агентов (лид → исполнитель)
                      ├─ запуски (владелец фиксируется при создании запуска)
                      └─ задачи доски (будущее) ── запуск ── рабочая копия (папка проекта | worktree | копия) ── результат
```

- Пространство, папка проекта и worktree — разные сущности ([workspaces-spec §1.1](implementation/workspaces-spec.md)).
- **Задача (будущее)** принадлежит одному пространству и ведётся одним или несколькими запусками. Её состояние
  выводится из этих запусков.
- **Результат** — это:
  - изменения в рабочей копии;
  - проверки на них;
  - commit, push и QA, если они выполнены приложением;
  - итог запуска.

## Чего не хватает

- **Отдельный проверяющий.** Сейчас ревью выполняет лид в той же сессии, где он планировал: контекст планировщика и
  проверяющего общий.
- **Явные условия приёмки.** Этап плана — это название и задание. Проверяемых условий приёмки с доказательствами по
  каждому нет.
- **Постоянные идентификаторы замечаний.** Замечания — список строк одного ревью. Идентификатора, условия закрытия и
  прослеживания между раундами нет. Блокирующие замечания не отделены от пожеланий.
- **Задача как сущность.** Цель = один запуск. Ни доски, ни зависимостей, ни нескольких задач одного пространства нет.
- **Параллельные исполнители.** Сейчас в одной папке может идти только один активный запуск (`folder_busy`). Проверки
  объединённого результата нет.

## Этапы (каждый проверяемый отдельно)

### A. Условия приёмки и независимое ревью

Контракт (черновик, после первого внешнего ревью; реализация не разрешена): [acceptance-review-spec](implementation/acceptance-review-spec.md).

- План задаёт для каждого этапа условия приёмки. Перепланирование может менять их разбиение, но удалить или ослабить
  обязательное условие — только по явному решению человека (принцип 9); изменение видно в журнале.
- Проверяющий получает отдельный контекст: требования, diff, результаты проверок, историю замечаний. Переписку
  исполнителя он не получает.
- Замечания получают постоянный id, признак «блокирует / пожелание», доказательство и условие закрытия. Пожелания не
  блокируют этап.
- Приложение считает этап готовым только по пункту 4 принципов. Итог показывает каждое условие приёмки вместе с его
  доказательством.
- **Критерии проверки:**
  - «accept» при невыполненном условии не принимает этап;
  - закрытое замечание не возвращается без нового доказательства;
  - пожелание не держит этап;
  - проверяющий не видит переписку исполнителя.

### B. Доска задач

- Колонки: очередь → работа → проверка → готово.
- Зависимости задач и причина блокировки: ждёт другую задачу, ответ, разрешение или проверку.
- Статус карточки задачи вычисляется из её запусков. «Готово» — только по пункту 4.
- Задачи хранятся по пространству и привязаны к запускам: у запуска появится ссылка на задачу.
- **Критерии проверки:**
  - статус на доске, карточке, в виджете и в итоге совпадает на одних данных;
  - перезапуск приложения не меняет статусы;
  - «готово» нельзя получить отметкой в файле.

### C. Параллельные исполнители

- Несколько исполнителей на разных задачах одного проекта, каждый в своём worktree. Правило `folder_busy` ослабляется
  только для worktree.
- Конфликты выявляются до объединения. Объединённый результат заново проходит обязательные проверки.
- Итог показывает вклад каждого исполнителя и проверку объединения отдельно.
- **Критерии проверки:**
  - при конфликте работа не теряется молча;
  - объединение без повторной проверки не считается готовым;
  - права каждого исполнителя равны выбранным пользователем.
- **Обязательно для завершения этапа C:** вернуться к [EXP-SPEC-01](EXP-SPEC-01-speculative-execution.md), проверить
  готовность по его §9 и представить план ограниченного пилота. Этап C не считается завершённым без этого пункта.

Несколько процессов Claude — это не Agent Teams. Интеграция с настоящими Agent Teams — отдельная проверка.

### D. Эксперимент: спекулятивное выполнение задач

- **Идентификатор:** EXP-SPEC-01. **Статус:** Запланирован; ожидает принятия этапов A–C; не запускался.
- **Суть.** Выполнение вероятного следующего шага до окончательного подтверждения его зависимости. Пока проверяющий
  оценивает задачу A, исполнитель готовит зависимую задачу B в отдельной рабочей копии на явно записанном
  предположении о результате A. Это не спекулятивное декодирование: генерация токенов внутри модели — другая
  технология.
- **Отличие от этапа C.** C — независимые задачи параллельно. D — зависимая задача, начатая на предположении.
- **Главные правила:**
  - предварительный результат не считается выполненным и не объединяется автоматически;
  - изменение зависимости требует повторной проверки;
  - никаких внешних и необратимых действий, права не расширяются.
- **Результат** — решение «внедрять / доработать / отказаться» с доказательствами. Отрицательный результат тоже
  завершает эксперимент.
- План, модель данных, метрики и сценарии: [EXP-SPEC-01](EXP-SPEC-01-speculative-execution.md).

**Порядок развития:** A → B → C → D. Каждый следующий этап начинается после принятия предыдущего.

## Как это учитывается в рабочих пространствах (принятый этап)

- Пространство владеет запусками. Владелец фиксируется при создании запуска и не переезжает вслед за карточками: так
  будущая задача сможет ссылаться на историю своего пространства.
- Счётчики пространства и общий виджет считаются из того же состояния оркестрации. Будущая доска будет использовать
  тот же источник.
- Полей «на будущее» (задачи, условия, id замечаний) в данных этого этапа нет.
