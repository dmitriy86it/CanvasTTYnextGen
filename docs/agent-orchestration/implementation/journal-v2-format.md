# Этап A: формат журнала v2 — редакция 5i

**Статус: проект, на утверждение владельца.** Дополняет [контракт этапа A](acceptance-review-spec.md) редакции 5h
(§11 там ссылается сюда). Принятые разделы 5h не меняются. Где 5i предлагает отступить от 5h, это сказано явно и
вынесено в «Открытые вопросы» (§7). Код приложения этой редакцией не меняется.

Вход:
- 5h целиком, включая §2.2.1 (`minReaderVersion`, `skippable`, версия по первой записи);
- [Автоматический цикл задач](../AUTOMATIC-TASK-CYCLE.md) (принципы 2–5, 9) и [ROADMAP](../ROADMAP.md);
- формат v1: `src/main/services/orchestration/journal.ts` (схемы `DATA_SCHEMAS`, `applyRecord`), `store.ts`, `schema.ts`;
- решение владельца о необязательных командах проверки (§0).

## 0. Решение владельца: необязательные команды проверки

1. Поле «Команды проверки» необязательное.
2. Если оно пустое, лид в первом ходе предлагает команды по файлам проекта и обосновывает каждую.
3. Автопилот принимает предложенные команды автоматически. Пошаговый режим ждёт «Принять» или «Изменить».
4. Если команд нет совсем, итог — «Завершено без проверок», а не «подтверждено». Commit делается как запрошено. Push и
   QA — только после явного подтверждения пользователя, даже в автопилоте.

Команды, предложенные лидом, — кандидаты в условия готовности этапа A (§6, критерии A1).

Как это читается в 5i:
- Пустые команды есть только в v2. Цель v1 по-прежнему требует 1–16 команд (`checkGoal`).
- Подтверждение push и QA (п. 4) относится к запуску **без проверок**. Запуск с проверками делает push и QA, как
  задано в цели (stage 13). Распространить подтверждение на все запуски — вопрос 7.4.

## 1. Конверт записи v2

| Ключ | v1 | v2 |
|---|---|---|
| `v` | `1` | `2` в каждой записи; другое значение посреди журнала — `invalid_event` (5h §2.1) |
| `seq`, `ts`, `runId`, `type`, `prevHash`, `hash`, `data` | как есть | без изменений; хеш считается по каноническому JSON всех ключей, кроме `hash` |
| `minReaderVersion` | нет | **только в первой записи** (`run.created`), целое `2`; в остальных записях — `invalid_event` |
| `skippable` | нет | не пишется (§3.3) |
| `formatPreview` | нет | **только в первой записи** журналов dev-сборок A1–A3 (`true`); в формате A4 не пишется (§3.4) |

`run.created.data` остаётся ровно `{goal}`, где `goal` — TextRef. Сборка 1.5.7 (A0) берёт цель журнала новой версии
из `run.created` строгой схемой v1 (`newerGoal`): лишний ключ в `data` скрыл бы цель. Новые ключи цели живут только
внутри текста цели:
- `commands` может быть `[]`, тогда `checks: []`;
- `mode`, `finish` и остальное — как в stage 13 (форма `checkGoal`). Цель без `mode` — автопилот, как сейчас
  (`progressOf`: `mode ?? "autopilot"`).

## 2. Записи

Обозначения:
- **Пишет** — main (приложение само), лид, проверяющий (через отчёт хода, запись делает main), пользователь (команда);
- **Команда** — общий протокол `command.received` → запись решения → `command.completed`; повтор с тем же
  `commandId` возвращает записанный результат без второй записи (5h §3.5);
- `TextRef` — `{sha256, bytes}` текста в `texts/`; канонический JSON.

Тексты:

```json
// отчёт хода плана v2 (5h §2.3) — новое поле checks
{"stages": [...], "dropped": [], "dropRequirements": [], "question": null,
 "checks": null | {"checks": [{"command": "npm test", "why": "1–500 символов", "source": ["package.json"]}],
                   "none": null | "почему команд нет, 1–500 символов"}}

// checks.proposed.proposal — предложение с номерами, присвоенными приложением по порядку
{"checks": [{"id": "cmd-1", "command": "npm test", "why": "…", "source": ["package.json"]}], "none": null}

// checks.decided.checks
{"checks": [{"id": "cmd-1", "command": "npm test", "origin": "lead" | "person"}]}

// run.status(completed).completion.basis — §2.3
```

**Поле `checks` отчёта плана** (проверка отчёта, нарушение → `invalid_report`, записей нет):
1. Первый ход плана запуска с `commands: []`, пока нет `checks.decided`, обязан дать непустое `checks` и `question:
   null`. Предложение вместе с вопросом — `invalid_report`: сначала ответ, затем ход плана с предложением.
2. Любой другой ход плана — `checks: null`. Это относится и к ходу после «Изменить», и к цели с командами: там даже
   `{checks: [], none: "…"}` — `invalid_report`.
3. Строки `command` — как в `checkGoal`: 1–1000 символов после обрезки пробелов, без `\0`, `\r`, `\n`, без повторов,
   0–16 строк. `none` непуст ровно тогда, когда строк 0. `source` — 0–16 относительных путей.
4. План этого отчёта проверяется целиком (5h §2.3) против предложенных команд: условие `check` ссылается только на
   `cmd-<n>` предложения.

**Проверки при воспроизведении**, по двум этапам разбора 5h §3.10:
- первый этап, по данным записей, нарушение → `replay_conflict`:
  - `checks.proposed`: `turnId` — завершённый ход `plan`, последний `orch.turn`; в журнале нет другой
    `checks.proposed`;
  - `checks.decided`: `proposalTurnId` — ход единственной `checks.proposed`, решения ещё нет;
    `by: "autopilot"` ⇔ `commandId: null` ⇔ `decision: "accept"`; при `commandId` — открытая команда;
  - между `checks.proposed` и `checks.decided` нет `turn.intent` с ролью `executor`/`reviewer`, `check.*`,
    `plan.recorded`;
  - `plan.recorded` хода предложения — только после `checks.decided(accept)` и без другого `orch.turn` между ними;
- второй этап, по текстам, нарушение → `integrity: "corrupt"`, `detail.phase: "texts"`:
  - `checks.proposed` — только при `commands: []` в цели; `count` = числу строк; `id` — `cmd-1…cmd-n` по порядку;
  - при `commands: []` до `checks.decided` нет `plan.recorded`, хода исполнителя или проверяющего и `check.*` (в том
    числе в журнале без `checks.proposed`);
  - автопилотное решение — только при `goal.mode` = `autopilot` или без `mode`; решение по команде — при любом режиме;
  - `accept`: `checks` совпадает с предложением (`id`, `command`, `origin: "lead"`);
  - текст `proposal` — строки отчёта плана в том же порядке с добавленным `id` (в самом отчёте `id` нет: лишний ключ
    → `invalid_report`);
  - `edit`: строки по правилу п. 3 выше; `id` — `cmd-1…cmd-n` по порядку нового списка; `origin: "lead"` — у
    строки, текст которой совпадает с какой-либо строкой предложения, иначе `person`.

**Пауза `awaiting_checks_decision`.** Допустимы только команда `checks.decide` («Принять», «Изменить») и Stop.
Resume, step, `clarification.added`, `limits.changed` → `rejected(invalid_state)`, как на `coverage_lost` (5h §3.6
п. 2). Подготовка идёт до первого хода (`cycle.ts`), вопроса на этой паузе быть не может. Набор команд меняется только
этим решением, один раз; цель с командами задаёт набор сразу, и `checks.*` в её журнале нет.

**Пауза `awaiting_finish_confirmation`.** Допустимы только команда `finish.confirm` и Stop. Остальное, в том числе
resume и step, → `rejected(invalid_state)`.

### 2.3. Требования, условия, замечания, завершение: что выводится, а не пишется

Отдельной записи нет у:
- **требований** — `R<n>` по номеру в `goal.criteria` текста цели из `run.created` (5h §1). Цепочка хешей фиксирует
  текст. Снять требование может только `plan.decided(accept)` с `dropRequirements`;
- **условий и доказательств** — `C<n>` из текстов планов (`plan.recorded`, `plan.decided(accept)`). Доказательство:
  - `check` — `check.finished` + `check.assessed` на текущем `checkKey`;
  - `change` — `review.assessed.applied.conditionsMet`;
  - `person` — `person.decided`;
  - снятие условия — `plan.decided(accept)`;
- **замечаний и их истории** — `F<n>` из `applied` и решений. История `F` — упорядоченный по `seq` список событий:
  - `opened`, `closed`, `reopened`, `refused`, `unchanged`, `disputed` — из `review.assessed`;
  - `closed_by_person`, `to_wish` — из `person.decided`;
  - `moved`, `closed_by_person`, `to_wish` — из `plan.decided`.

  У каждого события есть `runKey` и ход. Уровень меняется только событием `to_wish`.

**Функция завершения.** Чистая функция журнала, текстов и текущего снимка (`checkKey`, `runKey`, дерево):

```
completion(state, texts, snapshot) → { allowed: true, kind } | { allowed: false, blockers }

blockers (все, в этом порядке; пусто ⇔ allowed):
  checks_undecided                      checks.proposed без checks.decided
  plan_proposal_pending                 plan.proposed без plan.decided
  disputed_pending(index)               спорный пункт без person.decided (5h §3.4)
  stage_not_accepted(s)                 этап действующего плана не принят (5h §3.3)
  condition_unmet(C)                    действующее условие без действующего доказательства (5h §3.3, §3.7)
  check_not_passed(cmd)                 команда действующего набора не passed на текущем checkKey
  requirement_unmet(R)                  R не снято и (не покрыто выполненными условиями
                                        или нет met в свежем финальном отчёте) (5h §3.8)
  blocking_open(F)                      открытое blocking
  final_report_stale                    нет финального review.assessed на текущих runKey и
                                        clarificationVersion, или request ≠ "none"
  finish_pending(step)                  шаг, запрошенный целью, не done для текущего дерева/commit
                                        и не отклонён finish.confirmed(decline)
  finish_awaiting_person(step)          push/qa запуска без проверок без finish.confirmed для
                                        текущего дерева и commit

kind = действующий набор команд пуст ? "no_checks" : "confirmed"
```

Правило «завершение разрешено, только если…»: `run.status(completed)` пишется, только когда `completion(...)`
вернула `allowed: true`. В запись идут `kind` и `basis` — текст с входами решения:
- действующие команды и `checkRunId` их последних `passed`;
- `R → C → доказательство`;
- финальный ход проверяющего, `runKey`, `checkKeys` (по команде);
- исход шагов commit/push/QA.

**Проверки `completed` и `finish.intent` при воспроизведении**, так что «Завершено» нельзя записать мимо функции:
- первый этап (по записям), нарушение → `replay_conflict`:
  - нет `checks.proposed` без `checks.decided` и `plan.proposed` без `plan.decided`;
  - все этапы действующего плана приняты (`stage.accepted`);
  - есть финальный `review.assessed` (`stage: null`) с `request: "none"`, и после него нет `orch.turn`; в журнале
    `formatPreview` (ревью лидом, A1–A2) вместо него — `review.recorded(stage: null, verdict: "complete")` последнего
    финала, а проверки по `applied` второго этапа не действуют;
  - нет шага finish в состоянии `in_flight`/`outcome_unknown`/`unknown`;
  - `finish.intent(push|qa)`: в запуске без проверок (`checks.decided.count = 0`) ему предшествует `finish.confirmed`
    с `confirm` для этого шага, и после этой записи нет нового `finish.result(commit)`;
- второй этап (по текстам и `applied`), нарушение → `corrupt`, `detail.phase: "texts"`:
  - `kind` = `no_checks` ⇔ набор команд пуст;
  - для `confirmed` у каждой команды набора `basis` называет `checkRunId` с `passed`, `check.assessed` на
    `basis.runKey` и `checkKeys`;
  - нет открытого `blocking` и неразрешённого спорного пункта по `applied` и решениям;
  - каждое `R` снято `plan.decided(accept)` или имеет `met` в `requirements` финального отчёта;
  - `finish.intent(push|qa)` без проверок: `tree` и `commit` в `params` равны `tree`/`commit` подтверждения;
  - каждый шаг, запрошенный целью, — `done` для `basis`-дерева или `decline` в подтверждении.

**«Завершено без проверок» не выглядит подтверждённым:**
- `kind: "no_checks"` показывается своей строкой «Завершено без проверок». Значок и цвет не те, что у «Завершено»:
  это одна функция `runStatus.ts` для панели, карточек, виджета активности и истории пространства;
- итог открывается строкой «Команды проверки не запускались»;
- диалог подтверждения push и QA повторяет, что проверок не было;
- критерий A1-4 перечисляет каждое место показа статуса.

### 2.4. Порядок первого хода плана при пустых командах

```
orch.turn(plan) → turn.intent(lead) → turn.finished(report: план + предложение команд)
  → [отчёт невалиден] invalid_report, записей нет → новый ход плана
  → checks.proposed
      автопилот:  checks.decided(accept, by autopilot) → plan.recorded(тот же turnId) → этап 1
      пошагово:   run.status(paused, awaiting_checks_decision)
                    «Принять»:   command.received → checks.decided(accept, person) → command.completed
                                 → run.status(running) → plan.recorded(тот же turnId)
                                 → (reviewPlan) run.status(paused, plan_review) | этап 1
                    «Изменить»:  command.received → checks.decided(edit, person) → command.completed
                                 → run.status(running) → orch.turn(plan) нового хода → plan.recorded
                    Stop:        как сейчас
```

`run.status(running)` после решения пишет сам обработчик команды: resume и step на этой паузе отклоняются (§2.1), а
цикл на паузе ничего не делает. То же для `finish.confirmed`.

`plan.recorded` после `checks.decided(accept)` — единственный случай, когда запись плана идёт не сразу за
`turn.finished`. Разрешено, только если между ними нет другого `orch.turn`.

Новый ход плана после «Изменить»:
- **не** расходует `replans`: действующей версии плана ещё нет;
- обязан содержать `checks: null`: предложить команды можно только один раз.

| Что в журнале | Действие при открытии / решении цикла |
|---|---|
| `turn.finished` хода плана с предложением, нет `checks.proposed` | как «ход без записи результата»: новый ход плана (5h `stage-5-contract` §7) |
| `checks.proposed`, нет `checks.decided`, автопилот, запуск не терминальный | main пишет `checks.decided(accept, autopilot)` |
| `checks.proposed`, нет `checks.decided`, пошагово | пауза `awaiting_checks_decision` с тем же предложением |
| `checks.decided(accept)`, нет `plan.recorded` этого хода | main пишет `plan.recorded` по отчёту хода (тот же результат проверки: входы не менялись) |
| `checks.decided(edit)`, нет нового хода плана | новый ход плана |
| `command.received(checks.decide)` без `command.completed` | 5h §3.5: есть `checks.decided` с этим `commandId` → `accepted`, нет → `interrupted` |
| то же для `finish.confirm` | то же по `finish.confirmed` |
| решение записано (`checks.decided` или `finish.confirmed` после последней паузы этой причины), запуск всё ещё на паузе `awaiting_checks_decision`/`awaiting_finish_confirmation` | сбой между `command.completed` и `run.status(running)`: при открытии main пишет `run.status(paused, recovered)`, как после любого сбоя (открытие работу не запускает, 5h §3.1.1). «Продолжить» из `recovered` ведёт дальше по записанному решению; само решение не повторяется |
| `finish.confirmed`, дерево или commit с тех пор другие | решение не действует → снова `awaiting_finish_confirmation` |

## 3. Совместимость

### 3.1. `minReaderVersion` = 2

По §2.2.1 п. 4 журнал вправе объявить `minReaderVersion: 1`, только если читатель v1 (A0, сборка 1.5.7)
**пропуском** новых записей и **игнорированием** новых полей получает верное показанное состояние. Разбор по
каждой записи: что 1.5.7 показала бы при `minReaderVersion: 1`, если бы запись была `skippable` (новые типы) или
спроецирована на поля v1 (изменённые):

| Запись | Что покажет 1.5.7 | Верно? |
|---|---|---|
| `checks.proposed` | нет предложения; запуск «идёт», команд нет | **нет**: скрыто, что ждётся решение о командах |
| `checks.decided` | нет набора команд: `goal.checks` пуст, `check.*` с `cmd-1` не в списке целей (`progressOf` их не покажет) | **нет**: проверки, по которым шла приёмка, не видны |
| `finish.confirmed` | push/QA выполнены без объяснения, отказ не виден | **нет**: «отказано пользователем» выглядит как «не запрашивалось» |
| `review.assessed` | ревью нет; `stage.accepted` без `review.recorded(accept)` → `replay_conflict` → откат показа | **нет** (откат), а без проверки `stage.accepted` — этапы приняты без замечаний, открытые `blocking` скрыты |
| `review.discarded` | ход проверяющего без результата | **нет**: не видно, почему ревью повторялось |
| `plan.proposed` | ход плана без плана, действует старый | **нет**: скрыто ожидающее решение и снимаемые условия |
| `plan.decided` | старый план остаётся; следующая `plan.recorded` с версией через одну → `replay_conflict` | **нет** |
| `person.decided` | решение человека не видно | **нет**: условие `person` и закрытие человеком пропадают |
| `run.status(completed)` с `completion` | поле отброшено → «Завершено» | **нет, главное**: «Завершено без проверок» выглядит как подтверждённое |
| `run.status(paused)` с новыми `reason` | значение вне `PAUSED_REASONS` → `invalid_event` → откат показа | откат (показ «мигает» между полным и сырым) |
| `turn.intent(role: reviewer)` | вне `["lead","executor"]` → `invalid_event` → откат | откат |
| `stage.accepted` | `reviewTurnId` — ход проверяющего без `review.recorded(accept)` → `replay_conflict` → откат | откат; без этой проверки — «этап принят» без ревью |
| `check.started` (`checkId` из решённого набора) | примет; `progressOf` такие проверки не покажет (их нет в `goal.checks`) | **нет**: проверки невидимы |
| `finish.intent(push\|qa)` после подтверждения | примет без проверки подтверждения | **нет**: push выглядит обычным шагом, решение человека не видно |
| `orch.turn.tree`, `plan.recorded.conditionsAssigned` | поле отброшено | да |
| `run.created` (цель с `commands: []`) | цель показана; `progressOf` — без проверок | да |

Вывод: почти каждая новая запись при пропуске даёт неверное показанное состояние. Поэтому **`minReaderVersion: 2`**
по §2.2.1 п. 4. Сборка 1.5.7 показывает такой журнал в режиме §2.2:
- «Более новая версия · создан более новой версией Raoden Loom»;
- цель и сырые записи с проверкой цепочки;
- состояния нет, и поэтому оно не может быть неверным;
- доступно только «Отпустить связь» (§2.2.1 п. 1).

Сборки ≤ 1.5.6 моста не имеют: `unsupported_version`/`journal_corrupt`, остальные запуски целы (5h §2.2, проба S-A3).

### 3.2. Проверено на сборке 1.5.7

Фикстуры (§4) прочитаны функцией `parseJournal` из `main` (код A0 совпадает с 1.5.7) скриптом
`v2-fixtures/build.mjs --check`, только чтение. Таблица — в [`v2-fixtures/README.md`](v2-fixtures/README.md).
- `minReaderVersion: 2`: все 8 — `newer_version`, цепочка `ok`, цель читается.
- `minReaderVersion: 1`: откат показа на первой записи `checks.*` (`unknown_record`) или на первом ходе проверяющего
  (`invalid_event`).
- `minReaderVersion: 1` и `skippable` у новых видов: откат только на `turn.intent(reviewer)` или новой причине паузы.
  До неё 1.5.7 показывала бы v1-состояние без решений v2 — то самое неверное состояние из §3.1. Откат здесь
  защищает случайно, а не по правилу.

### 3.3. `skippable`

Ни одна запись v2 не помечается `skippable: true`:
- при `minReaderVersion: 2` сборка 1.5.7 признак не читает (режим §2.2);
- для будущих читателей признак значит «пропуск не меняет состояние», а у каждой новой записи v2 это не так (§3.1).

Будущая версия v3 решает это для своих записей сама.

### 3.4. Когда новые запуски пишутся в v2

Предложение 5i (согласуется с 5h §5):
- **A1–A3:** запись v2 есть в коде, но включается только признаком разработки `CANVASTTY_JOURNAL_V2=1`.
  Он читается через `developmentEnv`, поэтому упакованная сборка его игнорирует. Им пользуются тесты, smoke и пробный
  прогон владельца на dev-сборке. Пользовательские запуски пишутся в v1.
- **A4:** каждый новый нативный запуск (цель с `commands`, в том числе пустым) пишется в v2 без признака.
  Structured-режимы остаются v1 (5h §2.1).
- Журналы dev-сборок A1–A3 несут в первой записи `formatPreview: true`. Их форма ещё не окончательна: в A1–A2 ревью
  делает лид (`review.recorded`), `orch.turn.tree` появляется в A3. Сборка A4 и дальше показывает такой журнал
  только для чтения, как журнал более новой версии (§2.2: цель, сырые записи, «Отпустить связь»), с подписью
  «создан пробной сборкой этапа A». Она не пытается его воспроизвести и не называет повреждённым. Сборка 1.5.7 видит
  его как любой журнал v2 (`minReaderVersion: 2`).
- Формат A4 окончателен для v2: дальше — только новая версия журнала.

Пустые команды проверки доступны только запуску v2. Пока запись v2 выключена, поле «Команды проверки» обязательно,
как сейчас.

Альтернатива — включить v2 для пользователей сразу с A1 (вопрос 7.1). Тогда формат замораживается на A1, а
A2–A4 обязаны продолжать журналы A1, в которых ревью ещё делает лид.

### 3.5. Запуски v1 в новой версии

- Продолжаются и завершаются по правилам v1 (ревью лидом, `review.recorded`, команды обязательны).
- В v2 не переводятся, новых записей v2 в журнал v1 не попадает.
- `openRun` для v1 не меняется: незавершённые команды → `interrupted`, оборванный хвост → `journal_torn_tail`.
- `completed` v1 показывается как раньше («Завершено»). Признака `no_checks` у v1 нет: цель v1 всегда с командами.

## 7. Открытые вопросы владельцу

1. **Когда новые запуски пишутся в v2.**
   - **Рекомендация:** признак разработки до A4, по умолчанию с A4 (§3.4, как 5h §5).
   - Альтернатива: пользовательский признак с A1. Тогда формат замораживается на A1, и A4 продолжает журналы с ревью лидом.
2. **Новый состав A1–A4** (§5): необязательные команды и функция завершения — в A1, содержание 5h A1 — в A2,
   5h A2 и A3 объединены в A3. **Рекомендация:** принять. A1 минимален и даёт решение владельца первым.
3. **QA при отказе от push.** **Рекомендация:** решения независимы. Диалог предупреждает, если QA проверяет
   неотправленный commit.
4. **Подтверждение push/QA для запусков с проверками.** **Рекомендация:** нет. Решение владельца сформулировано для
   «команд нет совсем», для остальных действует stage 13.
5. **Защита автопилота от опасной предложенной команды.** **Рекомендация:**
   - без отдельного фильтра: команда идёт в ту же песочницу проверок, что и пользовательская;
   - команды видны в панели и итоге до первого запуска;
   - фильтр по тексту даёт ложное чувство безопасности.
6. **Изменение команд после принятия.** **Рекомендация:** нет в этапе A. Только «Изменить» на паузе предложения;
   другой набор — новый запуск.
7. **Предложение при цели с командами.** **Рекомендация:** нет. Лид предлагает команды, только если поле пустое.
   Непустое предложение в отчёте при заданных командах — `invalid_report`.
