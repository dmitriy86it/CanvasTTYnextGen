# Этап A: формат журнала v2 — редакция 5i

**Статус: утверждено владельцем 2026-10-01 (с решениями §7); дополнено решениями A1.1 от 2026-10-02 (§7а, §2.6).** Дополняет [контракт этапа A](acceptance-review-spec.md)
редакции 5h (§11 там ссылается сюда). Принятые разделы 5h не меняются. Где 5i отступает от 5h (состав подэтапов §5),
это решение владельца §7.

Вход:
- 5h целиком, включая §2.2.1 (`minReaderVersion`, `skippable`, версия по первой записи);
- [Автоматический цикл задач](../AUTOMATIC-TASK-CYCLE.md) (принципы 2–5, 9) и [ROADMAP](../ROADMAP.md);
- формат v1: `src/main/services/orchestration/journal.ts` (схемы `DATA_SCHEMAS`, `applyRecord`), `store.ts`, `schema.ts`;
- решение владельца о необязательных командах проверки (§0).

## 0. Решение владельца: необязательные команды проверки

1. Поле «Команды проверки» необязательное.
2. Если оно пустое, лид в первом ходе предлагает команды по файлам проекта и обосновывает каждую.
3. Автопилот принимает предложенные команды автоматически (уточнено решением §7 п. 5: только при запрещённой сети
   проверок). Пошаговый режим ждёт «Принять» или «Изменить».
4. Если команд нет совсем, итог — «Завершено без проверок», а не «подтверждено». Commit делается как запрошено. Push и
   QA — только после явного подтверждения пользователя, даже в автопилоте.

Команды, предложенные лидом, — кандидаты в условия готовности этапа A (§6, критерии A1).

Как это читается в 5i:
- Пустые команды есть только в v2. Цель v1 по-прежнему требует 1–16 команд (`checkGoal`).
- Подтверждение push и QA (п. 4) относится к запуску **без проверок**. Запуск с проверками делает push и QA, как
  задано в цели (stage 13); так и решено (§7 п. 4).
- Автопилот принимает предложение сам, только если сеть проверок запрещена (§7 п. 5); иначе ждёт «Принять», как
  пошаговый режим.

## 1. Конверт записи v2

| Ключ | v1 | v2 |
|---|---|---|
| `v` | `1` | `2` в каждой записи; другое значение посреди журнала — `invalid_event` (5h §2.1) |
| `seq`, `ts`, `runId`, `type`, `prevHash`, `hash`, `data` | как есть | без изменений; хеш считается по каноническому JSON всех ключей, кроме `hash` |
| `minReaderVersion` | нет | **только в первой записи** (`run.created`), целое `2`; в остальных записях — `invalid_event` |
| `skippable` | нет | не пишется (§3.3) |
| `formatPreview` | нет | **только в первой записи** журналов dev-сборок A1–A3 (`true`); в формате A4 не пишется (§3.4) |

`run.created.data` остаётся ровно `{goal}`, где `goal` — TextRef. Сборка 1.5.7 (A0) берёт цель журнала новой версии
из `run.created` строгой схемой v1 (`newerGoal`): лишний ключ в `data` скрыл бы цель. Новые ключи цели живут только
внутри текста цели:
- `commands` может быть `[]`, тогда `checks: []`;
- `mode`, `finish` и остальное — как в stage 13 (форма `checkGoal`). Цель без `mode` — автопилот, как сейчас
  (`progressOf`: `mode ?? "autopilot"`).
- `models` (дополнение 2026-10-04, выбор модели по ролям): `{lead?, executor?, reviewer?}` — имя модели роли, только
  выбранные роли; нет ключа или роли — «Как в CLI» (модель не передаётся, решает конфиг CLI). Модель передаётся на
  один поток Codex (`thread/start`/`thread/resume`, поле `model`) или один запуск Claude (`--model`); config.toml и
  настройки Claude не меняются. **Только в v2**: цель v1 с `models` — `invalid_goal`. Причина: сборка 1.5.7 читает
  цель v1 без строгой схемы и молча потеряла бы ключ — роль работала бы на модели из конфига CLI, а не на выбранной.
  Журнал v2 сборка 1.5.7 не продолжает (`minReaderVersion: 2`), так что смысл поля не теряется. Какой моделью роль
  работала на деле — из ответа CLI при старте (`session` в «Логе»: `thread/start.model`, `system/init.model`).

## 2. Записи

Обозначения:
- **Пишет** — main (приложение само), лид, проверяющий (через отчёт хода, запись делает main), пользователь (команда);
- **Команда** — общий протокол `command.received` → запись решения → `command.completed`; повтор с тем же
  `commandId` возвращает записанный результат без второй записи (5h §3.5);
- `TextRef` — `{sha256, bytes}` текста в `texts/`; канонический JSON.

### 2.1. Новые записи

| Запись | Поля (тип, обязательность) | Пишет | Идемпотентность | Влияние на состояние |
|---|---|---|---|---|

| `review.discarded` | 5h §2.4 | main | одна на ход | 5h §3.1, §3.1.1: счёт отброшенных ревью |

Тексты:

```json
// отчёт хода плана v2 (5h §2.3) — новое поле checks
{"stages": [...], "dropped": [], "dropRequirements": [], "question": null,
 "checks": null | {"checks": [{"command": "npm test", "why": "1–500 символов", "source": ["package.json"]}],
                   "none": null | "почему команд нет, 1–500 символов"}}

// checks.proposed.proposal — предложение с номерами, присвоенными приложением по порядку
{"checks": [{"id": "cmd-1", "command": "npm test", "why": "…", "source": ["package.json"]}], "none": null}

// checks.decided.checks
{"checks": [{"id": "cmd-1", "command": "npm test", "origin": "lead" | "person"}]}

// run.status(completed).completion.basis — §2.3
```

**Поле `checks` отчёта плана** (проверка отчёта, нарушение → `invalid_report`, записей нет):
1. Первый ход плана запуска с `commands: []`, пока нет `checks.decided`, обязан дать непустое `checks` и `question:
   null`. Предложение вместе с вопросом — `invalid_report`: сначала ответ, затем ход плана с предложением.
2. Любой другой ход плана — `checks: null`. Это относится и к ходу после «Изменить», и к цели с командами: там даже
   `{checks: [], none: "…"}` — `invalid_report`.
3. Строки `command` — как в `checkGoal`: 1–1000 символов после обрезки пробелов, без `\0`, `\r`, `\n`, без повторов,
   0–16 строк. `none` непуст ровно тогда, когда строк 0. `source` — 0–16 относительных путей.
4. План этого отчёта проверяется целиком (5h §2.3) против предложенных команд: условие `check` ссылается только на
   `cmd-<n>` предложения.

**Проверки при воспроизведении**, по двум этапам разбора 5h §3.10:
- первый этап, по данным записей, нарушение → `replay_conflict`:
  - `checks.proposed`: `turnId` — завершённый ход `plan`, последний `orch.turn`; в журнале нет другой
    `checks.proposed`;
  - `checks.decided`: `proposalTurnId` — ход единственной `checks.proposed`, решения ещё нет;
    `by: "autopilot"` ⇔ `commandId: null` ⇔ `decision: "accept"`; при `commandId` — открытая команда;
    `by: "autopilot"` — только если у `checks.proposed` `sandboxNetwork: "denied"` (§7 п. 5);
  - при `sandboxNetwork: "denied"` у каждого `check.started` запуска `profileSha256` ≠ `NO_SANDBOX_SHA256`
    (`userCheck.ts`): «сеть запрещена» нельзя записать для проверок, которые шли в login-shell без песочницы;
  - между `checks.proposed` и `checks.decided` нет ни одного `orch.turn` (допустимы только записи команды и
    `run.status`);
  - `plan.recorded` хода предложения — только после `checks.decided(accept)` и без другого `orch.turn` между ними;
- второй этап, по текстам, нарушение → `integrity: "corrupt"`, `detail.phase: "texts"`:
  - `checks.proposed` — только при `commands: []` в цели; `count` = числу строк; `id` — `cmd-1…cmd-n` по порядку;
  - при `commands: []` до `checks.decided` нет `plan.recorded`, хода исполнителя или проверяющего и `check.*` (в том
    числе в журнале без `checks.proposed`);
  - автопилотное решение — только при `goal.mode` = `autopilot` или без `mode`; решение по команде — при любом режиме;
  - `accept`: `checks` совпадает с предложением (`id`, `command`, `origin: "lead"`);
  - текст `proposal` — строки отчёта плана в том же порядке с добавленным `id` (в самом отчёте `id` нет: лишний ключ
    → `invalid_report`);
  - `edit`: строки по правилу п. 3 выше; `id` — `cmd-1…cmd-n` по порядку нового списка; `origin: "lead"` — у
    строки, текст которой совпадает с какой-либо строкой предложения, иначе `person`.

**Пауза `awaiting_checks_decision`.** Допустимы только команда `checks.decide` («Принять», «Изменить») и Stop.
Resume, step, `clarification.added`, `limits.changed` → `rejected(invalid_state)`, как на `coverage_lost` (5h §3.6
п. 2). Подготовка идёт до первого хода (`cycle.ts`), вопроса на этой паузе быть не может. Набор команд меняется только
этим решением, один раз; цель с командами задаёт набор сразу, и `checks.*` в её журнале нет.

**Пауза `awaiting_finish_confirmation`.** Допустимы только команда `finish.confirm` и Stop. Остальное, в том числе
resume и step, → `rejected(invalid_state)`.

### 2.3. Требования, условия, замечания, завершение: что выводится, а не пишется

Отдельной записи нет у:
- **требований** — `R<n>` по номеру в `goal.criteria` текста цели из `run.created` (5h §1). Цепочка хешей фиксирует
  текст. Снять требование может только `plan.decided(accept)` с `dropRequirements`;
- **условий и доказательств** — `C<n>` из текстов планов (`plan.recorded`, `plan.decided(accept)`). Доказательство:
  - `check` — `check.finished` + `check.assessed` на текущем `checkKey`;
  - `change` — `review.assessed.applied.conditionsMet`;
  - `person` — `person.decided`;
  - снятие условия — `plan.decided(accept)`;
- **замечаний и их истории** — `F<n>` из `applied` и решений. История `F` — упорядоченный по `seq` список событий:
  - `opened`, `closed`, `reopened`, `refused`, `unchanged`, `disputed` — из `review.assessed`;
  - `closed_by_person`, `to_wish` — из `person.decided`;
  - `moved`, `closed_by_person`, `to_wish` — из `plan.decided`.

  У каждого события есть `runKey` и ход. Уровень меняется только событием `to_wish`.

**Функция завершения.** Чистая функция журнала, текстов и текущего снимка (`checkKey`, `runKey`, дерево):

```
completion(state, texts, snapshot) → { allowed: true, kind } | { allowed: false, blockers }

blockers (все, в этом порядке; пусто ⇔ allowed):
  checks_undecided                      checks.proposed без checks.decided
  plan_proposal_pending                 plan.proposed без plan.decided
  disputed_pending(index)               спорный пункт без person.decided (5h §3.4)
  stage_not_accepted(s)                 этап действующего плана не принят (5h §3.3)
  condition_unmet(C)                    действующее условие без действующего доказательства (5h §3.3, §3.7)
  check_not_passed(cmd)                 команда действующего набора не passed на текущем checkKey
  requirement_unmet(R)                  R не снято и (не покрыто выполненными условиями
                                        или нет met в свежем финальном отчёте) (5h §3.8)
  blocking_open(F)                      открытое blocking
  final_report_stale                    нет финального review.assessed на текущих runKey и
                                        clarificationVersion, или request ≠ "none"
  finish_pending(step)                  шаг, запрошенный целью, не done для текущего дерева/commit
                                        и не отклонён finish.confirmed(decline)
  finish_awaiting_person(step)          push/qa запуска без проверок без finish.confirmed для
                                        текущего дерева и commit

kind = действующий набор команд пуст ? "no_checks" : "confirmed"
```

Правило «завершение разрешено, только если…»: `run.status(completed)` пишется, только когда `completion(...)`
вернула `allowed: true`. В запись идут `kind` и `basis` — текст с входами решения:
- действующие команды и `checkRunId` их последних `passed`;
- `R → C → доказательство`;
- финальный ход проверяющего, `runKey`, `checkKeys` (по команде);
- исход шагов commit/push/QA.

**Проверки `completed` и `finish.intent` при воспроизведении**, так что «Завершено» нельзя записать мимо функции:
- первый этап (по записям), нарушение → `replay_conflict`:
  - нет `checks.proposed` без `checks.decided` и `plan.proposed` без `plan.decided`;
  - все этапы действующего плана приняты (`stage.accepted`);
  - есть финальный `review.assessed` (`stage: null`) с `request: "none"`, и после него нет `orch.turn`; в журнале
    `formatPreview` (ревью лидом, A1–A2) вместо него — `review.recorded(stage: null, verdict: "complete")` последнего
    финала, а проверки по `applied` второго этапа не действуют;
  - нет шага finish в состоянии `in_flight`/`outcome_unknown`/`unknown`;
  - `finish.intent(push|qa)`: в запуске без проверок (`checks.decided.count = 0`) ему предшествует `finish.confirmed`
    с `confirm` для этого шага, и после этой записи нет нового `finish.result(commit)`;
- второй этап (по текстам и `applied`), нарушение → `corrupt`, `detail.phase: "texts"`:
  - `kind` = `no_checks` ⇔ набор команд пуст;
  - для `confirmed` у каждой команды набора `basis` называет `checkRunId` с `passed`, `check.assessed` на
    `basis.runKey` и `checkKeys`;
  - нет открытого `blocking` и неразрешённого спорного пункта по `applied` и решениям;
  - каждое `R` снято `plan.decided(accept)` или имеет `met` в `requirements` финального отчёта;
  - `finish.intent(push|qa)` без проверок: `tree` и `commit` в `params` равны `tree`/`commit` подтверждения;
  - каждый шаг, запрошенный целью, — `done` для `basis`-дерева или `decline` в подтверждении.

**«Завершено без проверок» не выглядит подтверждённым:**
- `kind: "no_checks"` показывается своей строкой «Завершено без проверок». Значок и цвет не те, что у «Завершено»:
  это одна функция `runStatus.ts` для панели, карточек, виджета активности и истории пространства;
- итог открывается строкой «Команды проверки не запускались»;
- диалог подтверждения push и QA повторяет, что проверок не было; если QA подтверждён, а push отклонён, диалог
  предупреждает, что QA проверит неотправленный commit, и решение записывается как есть (§7 п. 3);
- критерий A1-4 перечисляет каждое место показа статуса.

### 2.4. Порядок первого хода плана при пустых командах

```
orch.turn(plan) → turn.intent(lead) → turn.finished(report: план + предложение команд)
  → [отчёт невалиден] invalid_report, записей нет → новый ход плана
  → checks.proposed
      автопилот и sandboxNetwork = denied:
                  checks.decided(accept, by autopilot) → plan.recorded(тот же turnId) → этап 1
      иначе (пошагово, или автопилот при sandboxNetwork = open):
                  run.status(paused, awaiting_checks_decision)
                    «Принять»:   command.received → checks.decided(accept, person) → command.completed
                                 → run.status(running) → plan.recorded(тот же turnId)
                                 → (reviewPlan) run.status(paused, plan_review) | этап 1
                    «Изменить»:  command.received → checks.decided(edit, person) → command.completed
                                 → run.status(running) → orch.turn(plan) нового хода → plan.recorded
                    Stop:        как сейчас
```

`run.status(running)` после решения пишет сам обработчик команды: resume и step на этой паузе отклоняются (§2.1), а
цикл на паузе ничего не делает. То же для `finish.confirmed`.

`plan.recorded` после `checks.decided(accept)` — единственный случай, когда запись плана идёт не сразу за
`turn.finished`. Разрешено, только если между ними нет другого `orch.turn`.

Новый ход плана после «Изменить»:
- **не** расходует `replans`: действующей версии плана ещё нет;
- обязан содержать `checks: null`: предложить команды можно только один раз.

### 2.5. Восстановление (дополнение к таблице 5h §3.10)

| Что в журнале | Действие при открытии / решении цикла |
|---|---|

| `checks.decided(accept)`, нет `plan.recorded` этого хода | при решении цикла main пишет `plan.recorded` по отчёту хода (тот же результат проверки: входы не менялись) |

### 2.6. Команды лида в песочнице проверок (A1.1, решения владельца §7а)

**Источник команды.** Уже в формате A1: текст `checks.decided.checks` даёт каждой строке `origin: "lead" | "person"`
(§2.1). Отдельного поля не нужно. Команды цели (`commands` не пустой) — команды человека.

**Где выполняется.** Строка с `origin: "lead"` запуска, у которого `checks.proposed.sandboxNetwork: "denied"`,
выполняется в профиле проверок лида, пока человек не заменил её своей строкой (`checks.amended`). Остальные — команды человека и
команды цели — как в A1: login-shell пользователя без песочницы (`NO_SANDBOX_SHA256`). main пишет
`sandboxNetwork: "denied"`, когда этот профиль есть (macOS, `sandbox-exec`); иначе `"open"`, и решает человек, как в A1.

**Профиль** (`sandbox.ts` `buildCheckProfile`; параметры — рабочая папка запуска и временный каталог проверки):
- запись: только рабочая папка запуска (копия, worktree или папка проекта — по режиму) и свой временный каталог
  (`TMPDIR`, создаётся на каждый запуск проверки и удаляется после); `/dev/null`. Кроме `<рабочая папка>/.git`:
  хук или `core.fsmonitor`, записанный туда, потом выполнил бы git самого человека — вне песочницы (ревью S1-1).
  gitdir вне рабочей папки (у worktree) не пишется вовсе. Рабочая папка, которая накрывает домашний каталог или
  хранилище секретов, — профиль не строится (`sandbox_unavailable`);
- чтение: как в профиле runner (`buildProfile`) — по умолчанию разрешено, deny-список секретов (`.ssh`, `.aws`,
  `.codex`, `.claude`, `.config/gh`, `.config/git`, `.docker`, `.kube`, `.gnupg`, `Library/Keychains`, `.claude.json`,
  `.npmrc`, `.gitconfig`, `.netrc`), в этом профиле ещё ключи локальных машин (`.orbstack`, `.colima`, `.lima`,
  `.vagrant.d`), и данные оркестрации (`<userData>/orchestration`, кроме рабочей папки копии);
- сеть: только эта машина — `localhost:*` (bind, входящие, исходящие; 127.0.0.1 и ::1), Unix-сокеты в рабочей
  папке и во временном каталоге. Наружу и DNS — нет. Факт Seatbelt: `localhost` охватывает все адреса этой машины,
  в том числе её LAN-адрес (это та же машина); другой хост той же сети — EPERM;
- запуск: `sandbox-exec -f <профиль> -- <supervisor> <shell> -c <строка>`, окружение — измеренное окружение
  login-shell (stage 13) плюс `TMPDIR`. Supervisor внутри песочницы, как у проверок проекта: после выхода команды его
  проход (`SUP_SANDBOX_SWEEP`) находит и убивает всё, что осталось в этом экземпляре песочницы, отсоединённые
  процессы тоже, до снимка дерева (ревью S1-3); пусто не подтверждено → `cleanup_unverified`. Не `-ilc`: стартовые файлы оболочки уже учтены в окружении, а их записи в
  `$HOME` профиль всё равно отклонит. Другой argv — другой `commandSha256` и другой ключ проверки: результат в
  песочнице не засчитывается за ту же строку без неё;
- `check.started.profileSha256` — sha256 текста профиля (≠ `NO_SANDBOX_SHA256`).

**Самотест** перед каждой проверкой в профиле (`checkSelftest`): тем же профилем, собственным Node приложения.
Запись в рабочую папку и временный каталог — да; запись в `$HOME` вне рабочей папки — EPERM; чтение
`~/Library/Keychains` — EPERM; чтение данных оркестрации — EPERM; запись в `<рабочая папка>/.git` — EPERM; TCP на
127.0.0.1 — да; TCP на внешний адрес (1.1.1.1:443) — EPERM. Отказ должен быть
именно EPERM (отказ песочницы), а не ENOENT или закрытый порт. Не прошёл — проверка не запускается, `check.started`
не пишется, пауза `sandbox_unavailable` с причиной.

**Отказ песочницы.** Проверка в профиле, упавшая с признаками отказа в выводе (EPERM, «Operation not permitted»,
ошибка разрешения имени: ENOTFOUND, `getaddrinfo`, «Could not resolve host», `php_network_getaddresses` и т. п.,
`prepare.ts` `sandboxRefused`), классифицируется `check.classified(class: "sandbox")` — не ошибка кода, исполнителю
не уходит. Класс `"sandbox"` — только v2 и только у проверки в профиле. Признак — текст вывода, не факт от ядра:
команда сама может напечатать «EPERM» и получить эту паузу (ревью S1-4). Ядро отказ не подтверждает: Seatbelt на
macOS 27 не пишет такие отказы в системный журнал надёжно. Поэтому пауза говорит «по выводу команды», и команду лида
без песочницы запустить нельзя: только сделать её своей (решение владельца по S1-4, §7а). Цикл встаёт на паузу
**`check_needs_permissions`** («Проверке нужно больше прав»), в автопилоте тоже; пауза сама не снимается.

**Пауза `check_needs_permissions`.** Допустимы только команда `check.amend` и Stop; resume, step, уточнения →
`rejected(invalid_state)`. Действие одно (только человек): «Изменить команду» — `check.amend {checkId, line}`.
Редактор открывается с полным текстом команды, без сокращения, и с подписью «Команду предложил лид. После сохранения
она будет выполняться как ваша — без песочницы». Сохранённая строка — команда человека (в терминах формата `origin`
`"person"`), идёт в его login-shell без песочницы. Сохранение без изменений допустимо — это явное решение человека.
`check.amend` без `line` (бывшее «Запустить без песочницы», редакция A1.1 до S1-4) — нет такой команды:
IPC и main отклоняют её (`invalid_command`).

| Запись | Поля | Кто пишет | Правила |
|---|---|---|---|
| `checks.amended` | `commandId` uuid; `checkId` `cmd-n` решённого набора; `line` TextRef строки (канонический JSON строки) | пользователь (команда `check.amend`) | `checkId` — проверка, которую песочница отклонила последней и ещё не выпущенная; одна поправка на проверку. Порядок: `command.received` → `checks.amended` → `command.completed` → `run.status(running)`. Действует на эту проверку в этом запуске: дальше вместо строки лида идёт строка `line` — команда человека, без песочницы. (До S1-4 `line` мог быть null — «та же строка без песочницы»; убрано, формат v2 ещё за признаком) |

**Воспроизведение** (дополнение к §2.1):
- первый этап: `checks.amended` — при открытой команде `check.amend`, `checkId` из решённого набора, последний
  законченный прогон этой проверки классифицирован `"sandbox"`, поправки этой проверки ещё нет;
  `check.classified("sandbox")` у проверки без песочницы → `replay_conflict`. Правило A1 «`"denied"` и
  `NO_SANDBOX_SHA256` → `replay_conflict`» уточнено: для принятого предложения (все строки от лида) — если проверка не
  выпущена `checks.amended`;
- второй этап (тексты): при `"denied"` строка `origin: "lead"` без поправки не выполняется без песочницы.

**Где профиль, решает журнал, а не открытие.** Строка лида запуска с `"denied"` идёт в профиле при любом открытии;
нет Seatbelt — самотест не проходит, `sandbox_unavailable`, ничего не запущено (ревью S1-2).

**Принятый остаток: localhost и сервисы машины** (ревью S1-5; решение владельца по PR #16, 2026-10-02: Q2 не
сужать). «Эта машина» в Seatbelt — все её адреса: проверка лида может слушать на 0.0.0.0 (литерал 127.0.0.1
профилем не выразить) и ходить на собственный LAN-адрес; сервисы, слушающие localhost (SSH-туннель, локальные VM и
контейнеры, прокси), ей доступны — и путь наружу, если такой сервис его даёт. Это принято: агенты в режиме «Как в
моём терминале» имеют те же и более широкие возможности, и песочница проверок не строже прав агентов. Права агентов
в автопилоте по умолчанию — открытый пункт до A4 (ROADMAP).

**Автопринятие** (уточнение §7 п. 5): автопилот принимает сам, если все принятые команды — от лида и выполняются в
профиле, то есть при `"denied"` (правило о сети выполнено по построению профиля); при нуле предложенных команд — всегда
(§7а Q1). Смешанный набор возникает только из «Изменить» — это решение человека.

### 2.7. Требования и условия в A2 (уточнено при реализации A2)

План A2 (§5): 5h §2.3, §3.3 п. 1–2, блокеры `condition_unmet` и `requirement_unmet`. Ревью в A2 по-прежнему делает лид
(журналы `formatPreview`, `review.recorded`); чего 5h для этого не задаёт, уточнено здесь. Ничто ниже не меняет
утверждённых решений: снятия и решения человека остаются за A4.

**Требования.** `R<n>` — номер в `goal.criteria` (5h §1): их задаёт человек, лид их не формулирует и не меняет.
`dropRequirements` в A2 только пустой; непустой — `invalid_report` (снятие — решением человека, A4).

**Отчёт плана лида** (схема ответа хода). Подмножество JSON Schema валидатора (`schema.ts`) не знает `anyOf`, поэтому
пункт `conditions` — плоский объект, все ключи обязательны:

```json
{"keep": "C3" | null, "text": "…" | null, "covers": ["R1"] | null,
 "evidence": {"kind": "check" | "change", "check": "cmd-1" | null} | null}
```

Ровно одно из двух: `keep` (остальное `null`) или новое условие (`keep: null`, `text` 1–500, `covers`, `evidence`).
`evidence.check` — `cmd-<n>` действующего набора (у хода предложения — предложения) ровно при `kind: "check"`.
`kind: "person"` в A2 нет (решение человека — A4): в схеме его нет. `dropped` в A2 только пустой; непустой —
`invalid_report`. Остальное — 5h §2.3: 1–12 условий на этап, `keep` только непринятых условий без повторов, каждое
непринятое условие прежнего плана — в `keep`, покрытие каждого `R`. Нарушение — `invalid_report` с перечнем, план не
пишется; следующий ход плана получает перечень, пересчитанный из отчёта отклонённого хода.

**Текст плана** (`plan.recorded.plan`) — в форме фикстур §4: `{stages: [{title, task, conditions}], dropped: [],
dropRequirements: [], question: null}`; новое условие — `{id, text, covers, evidence: {kind, check?}}` с номером от
приложения, перенесённое — `{keep}`. `plan.recorded.conditionsAssigned` — число новых условий.
План хода предложения пишется только после «Принять» (набор = предложение); после «Изменить» он отбрасывается
(§2.4), и условия `check` следующего плана ссылаются на изменённый набор.

**Ответ ревью лида** (журналы `formatPreview`):
- ревью этапа: `{verdict, findings, question, conditions: [{id, status: "met"|"not_met", paths, note}]}` — ровно по
  одному пункту на каждое условие `change` этого этапа. `met` — с непустым `paths`, и хотя бы один путь входит
  в `diffTreeNames(baseline → снимок ревью)` (ограничитель 5h §3.3, не доказательство); иначе `invalid_report`.
  Шлюз этапа A (2026-10-03): схема, которую получает CLI, перечисляет в `conditions[].id` только эти условия (нет
  ни одного — `maxItems: 0`, без пустого `enum`); отчёт проверяется общей схемой цели хода. Лишнее, не меняющее
  смысла, не причина отказа: отметка условия `check` или `person` (его засчитывает только команда или человек),
  отметка снятого человеком `R`, отметка финальным ревью условия, которое не нужно подтверждать, путь `met` или
  закрытия замечания, не менявшийся рядом с изменёнными. Лишнее отбрасывается до проверки,
  никогда не засчитывается и называется в ленте (`report_note`);
- финальное ревью: `{verdict, findings, question, requirements: [{id, status: "met"|"not_met", note}]}` — ровно по
  одному пункту на каждое `R`.

**Доказательства** (выводятся, записей нет):
- `check` — команда `passed` на текущем `checkKey`; правка дерева делает доказательство устаревшим, новый прогон
  возвращает его;
- `change` — `met` в ответе ревью, по которому этап принят (`stage.accepted.reviewTurnId`). Свежесть между этапами —
  5h §3.7, A4.

**Цикл.** Этап принимается (5h §3.3 п. 1–2), только если вердикт `accept`, все команды прошли на текущем `checkKey` и
каждое условие этапа выполнено; иначе он возвращается исполнителю с невыполненными условиями. Финал `complete`
завершает запуск, только если функция завершения не видит блокеров; `requirement_unmet` или `condition_unmet` — ход
плана с перечнем причин (5h §3.8, в пределах `replans`). Возврат условий принятых этапов в непринятые — A4.

**Функция завершения** получает факты условий: `condition_unmet(C)` — действующее условие без доказательства;
`requirement_unmet(R)` — `R` не покрыто выполненным условием или в последнем финальном ответе лида не `met`. `basis`
несёт `requirements: [{id, conditions, met}]`, как в фикстурах.

**Воспроизведение:**
- первый этап: `plan.recorded.conditionsAssigned` в v2 необязателен — его нет только у планов формы A1. После плана с
  этим полем план без него — `replay_conflict`;
- второй этап (тексты), нарушение → `phase: "texts"`:
  - план с `conditionsAssigned`: номера новых условий идут подряд от следующего свободного, их число равно
    `conditionsAssigned`; `keep`, покрытие и ссылки `check` — по правилам выше; план без поля — без условий;
  - `stage.accepted` этапа с условиями `change`: ответ принявшего ревью отмечает каждое `met` с путями;
  - `completed` запуска с условиями: каждое `R` покрыто выполненным условием и `met` в последнем финальном ответе.
    «Завершено» без доказательств — ошибка целостности.
    Запуск проверки условия `check` сверяется с `basis` по `checkKey` (не по `runKey`: дерево, виденное раньше, или
    поправка другой команды его не перезапускают). Воспроизведение сверяет `basis` с журналом, не с деревом: дерева
    запуска проверки и финального ревью журнал не хранит (ревью A2, круг 2).

**Журналы формы A1** (`formatPreview`, план без условий): читаются и продолжаются. Пока действует такой план, блокеры
условий не действуют — их нет в данных (§2.2). Следующий план пишется в форме A2, и с него действуют все правила
выше.

**Показ.** В итоге запуска — раздел «Условия»: требования, их условия, статус каждого («выполнено» / «не выполнено» /
«не проверялось»), доказательство (прогон команды или ответ ревью) и строка «N из M условий выполнено». Та же функция
модели renderer — для карточек и ленты.

### 2.8. Замечания и проверяющий в A3 (уточнено при реализации A3)

План A3 (§5): 5h A2 + A3 — роль `reviewer`, новая сессия на ревью, пакет 5h §3.2, `review.assessed` /
`review.discarded`, замечания с id и историей, 5h §3.1.1, §3.4, §3.10, прогресс по id. Чего 5h не задаёт, уточнено
здесь; решения человека (`person.decided`, `plan.proposed`/`plan.decided`), свежесть 5h §3.7 и возврат условий 5h §3.8
остаются за A4.

**Кто проверяет.** Роль `reviewer` (5h §3.1): провайдер лида (Codex), **новая сессия на каждое ревью**
(`turn.intent.sessionId: null`), лимит хода `leadTurnMs`, права и настройки CLI — те же, что у лида (`goal.access`),
диалог разрешений называет провайдера проверяющего. Лид только планирует. Карточки на холсте у проверяющего нет —
это сессия CLI лида: карточка Codex показывает его работу, панель запуска — отдельного участника «Проверяющий», лента —
его события с ролью `reviewer`.

**Какие запуски.** Журнал v2 без `review.recorded` ревьюирует проверяющий (`review.assessed`). Журнал v2 с
`review.recorded` (запуски A1–A2, ревью лидом) доводится лидом по правилам A2 до конца. Смешение в одном журнале —
`replay_conflict`: `review.recorded` после хода `reviewer` или `review.assessed`, и наоборот.

**`orch.turn.tree`** пишется в каждом `orch.turn` журнала A3: oid дерева до хода у проверяющего, `null` у остальных
(как в фикстурах §4). В журналах A1–A2 ключа нет. Ход `reviewer` без `tree` — `replay_conflict`.

**Отчёт проверяющего** (схема ответа хода). Валидатор не знает `anyOf`, поэтому `relation` — плоский объект, все ключи
обязательны:

```json
{"conditions": [{"id", "status", "paths", "note"}],
 "requirements": [{"id", "status", "note"}],          // только в финальном ревью
 "findings": [{"id": "F3" | null, "severity": "blocking" | "wish", "condition": "C2" | null,
               "problem": "1–2000", "evidence": "0–2000", "closeWhen": "1–1000", "status": "open" | "closed",
               "paths": ["…"], "relation": null | {"repeatOf": "F1" | null, "distinctFrom": "F1" | null, "why": "…" | null}}],
 "request": "none" | "replan" | "question", "question": null | "…"}
```

`conditions` ревью этапа — по правилу §2.7 (ровно одна отметка на каждое условие `change` этапа); в финальном ревью —
пустой (подтверждение условий принятых этапов — 5h §3.7, A4). `requirements` финала — ровно по одному на каждое `R`.

**`invalid_report`** (отчёт не применяется, `review.assessed` нет): ссылка на несуществующий `F` (в том числе своя
«нумерация» нового замечания); один `F` дважды в отчёте; смена `severity` или `condition` существующего `F`; новое
`blocking` без `paths`; закрытие `blocking` на `runKey` его открытия, с пустым `paths` или без единого пути из
`diffTreeNames(дерево открытия → дерево ревью)` (лишний неизменённый путь рядом с изменёнными — §2.7); `relation` с обоими `repeatOf` и `distinctFrom` или `distinctFrom` без
`why`; нарушение §2.7. Следующий ход проверяющего получает перечень нарушений, пересчитанный из отклонённого отчёта.

**Применение** — 5h §3.4 и §3.10 без изменений: группы `opened` / `closed` / `reopened` / `refused` / `disputed` /
`unchanged`, номера `F` подряд от `nextFinding`, возможный повтор и `relation`, привязка к этапу. Уточнения:
- `wish` проверяющий закрывает без ограничения на пути (правило путей 5h §3.4 — для `blocking`); повторное открытие —
  по общему правилу;
- `F`, названный по id со статусом, который у него уже есть, — `unchanged` (и открытый, и закрытый);
- «дерево открытия» замечания — `orch.turn.tree` ревью, которое его открыло (или открыло повторно); «дерево
  закрытия» — ревью, которое его закрыло;
- с несколькими кандидатами `distinctFrom` указывает одного; `possibleRepeatOf` нового `F` — он.
- кандидат с исчерпанным `distinctFrom` — спорный пункт при любом `relation` (и `repeatOf` тоже);
- один `F` назван в отчёте один раз: по id или как `repeatOf` одного нового пункта; иначе `invalid_report`;
- новое замечание ревью этапа с условием другого этапа привязывается к этапу без условия; дальше его называют с
  `condition: null` (пакет ревью показывает привязку);
- владелец открытого `blocking`, чьё условие у принятого этапа, — по правилу непривязанного (этап, где открыт или
  открыт снова, иначе первый непринятый этап следующего плана): открытое блокирующее всегда доходит до исполнителя.

**Спорный пункт в A3.** `applied.disputed` записывается, запуск встаёт на `awaiting_person_decision`. Решение человека
(`person.decided`) — A4: до него на этой паузе допустим только Stop; этап не принимается, запуск не завершается.

**Приёмка этапа и цикл** (5h §3.3). Вердикта у проверяющего нет. Свежий `review.assessed` этапа (тот же `runKey` и
`clarificationVersion`) с `request: "none"` принимает этап, только если все проверки `passed` на текущем `checkKey`,
каждое условие `change` этапа отмечено `met` (`applied.conditionsMet`), нет открытого `blocking` с этим этапом-владельцем
и нет спорного пункта. Иначе этап возвращается исполнителю: его задание несёт невыполненные условия и открытые
`blocking` **своего этапа**, пожеланий в нём нет. `request: "replan"` → ход плана; `"question"` → вопрос человеку,
после ответа — новое ревью.

**Функция завершения** получает ещё два блокера: `blocking_open` (любое открытое `blocking`) и `disputed_pending`.
Финал `request: "none"` с любым блокером — ход плана (как в A2, в пределах `replans`).

**Дерево во время ревью** — 5h §3.1, §3.1.1 целиком: `review.discarded`, один автоматический повтор, пауза
`tree_changed_during_review` (resume/step из неё и `recovery.decided` хода проверяющего — разрешение на один ход).
Проверка дерева идёт до `pauseForOutcome` и `invalid_report`.
Считаются только отброшенные подряд: ход проверяющего с тем же ключом, который не отброшен, начинает счёт заново.
На паузе `awaiting_person_decision` уточнение не принимается (только Stop).

**Прогресс** (5h §3.3): ключ раунда — множество id открытых `blocking` этапа и невыполненных условий этапа после ревью.

**Воспроизведение:**
- первый этап: `turn.intent(role: "reviewer")` — только в v2; `review.assessed` — завершённый ход проверяющего нужной
  цели, последний `orch.turn`, одна запись результата на ход, `report` = `turn.finished.report.ref`;
  `review.discarded` — ход проверяющего с `turn.finished`, последний `orch.turn`, `treeBefore` = `orch.turn.tree`,
  `treeAfter` ≠ `treeBefore`; `stage.accepted` — по `review.assessed` этого этапа с `request: "none"`;
  `completed` — после последнего финального `review.assessed` с `request: "none"`;
- второй этап (тексты), нарушение → `phase: "texts"`: `applied.report` = отчёту; каждый `index` отчёта учтён ровно
  один раз; номера `opened` подряд от `nextFinding`, `nextFinding` записан верно; `closed`, `reopened`, `unchanged`,
  `refused` и кандидаты `disputed` ссылаются на существующие `F` в нужном состоянии; `opened` совпадает с пунктом
  отчёта (`severity`, `paths`); `conditionsMet` = условия, отмеченные `met`; `stage.accepted` — без открытого
  `blocking` этапа и без спорного пункта на момент приёмки; `completed` — без открытого `blocking` и без спорного
  пункта; `request` записи = `request` отчёта; `opened[].stage` = этап ревью; названный `F` не меняет уровень и
условие; закрытие `blocking` — с путями и не на `runKey` открытия (принадлежность путей diff — правило живого
применения, при воспроизведении деревьев нет). «Завершено» с открытым блокирующим — ошибка целостности.

**Оборванный хвост** журнала v2 (5h §3.10: `quarantine/`, `journal.tail_repaired`) и восстановление команд (15h) — A4;
в A3 хвост принимается как прежде (решением человека).

**Показ.** В итоге — раздел «Замечания»: номер, уровень, статус, владелец-этап, пути, история (кто и на каком ревью
открыл, закрыл, отклонил повтор; `runKey` и дерево), пожелания отдельно, пометка «возможный повтор `F1`»; строка
«Открыто блокирующих: N» — одной функцией модели renderer для итога, карточек и ленты.

### 2.9. Решения человека и финал в A4 (уточнено при реализации A4)

План A4 (§5): `person.decided`, `plan.proposed`/`plan.decided`, 5h §3.5–§3.8, интерфейс §4, восстановление 5h §3.10 и
15h. Чего 5h не задаёт, уточнено здесь.

**Включение (уточнено при реализации A4).** Решение «новые запуски пишутся в v2 по умолчанию» (§3.4, §7 п. 1) — одна
константа `JOURNAL_V2_BY_DEFAULT` в `journal.ts`. В PR A4 она `false`, тест закрепляет это. Запись v2 по-прежнему
включает только `CANVASTTY_JOURNAL_V2=1` (`journalV2: JOURNAL_V2_BY_DEFAULT || признак`). От той же константы зависит
показ журналов `formatPreview`: пока она `false`, журналы A1–A3 открываются и продолжаются под признаком, как до A4;
когда станет `true` — только просмотр с подписью «создан пробной сборкой этапа A» (`newer_version`, `detail.preview`).
Проба S-A3 на 1.5.7 и ≤ 1.5.6 — шаг включения, не этого PR.

**Окончательная форма v2.** Первая запись нового запуска — `minReaderVersion: 2` без `formatPreview`. Эту форму сборка
воспроизводит сама: `review.recorded` в ней — `invalid_event`, `orch.turn` без ключа `tree` — `invalid_event`.
Фикстуры §4 — эта форма: они воспроизводятся целиком, тексты тоже (`build.mjs --check`, столбец «эта сборка»).

**Записи** (данные, все ключи обязательны):

```
plan.proposed  {turnId, plan: TextRef, firstStage, stageCount, conditionsAssigned}
plan.decided   {commandId, proposalTurnId, decision: accept|return, version: int (accept) | null (return),
                choices: TextRef, note: null (accept) | TextRef|null (return), runKey, tree}
person.decided {commandId, subject: condition|finding|disputed,
                target: C<n> | F<n> | {reviewTurnId, index},
                decision: met|not_met (condition) | close|to_wish (finding) | new|repeat (disputed),
                finding: null | F<n> (только repeat), reopened: null | boolean (только repeat), runKey, tree}
```

`runKey` и `tree` — состояние, о котором решал человек (что он видел). `reopened` у `repeat` — итог правила повторного
открытия на этом дереве. Решения лежат только в записях с `commandId`. Автопилот и агенты их не пишут.

**Команды.** `person.decide {subject, target, decision, finding, runKey}` и `plan.decide {proposalTurnId, decision,
choices, note, runKey}` — ровно эти ключи (IPC). Любой другой, например `by` или роль, — отказ разбора. `runKey`
команды — состояние, которое показала панель (`view.decisions.runKey`). Другое → `rejected(stale_revision)`, вид
обновляется, человек решает заново. Что человек видел, задаёт панель, а не payload: `tree` и `reopened` main
вычисляет сам.

**Где принимаются решения.**
- **Спорный пункт и условие `person`** — пауза `awaiting_person_decision`. Resume, step и уточнение на ней →
  `rejected(invalid_state)`.
- **Закрыть или понизить замечание** — на паузах, где запуск стоит не по своей воле: `RESUMABLE`, `STEP_ONLY`,
  `limit_reached`, `awaiting_answer`, `awaiting_person_decision`. Сюда не входят паузы ожидания других решений и
  `outcome_unknown`.
- **Решение о предложении плана** — пауза `coverage_lost`. Там допустимы только `plan.decide` и Stop.

Ожидающее предложение — первое, что видит цикл, даже после дедлайна запуска: иначе его некому было бы решить. Пока
оно ждёт, уточнение и поднятие лимита → `rejected(invalid_state)`.

После решения на `awaiting_person_decision` и `coverage_lost` main пишет `command.completed`, затем
`run.status(running)`: запуск продолжается сам, как после `checks.decided` (§2.4). На остальных паузах решение запуск
не продолжает: он стоит, и действия паузы остаются прежними.

**Спорный пункт (5h §3.4).** Панель показывает рядом пункт ревью (проблему, доказательство, пути) и каждого
закрытого кандидата.
- «Новый дефект» → `F<n>` открыт, `possibleRepeatOf` — кандидаты через «, ». В истории: `opened` с `by: person`, у
  кандидатов — `decided`.
- «Повтор `F<k>`» (только кандидат) → правило повторного открытия по id. Пути `F<k>` менялись после его закрытия
  (diff дерева закрытия → дерево ревью): `reopened`. Не менялись: `refused` (`declared_repeat`). Событие несёт
  `by: person`.

Пункт решается один раз. Повторное решение → `rejected(invalid_state)`. После решения финал оценивается заново
(5h §3.8). Отклонённый повтор ничего не блокирует: если финал свежий и прочие условия выполнены, запуск завершается
без нового плана.

**Замечание.** `close` — любое открытое замечание. `to_wish` — только `blocking`: уровень становится `wish`,
замечание открыто, помечено `downgraded`. История — `closed_by_person` / `to_wish` с `by: person`. Понижение не
выглядит исправлением: в итоге «понижено человеком, не исправлено».

**Условие `person`** (вид доказательства `person` в схеме плана). Отметки проверяющего его не меняют.
- После свежего ревью этапа, пока решения нет → пауза `awaiting_person_decision` («stage N condition»).
- `met` — доказательство. `not_met` — этап возвращается исполнителю.
- Действует последнее решение после последнего хода исполнителя этапа.
- `stage.accepted` требует `met`.

**Предложение плана (5h §3.6).**
- Отчёт плана с непустыми `dropped` или `dropRequirements` пишется как `plan.proposed`, а не как план. Номера новых
  условий резервируются: `conditionsAssigned`, счётчик запуска `nextCondition`. Действующий план не меняется. Пауза
  `coverage_lost`.
- План, предлагающий команды проверки (§2.1), снимать не может: это `invalid_report`.
- Каждое снятие — с непустым `why`.
- Панель показывает:
  - что снимается и почему;
  - что останется без покрытия: требования, которые снимаемые условия покрывали и не покроет ничто действующее,
    в том числе снимаемые вместе с предложением;
  - новые этапы;
  - выбор для каждого открытого `blocking`, привязанного к снимаемому условию: перенести на этап нового плана,
    закрыть, понизить.
- «Принять» доступно, когда выбор сделан для каждого такого замечания; `choices` — ровно эти замечания.
  - `accept` → действует версия `version` с текстом предложения (`proposed: true`, номера от его `base`).
  - `choices` применяются: `moved` / `closed_by_person` / `to_wish` с `by: person`.
  - Пожелания снятого условия теряют привязку.
- `return` → действующий план остаётся. Ходы плана получают пояснение человека (`note`), пока не записан новый
  план: отклонённый приложением ход плана его не «расходует».

Перед записью `accept` main ещё раз проверяет предложение против планов (5h §2.3). Нарушение →
`rejected(invalid_state)`.

**Финальный отчёт и снятые требования.** Отметка ставится для каждого требования в силе. Снятое `R` не отмечается:
схема хода его не предлагает, а лишняя отметка не засчитывается (шлюз этапа A, §2.7). Снятое `R` никогда не считается выполненным: статус `dropped`, в основании
`{met: false, dropped: true}`.

**Свежесть `change` (5h §3.7).**
- Доказательство условия `change` принятого этапа несвежее, если путь, названный в его отметке, изменился с
  checkpoint этого этапа.
- Несвежее не считается. В показе — «файлы менялись после приёмки этапа».
- Засчитывается, только если финальное ревью его подтвердило. `conditions` финального отчёта — ровно несвежие
  условия, отметка `met` с путями из diff базы → финальное дерево. Иначе `invalid_report`.
- Финальное ревью с другим `request` может отметить только несвежие; отметка другого условия лишняя (§2.7).
- Вид запуска, который никто не держит (список, карточки до открытия), дерево копии не читает: он ничего не пишет.
  Там доказательство `change` принятого этапа, после приёмки которого был ход исполнителя, считается несвежим, пока
  финал его не подтвердил («менялись или могли меняться»). Завершённый запуск показывается по основанию.

**Возврат условий (5h §3.8).** При отказе свежего финала (`request: "none"`) непринятыми становятся условия принятых
этапов, у которых одно из трёх:
- нет доказательства на дереве финала: несвежее и не подтверждено, не выполнено; проверки — по последнему результату
  перед финалом;
- они покрывают `R` с `not_met`;
- они связаны с открытым `blocking`.

Следующий план обязан их `keep` или `dropped`. Множество вычисляется живо из финального ревью действующей версии
плана. При воспроизведении оно не пересчитывается: `planProblems(returned = "any")`.

Возврат к checkpoint ниже этапа недостижим: `reset_to_checkpoint` всегда ведёт к последнему checkpoint. Отдельного
правила нет.

**Итог: не чище, чем есть (уточнено при реализации A4).**
- Основание `completed` получает раздел `person`: `droppedConditions`, `droppedRequirements`, `downgraded`,
  `closedByPerson`, `conditions` (условия `person` и их статус). Требования — с `dropped`.
- В итоге, на доске панели и в разделах — строка «Решения человека вместо доказательств: снято …; понижено …; закрыто
  человеком …». Снятые условия — отдельным списком «Сняты решением человека (не выполнены)», с причиной лида.
- Счёт «N из M условий выполнено» снятые условия не включает и выполненными их не называет.
- История замечаний помечает каждое событие человека: «решение человека».
- «Закрыто человеком» — по последнему событию открытия или закрытия (`opened`, `reopened`, `closed`,
  `closed_by_person`). Позднейшие события — спорный повтор, его отклонение — этого не меняют.

**Восстановление.**
- **Оборванный хвост v2** берётся при открытии сам: байты — в `quarantine/torn-<offset>-<sha256>.bin`, журнал
  усечён до последней целой строки, запись `journal.tail_repaired`. Целые строки не трогаются. v1 по-прежнему
  спрашивает человека.
- **Команды v2.** Команда, чьё решение уже в журнале (`decidedCommands`: ответы, уточнения, лимиты, восстановление,
  решения о командах проверки, `finish.confirmed`, `plan.decided`, `person.decided`), при открытии завершается
  `accepted`. Повтор того же `commandId` ничего не пишет. `recover` — `accepted`, только если решение есть у каждого
  хода `outcome_unknown`. Команда без решения → `rejected(interrupted)`.
- Пауза человека после сбоя показывается как `recovered`, как любой запуск с незавершённой работой (запись
  `run.recovered`). «Продолжить» возвращает к той же паузе человека: ни цикл, ни автопилот за человека не решают.
  Пауза с уже записанным решением → `paused(recovered)`, продолжает человек.

**Воспроизведение.**
- Первый этап:
  - `plan.proposed` — завершённый ход плана, последний `orch.turn`. `firstStage` = принятые + 1.
  - Пока предложение ждёт, допустим только `plan.decided`. `turn.intent`, `check.started` и `completed` →
    `replay_conflict`.
  - `plan.decided` — по открытой команде, к ожидающему предложению.
  - `person.decided`:
    - по открытой команде `person.decide`;
    - спорный пункт — существующего `review.assessed`, решается один раз;
    - номер нового `F` — следующий;
    - повтор с `reopened: true` на `runKey` закрытия — нарушение.
- Второй этап (тексты):
  - план без `proposed` не снимает;
  - `choices` — ровно затронутые замечания;
  - решение об условии — только для условия `person`;
  - `stage.accepted` — при `met` человека;
  - push и QA запуска без проверок доставляют `tree` и `commit` из `finish.confirmed`, принятого после последнего
    commit и до этого шага;
  - `completed` — снятое `R` не требует доказательства и не считается выполненным.

**Порядок блокеров** (§2.3): `checks_undecided`, `plan_proposal_pending`, `disputed_pending`, `stage_not_accepted`, …

## 3. Совместимость

### 3.1. `minReaderVersion` = 2

По §2.2.1 п. 4 журнал вправе объявить `minReaderVersion: 1`, только если читатель v1 (A0, сборка 1.5.7)
**пропуском** новых записей и **игнорированием** новых полей получает верное показанное состояние. Разбор по
каждой записи: что 1.5.7 показала бы при `minReaderVersion: 1`, если бы запись была `skippable` (новые типы) или
спроецирована на поля v1 (изменённые):

| Запись | Что покажет 1.5.7 | Верно? |
|---|---|---|
| `checks.proposed` | нет предложения; запуск «идёт», команд нет | **нет**: скрыто, что ждётся решение о командах |
| `checks.decided` | нет набора команд: `goal.checks` пуст, `check.*` с `cmd-1` не в списке целей (`progressOf` их не покажет) | **нет**: проверки, по которым шла приёмка, не видны |
| `finish.confirmed` | push/QA выполнены без объяснения, отказ не виден | **нет**: «отказано пользователем» выглядит как «не запрашивалось» |
| `review.assessed` | ревью нет; `stage.accepted` без `review.recorded(accept)` → `replay_conflict` → откат показа | **нет** (откат), а без проверки `stage.accepted` — этапы приняты без замечаний, открытые `blocking` скрыты |
| `review.discarded` | ход проверяющего без результата | **нет**: не видно, почему ревью повторялось |
| `plan.proposed` | ход плана без плана, действует старый | **нет**: скрыто ожидающее решение и снимаемые условия |
| `plan.decided` | старый план остаётся; следующая `plan.recorded` с версией через одну → `replay_conflict` | **нет** |
| `person.decided` | решение человека не видно | **нет**: условие `person` и закрытие человеком пропадают |
| `run.status(completed)` с `completion` | поле отброшено → «Завершено» | **нет, главное**: «Завершено без проверок» выглядит как подтверждённое |
| `run.status(paused)` с новыми `reason` | значение вне `PAUSED_REASONS` → `invalid_event` → откат показа | откат (показ «мигает» между полным и сырым) |
| `turn.intent(role: reviewer)` | вне `["lead","executor"]` → `invalid_event` → откат | откат |
| `stage.accepted` | `reviewTurnId` — ход проверяющего без `review.recorded(accept)` → `replay_conflict` → откат | откат; без этой проверки — «этап принят» без ревью |
| `check.started` (`checkId` из решённого набора) | примет; `progressOf` такие проверки не покажет (их нет в `goal.checks`) | **нет**: проверки невидимы |
| `finish.intent(push\|qa)` после подтверждения | примет без проверки подтверждения | **нет**: push выглядит обычным шагом, решение человека не видно |
| `orch.turn.tree`, `plan.recorded.conditionsAssigned` | поле отброшено | да |
| `run.created` (цель с `commands: []`) | цель показана; `progressOf` — без проверок | да |

Вывод: почти каждая новая запись при пропуске даёт неверное показанное состояние. Поэтому **`minReaderVersion: 2`**
по §2.2.1 п. 4. Сборка 1.5.7 показывает такой журнал в режиме §2.2:
- «Более новая версия · создан более новой версией Raoden Loom»;
- цель и сырые записи с проверкой цепочки;
- состояния нет, и поэтому оно не может быть неверным;
- доступно только «Отпустить связь» (§2.2.1 п. 1).

Сборки ≤ 1.5.6 моста не имеют: `unsupported_version`/`journal_corrupt`, остальные запуски целы (5h §2.2, проба S-A3).

### 3.2. Проверено на сборке 1.5.7

Фикстуры (§4) прочитаны функцией `parseJournal` из `main` (код A0 совпадает с 1.5.7) скриптом
`v2-fixtures/build.mjs --check`, только чтение. Таблица — в [`v2-fixtures/README.md`](v2-fixtures/README.md).
- `minReaderVersion: 2`: все 8 — `newer_version`, цепочка `ok`, цель читается.
- `minReaderVersion: 1`: откат показа на первой записи `checks.*` (`unknown_record`) или на первом ходе проверяющего
  (`invalid_event`).
- `minReaderVersion: 1` и `skippable` у новых видов: откат только на `turn.intent(reviewer)` или новой причине паузы.
  До неё 1.5.7 показывала бы v1-состояние без решений v2 — то самое неверное состояние из §3.1. Откат здесь
  защищает случайно, а не по правилу.

### 3.3. `skippable`

Ни одна запись v2 не помечается `skippable: true`:
- при `minReaderVersion: 2` сборка 1.5.7 признак не читает (режим §2.2);
- для будущих читателей признак значит «пропуск не меняет состояние», а у каждой новой записи v2 это не так (§3.1).

Будущая версия v3 решает это для своих записей сама.

### 3.4. Когда новые запуски пишутся в v2

Решение владельца §7 п. 1 (согласуется с 5h §5):
- **A1–A3:** запись v2 есть в коде, но включается только признаком разработки `CANVASTTY_JOURNAL_V2=1`.
  Он читается через `developmentEnv`, поэтому упакованная сборка его игнорирует. Им пользуются тесты, smoke и пробный
  прогон владельца на dev-сборке. Пользовательские запуски пишутся в v1.
- **A4:** каждый новый нативный запуск (цель с `commands`, в том числе пустым) пишется в v2 без признака.
  Structured-режимы остаются v1 (5h §2.1). **Уточнено при реализации A4:** это одна константа
  `JOURNAL_V2_BY_DEFAULT`. В PR A4 она `false`: A4 реализован, включение v2 — после реальной серии (§2.9).
- Журналы dev-сборок A1–A3 несут в первой записи `formatPreview: true`. Их форма ещё не окончательна: в A1–A2 ревью
  делает лид (`review.recorded`), `orch.turn.tree` появляется в A3. Когда v2 включён (`JOURNAL_V2_BY_DEFAULT`),
  сборка показывает такой журнал только для чтения, как журнал более новой версии (§2.2: цель, сырые записи, «Отпустить связь»), с подписью
  «создан пробной сборкой этапа A». Она не пытается его воспроизвести и не называет повреждённым. Сборка 1.5.7 видит
  его как любой журнал v2 (`minReaderVersion: 2`).
- Формат A4 окончателен для v2: дальше — только новая версия журнала.

**A1.1, решение §7а Q3:** сборки A1–A3 открывают журнал v2 без `formatPreview` (окончательную форму A4) путём A0:
«Только просмотр», записи как есть, без вычисленного состояния — даже если в нём только записи A1 и его
`minReaderVersion` ≤ версии читателя. Урезанное состояние не показывается никогда.

Пустые команды проверки доступны только запуску v2. Пока запись v2 выключена, поле «Команды проверки» обязательно,
как сейчас.

Решено так (§7 п. 1); вариант «v2 для пользователей сразу с A1» отклонён.

### 3.5. Запуски v1 в новой версии

- Продолжаются и завершаются по правилам v1 (ревью лидом, `review.recorded`, команды обязательны).
- В v2 не переводятся, новых записей v2 в журнал v1 не попадает.
- `openRun` для v1 не меняется: незавершённые команды → `interrupted`, оборванный хвост → `journal_torn_tail`.
- `completed` v1 показывается как раньше («Завершено»). Признака `no_checks` у v1 нет: цель v1 всегда с командами.

## 7. Решения владельца (2026-10-01)

1. **Когда новые запуски пишутся в v2:** только по признаку разработки до A4 (§3.4); с A4 — по умолчанию.
2. **Подэтапы** (§5): A1 — формат, необязательные команды, итог «без проверок»; A2 — условия; A3 — замечания и
   проверяющий; A4 — решения человека, финал, включение v2.
3. **QA и push решаются независимо**, диалог предупреждает, если QA проверяет неотправленный commit.
4. **Запуски с проверками** подтверждения push/QA не требуют (stage 13 как есть).
5. **Автопринятие предложенных команд в автопилоте — только при запрещённой сети проверок.** Профиль песочницы,
   в которой будут выполняться проверки этого запуска, должен запрещать исходящие соединения: наружу, к localhost и
   DNS (профиль `sandbox.ts` разрешений на сеть не даёт вовсе). Иначе автопилот тоже ждёт «Принять».
   - В формате: `checks.proposed.sandboxNetwork` — `"denied"`, только если проверки этого запуска идут под профилем
     Seatbelt без сетевых разрешений, иначе `"open"`. `checks.decided(by: "autopilot")` допустима только при
     `"denied"`, нарушение — `replay_conflict` (§2.1).
   - Что профиль запрещает сеть, подтверждает тест на реальном Seatbelt (A1). Это предпосылка правила, а не
     проверка пути v2: в A1–A4 предложенные команды под Seatbelt не выполняются, этот шаг в подэтапы этапа A не
     входит.
   - Правило действует и при `count: 0` («команд нет»): автопилот ждёт «Принять» и тогда, хотя запускать нечего.
     Так буквально по решению; отступление — вопрос владельцу.
   - **Факт на 2026-10-01:** нативные проверки — а v2 бывает только у нативных запусков (5h §2.1) — идут без
     песочницы, в login-shell пользователя (`userCheck.ts`, stage 12). Поэтому в A1 у всех запусков v2
     `sandboxNetwork: "open"`, и автопилот ждёт «Принять». Автопринятие появится, только если предложенные команды
     начнут выполняться под Seatbelt — вне этапа A.
6. **Команды после принятия не меняются;** «Изменить» — только на паузе предложения. (A1.1, §7а Q2: исключение —
   «Изменить команду» на паузе `check_needs_permissions`, для одной отклонённой песочницей проверки.)
7. **Предложение команд при заданных в цели командах** — `invalid_report`.

## 7а. Решения владельца A1.1 (2026-10-02)

Пункт 5 §7 в части «вне этапа A» и «правило действует и при `count: 0`» уточнён этими решениями; принятый текст
выше оставлен как был.

- **Q1. Лид предложил 0 команд:** правило о сети неприменимо. Автопилот — сразу к итогу `no_checks`, без паузы
  (`checks.decided(by: "autopilot", count: 0)`; при воспроизведении автопилотное решение допустимо при `"denied"` или
  `count: 0`). Пошагово — пауза «Лид не нашёл команд проверки» с действиями «Добавить команды» (`edit`) и
  «Продолжить без проверок» (`accept`).
- **Q2. Команды лида — в песочнице Seatbelt** (§2.6): сеть наружу запрещена, кроме этой машины; запись — рабочая
  папка и временный каталог; чтение — как у runner. Команды человека — как прежде. Автопринятие — если все принятые
  команды от лида и идут в профиле. Отказ песочницы — пауза «Проверке нужно больше прав»: «Запустить без песочницы»
  (только человек, и в автопилоте) и «Изменить команду»; решение записано (`checks.amended`) и действует на эту
  команду в этом запуске.
  - **Уточнение по PR #16, S1-4 (2026-10-02):** «Запустить без песочницы» для команды лида убрано — отказ виден
    только по выводу, команда может его подделать. Остаётся «Изменить команду»: полный текст в редакторе, сохранённая
    строка (изменённая или нет) — команда человека, без песочницы, через `checks.amended` (`line` теперь
    обязателен). В автопилоте пауза сама не снимается.
- **S1-5 (PR #16, 2026-10-02):** Q2 не сужается; доступ проверок лида к localhost и сервисам машины — принятый
  остаток (§2.6): агенты «Как в моём терминале» могут не меньше.
- **Q3. v2 без `formatPreview` в сборках A1–A3** — только просмотр путём A0, записи как есть, без вычисленного
  состояния (§3.4).
