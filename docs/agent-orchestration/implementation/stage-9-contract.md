# Контракт этапа Р9: сквозные проверки приложения и восстановление после аварий

Строка 9 таблицы этапов ROADMAP, поверх принятых Р7 (движок в main, IPC) и Р8 (UI на холсте). Проверяется настоящее приложение (неупакованная сборка `npm run build`) с отдельным временным `userData` и временным Git-проектом. Провайдеры — fake CLI (`tests/fixtures/orchestration/mock-*.mjs`), реальные модели, упаковка и публикация не запускаются.

## 1. Что уже доказано до Р9

| Сценарий | Уровень | Где |
|---|---|---|
| Два этапа: план → исполнитель → проверка → ревью → checkpoint каждого этапа → финальное ревью → `completed` | сервис на тестовых агентах; ветка проверялась только как `main == HEAD` | `orchestration-service` |
| Один этап до `completed`, с раундом исправлений | Electron: IPC smoke и UI smoke | `smoke:orchestration-ipc`, `smoke:orchestration-ui` |
| Pause, Step, Resume, Stop; поздний ответ после Stop | сервис (гонки) и менеджер | `orchestration-service-races`, `orchestration-service`, `orchestration-manager-ipc` |
| Stop через UI (пауза на плане, работающий исполнитель) | Electron UI | UI smoke; Pause и Step там только предлагались, не нажимались |

## 2. Пробелы, которые закрывает Р9

1. Два этапа в настоящем приложении с проверкой исходного проекта: HEAD, ветка, все ссылки вне `refs/canvastty/`, `git status` и хэши рабочих файлов не меняются; проект получает только `refs/canvastty/<runId>/*`.
2. Pause после хода, Step, Resume и Stop нажатием в окне; после принятого Stop не начинается ни одна операция.
3. SIGKILL именно main-процесса приложения (не его группы и не штатный выход) во время хода исполнителя и отдельно во время проверки. После повторного запуска:
   - карточки, связь и история на месте;
   - ничего не повторяется само;
   - доступны действия восстановления по контракту;
   - все процессы убитого приложения завершаются сами.
4. Потерянный ответ IPC после того, как main принял команду; повтор кнопкой на панели, в том числе после перезагрузки окна; действие выполняется один раз.
5. Ошибка загрузки текста истории: понятное сообщение и работающий «Повторить».

## 3. Механизмы теста

- **Окно** — DevTools-протокол renderer (`--remote-debugging-port`, как в UI smoke Р8): события мыши, проверка попадания, снимки. Общий драйвер — `scripts/orchestration-app-kit.mjs`; его используют и UI smoke, и E2E.
- **Наблюдение** — только чтение: журнал `runs/<id>/journal.jsonl`, счётчики вызовов fake CLI, `git` исходного проекта, `ps`. Вывод о прерванной проверке — через `readRun` (решение `not_verified(interrupted)` не журналируется, Р2).
- **Удержание операции:**
  - исполнитель ждёт в обёртке fake CLI, пока есть файл-флаг;
  - проверка — тест проекта, который ждёт, пока есть свой файл-флаг. Песочница читает вне копии: чтение запрещено списком, а не по умолчанию (Р4).
- **Авария** — `SIGKILL` pid main-процесса. Процесс Electron запускается напрямую, без обёртки, поэтому `child.pid` и есть main. До убийства снимается дерево его потомков. После убийства ждём, пока исчезнут все эти pid, и проверяем, что нет ни одного процесса с путём временного каталога теста в командной строке.
- **Потеря ответа** — `CANVASTTY_ORCHESTRATION_TEST_DROP_REPLIES=<абсолютный каталог>`. Переменная читается только через `developmentEnv`: упакованная сборка её игнорирует, это проверяет `orchestration-manager-ipc`. Работает так (`dropCommandReplies` в `manager.ts`):
  - команда, для вида которой в каталоге лежит файл, выполняется как обычно;
  - затем файл удаляется, а ответ заменяется ошибкой IPC. Так renderer получает транспортный сбой после того, как main принял команду.
  
  Другие каналы не затрагиваются. Отладочный порт main-процесса (`--inspect`) не используется: открыть его запрещено средой исполнения, а в упаковке его закрывает fuse `enableNodeCliInspectArguments: false`.
- **Ошибка загрузки текста** — `chmod 000` на файлы `runs/<id>/texts/*`, затем права возвращаются и нажимается «Повторить».

Все действия пользователя идут через окно. Прямые вызовы `window.canvasTTY.orchestration` используются только для чтения состояния холста в утверждениях.

## 4. Восстановление после аварии (уточнение Р7 §5)

Запуск на диске, который не держит ни один процесс, но журнал оставил его `preparing`/`running`/`pausing`/`stopping` или с незавершённой работой, остался от процесса, завершившегося без shutdown. Условие — `needsRecovery(state)` в `journal.ts`, то же, по которому `openRun` пишет `run.recovered`.

`list`/`get` показывают такой запуск так, как его запишет открытие:
- `paused(outcome_unknown)`, если ход был в полёте;
- иначе `paused(recovered)`.

При этом ничего не пишется и не запускается. `revision` та же, потому что `run.recovered` её не меняет. Поэтому команда, отправленная с показанной ревизией, не устаревает.

До Р9 такой запуск показывался «Выполняется» с «Пауза» и «Стоп», а действия восстановления были недоступны (T98).

Действия по контракту Р5:
- `outcome_unknown` — «Принять результат хода», «Повторить ход», «Вернуть к последнему checkpoint» (с подтверждением), «Стоп»;
- `recovered` — «Продолжить», «Один шаг», «Стоп».

Прерванная проверка — `not_verified(interrupted)`. Она запускается снова только после «Продолжить» или «Один шаг», новым `checkRunId`.

## 5. Ошибка загрузки текста

`orchestration:text` отвечает так:
- `text_missing` и `text_corrupt` — как отвечает Store;
- любая другая ошибка файла (права, ввод-вывод) — `text_unreadable`, без пути и errno.

У всех трёх кодов есть сообщения на русском и английском. До Р9 показывалось «Операция не выполнена (EACCES)» (T99).

## 6. Проверки

- `scripts/e2e-orchestration.mjs` (`npm run e2e:orchestration [-- --out <dir>]`, после `npm run build`): три запуска приложения на одном `userData`, run A–D, 38 утверждений; отчёт `report.json` и снимки обезличены.
- `tests/orchestration-r9-e2e.test.mjs`: `text_unreadable` и `dropCommandReplies` на уровне менеджера.
- `tests/orchestration-service-races.test.mjs`: вид запуска после аварии до открытия (`paused(outcome_unknown)` / `paused(recovered)`), чтение ничего не пишет, ревизия совпадает с открытым запуском.
- `tests/orchestration-manager-ipc.test.mjs`: `CANVASTTY_ORCHESTRATION_TEST_DROP_REPLIES` читается только через `developmentEnv`.
- Регрессии UI smoke Р8 после выноса драйвера в `orchestration-app-kit.mjs`.

Результаты — VALIDATION-MATRIX (E1–E9), свидетельства — [evidence/e2e-stage-9/](../evidence/e2e-stage-9/).

## 7. Вне Р9

Упаковка и packaged-прогон, реальные модели, Linux-runner, поиск осиротевших процессов при старте (`recovery.inspected` в ARCHITECTURE-PROPOSAL: не реализован; при SIGKILL всей группы main процессы CLI переживут supervisor — известное ограничение, не проверялось).
