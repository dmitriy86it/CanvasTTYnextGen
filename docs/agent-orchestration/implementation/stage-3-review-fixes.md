## Дефект 1. Частичное восстановление выдавалось за безопасный конфликт

**Было:** любой ненулевой выход `read-tree -m -u` → `restore_conflict` («копия не менялась»). Воспроизведение 1: `zdir` без права записи — `a.txt` уже восстановлен, `zdir/c.txt` остался изменённым, а вызывающему сообщили о конфликте.

**Решение — три различимых исхода.**

1. **Отказ до записи.** Проверки до первой записи: путь цели занят файлом вне recovery-дерева (`restore_conflict`), состояние копии не совпадает с подготовленным снимком (`restore_state_changed`, дефект 2). Копия не менялась — это гарантируется тем, что запись ещё не начиналась.
2. **Частичный или неизвестный результат.** Любой сбой после начала записи. Перед первой записью создаётся файл-намерение `workspace/restore.json` (`{v:1, target, targetCommit, recoveryCommit, fromTree, toTree, startedAt}`, tmp → fsync → rename). При сбое `read-tree` дерево копии сравнивается с `fromTree`: совпало → ничего не записано, `restore_conflict`, файл-намерение удаляется; не совпало → `restore_incomplete`, файл-намерение **остаётся**. Пока он есть, `createSnapshot`, `createCheckpoint`, `prepareRestore` и `applyRestore` отказывают с `restore_incomplete`: содержимое копии неизвестно. Крах процесса между записью файла-намерения и подтверждением даёт тот же результат.
3. **Подтверждённый успех.** После `read-tree` проверяется только то, что восстановление обязано было сделать, **без учёта ignore-правил**: во временном индексе `read-tree <toTree>` → `update-index --refresh` → `diff-index --raw <toTree>` без pathspec (в индексе только пути `toTree`, поэтому неотслеживаемые и игнорируемые файлы в сравнение не входят), плюс каждый путь из `fromTree \ toTree` отсутствует на диске — с одним исключением: путь, который цель требует как каталог для своих файлов (`item` → `item/child.txt`), допустим в виде каталога; файл, который там был, к этому моменту уже удалён, а содержимое целевых файлов внутри проверено `diff-index`. Всё совпало → файл-намерение удаляется, возвращается `{status: "restored"}`; иначе `restore_incomplete`, файл-намерение остаётся.

   Пересчитывать всё дерево копии здесь **нельзя**: набор игнорируемых файлов зависит от `.gitignore`, который сам меняется восстановлением. Если цель не содержит правила, добавленного агентом, ранее скрытый артефакт после восстановления становится видимым, дерево не совпадает с `toTree` — и корректное восстановление объявлялось бы неизвестным, блокируя run (найдено restore-tests при проверке пост-проверки). Файлы вне `fromTree ∪ toTree` не проверяются: контракт их не трогает.

Автоматического откота частичного восстановления **нет**: надёжного протокола для этого у нас нет, а вторая неудачная попытка записи ухудшила бы состояние. Разблокировка только явная: `clearIncompleteRestore(ws)` удаляет файл-намерение по решению пользователя. Recovery-снимок при этом сохранён и остаётся в журнале, откат из него — отдельное восстановление, которое пользователь запускает сам.

Атомарность восстановления **не заявляется**: `read-tree -m -u` меняет файлы по одному.

## Дефект 2. Изменение копии между `prepareRestore` и `applyRestore`

**Было:** `applyRestore` сообщал успех, а изменённый после подготовки `b.txt` и новый `new.txt` оставались нетронутыми: `read-tree -m -u` меняет только пути, отличающиеся между `fromTree` и `toTree`.

**Решение:** до первой записи дерево копии пересчитывается и сравнивается с `prepared.fromTree` (деревом recovery-снимка). Расхождение → `restore_state_changed {expected, actual}` до записи. После записи — проверка результата против `toTree` (выше). Только подтверждённый результат позволяет записать `workspace.restored`.

`restore_state_changed` намеренно не замечает игнорируемые файлы: они вне снимка, их появление или изменение восстановлению не мешает.

**Границы.** Это проверка до операции и после операции, а не защита от произвольных конкурентных записей: писать в копию во время самого `read-tree` никто не мешает. Требование: **во время восстановления в run нет активного исполнителя и других писателей** (единственный писатель журнала — под блокировкой Store, агент остановлен). Это требование, а не обеспеченное свойство.

## Дефект 3. Recovery-снимок терял файл, принятый после baseline

**Было:** `createSnapshot` по умолчанию брал базу `ws.baseline`, а `prepareRestore` базу не передавал. Файл, принятый в `stage-1` и после этого попавший под `.gitignore`, в recovery-снимок не попадал: по базе baseline он неотслеживаемый и игнорируемый.

**Решение:** база — **применимая база копии**, и она больше не подразумевается. `createSnapshot(ws, kind, base)` и `prepareRestore(ws, target, base)` принимают её обязательным параметром. Значение берётся из доверенного состояния журнала: `RunState.workspace.current` — `{commit, tree}`, который равен baseline и меняется только на подтверждённых событиях `checkpoint.created` и `workspace.restored`. Более новый ref без события журнала применимой базой не считается (он в `unjournaled`).

**Применимость базы проверяется только по форме:** `base.tree` должен быть деревом `base.commit`, иначе `invalid_input`. Что база взята из журнала, модуль проверить не может — это **требование к вызывающему** (будущий OrchestrationService передаёт `RunState.workspace.current`). Устаревшая база молча воспроизводит этот дефект.

Проверяется содержимое recovery-коммита, а не наличие ref: файл, входящий в применимую базу, обязан быть в recovery-снимке со своим содержимым с диска, даже если новое правило ignore его скрывает.

## Дефект 5 (второе ревью). Каталог, нужный цели, считался остатком

**Было:** копия заменила каталог `item` обычным файлом; восстановление к baseline правильно вернуло `item/child.txt`, но проверка отброшенных путей видела `item` в списке удалённых (`diff-tree --diff-filter=D`) и находила его на диске — уже как необходимый каталог. Результат: `restore_incomplete {path: "item"}`, файл-намерение оставался и блокировал run, хотя восстановление было полностью корректным.

**Решение:** список путей цели берётся из временного индекса (`ls-files --cached` после `read-tree <toTree>`), из него собирается множество каталогов, которые цели нужны. Отброшенный путь допустим, только если он **каталог и входит в это множество**. Оставшийся файл, каталог, которого цель не требует, и неверный тип пути по-прежнему дают `restore_incomplete` с `detail {path, directory}`. Проверка не снята и безусловным успехом не заменена.

Пустой каталог, который Git оставляет после удаления последнего файла в нём, остатком не считается: в списке отброшенных путей стоят файлы, а не каталоги.

**Ограничение проверки, установленное мутациями:** сама ветка «путь остался на диске» недостижима через публичное восстановление — попытку вернуть отброшенный файл до применения ловит раньше пред-проверка (`restore_state_changed`, до записи). Поэтому две мутации выживают: поблажка для любого каталога и снятие всей проверки. Поблажка именно для нужных каталогов мутацией убита. Проверка остаётся защитой в глубину от файловой системы или версии Git, молча не удаливших путь.

## Состояние в журнале (координатор)

| type | data | замечание |
|---|---|---|
| `workspace.restore_failed` | `{target, targetCommit, recoveryCommit, result: "partial" \| "unknown"}` | новое событие |

`RunState.workspace`:
- `current: {commit, tree}` — применимая база; baseline → меняется на `checkpoint.created` и `workspace.restored`;
- `pendingRestore` — восстановление начато и не подтверждено;
- `failedRestore` — последняя попытка дала частичный или неизвестный результат; `pendingRestore` сохраняется.

Правила воспроизведения:
- `checkpoint.created` отвергается, пока есть `pendingRestore`: содержимое копии не подтверждено;
- `workspace.restore_started` допускается, когда `pendingRestore` нет либо есть `failedRestore` (явная повторная попытка);
- `workspace.restore_failed` требует совпадения с `pendingRestore`; `pendingRestore` остаётся;
- `workspace.restored` требует совпадения с `pendingRestore`, снимает `pendingRestore` и `failedRestore`, ставит `current` = цель.

**Файл-намерение и журнал могут расходиться**, и политика такая: блокирует файл-намерение, а не журнал. Возможные расхождения:
- файл-намерение есть, `pendingRestore` есть → обычный случай: `restore_failed` уже записан или ещё нет; продолжение заблокировано;
- файл-намерение есть, `pendingRestore` нет (крах между подтверждённым восстановлением и удалением файла; `clearIncompleteRestore` делает fsync каталога, но окно остаётся) → копия всё равно считается неизвестной и блокируется. Автоматически файл не удаляется: модуль не отличает этот случай от восстановления, о котором журнал не успел узнать. Снимает пользователь через `clearIncompleteRestore`;
- файла-намерения нет, `pendingRestore` есть → восстановление не начинало запись либо процесс погиб до создания файла; операции не заблокированы, но этап принять нельзя, пока `pendingRestore` не снят.

Порядок прежний: Git-результат → событие журнала. Событие `restored` пишется только после подтверждённого результата, `restore_failed` — после частичного или неизвестного.

## API после исправления

```ts
// snapshots.ts
createSnapshot(ws, kind: "recovery" | "intermediate", base: SnapshotInfo)            // base обязателен
prepareRestore(ws, target: {name, commit}, base: SnapshotInfo): Promise<PreparedRestore>
applyRestore(ws, prepared): Promise<{ status: "restored" }>                          // иначе исключение
// workspace.ts
applyTreeToCopy(ws, fromTree, toTree, about?): Promise<void>                         // restore_conflict | restore_state_changed | restore_incomplete
readIncompleteRestore(ws): Promise<RestoreIntent | null>
clearIncompleteRestore(ws): Promise<void>                                            // только по явному решению пользователя
```

Новые коды `WorkspaceErrorCode`: `restore_state_changed`, `restore_incomplete`.

## Уточнения реализации (restore-core, приняты)

- `applyTreeToCopy(ws, fromTree, toTree, about?)`: четвёртый необязательный параметр `about {target?, targetCommit?, recoveryCommit?}`. Примитив сам этих полей не знает, а контракт называет их опциональными в файле-намерении — передаёт их `applyRestore`.
- Экспортирован `assertNoIncompleteRestore(ws)`: блокировка срабатывает по факту существования файла-намерения, даже если его содержимое нечитаемо, и код ошибки один и тот же (`restore_incomplete`) для всех операций. `readIncompleteRestore` возвращает `null` и при отсутствии файла, и при нечитаемом JSON.
- Внутри `applyTreeToCopy` пересчёт дерева идёт без блокировки (иначе была бы самоблокировка после записи файла-намерения); публичный `snapshotCopyTree` блокировку проверяет.
- Проверка состояния использует базой сам `fromTree`: всё, что в нём есть, считается отслеживаемым и перечитывается с диска, поэтому равенство деревьев означает, что копия не менялась.
- Сбой `read-tree` при неизменной копии различается как раньше: `git_failed` → `restore_conflict`, таймаут или сбой запуска → `git_error`. Ошибка не от Git (например, сбой файловой системы при пересчёте) оставляет файл-намерение: состояние неизвестно.
- Из `index.ts` наружу выведены `readIncompleteRestore` и `clearIncompleteRestore`, тип `RestoreIntent`. `assertNoIncompleteRestore` остаётся внутренним.
- Журнал: `workspace.restored` отвергается, пока стоит `failedRestore` — подтвердить можно только новую, явно начатую попытку.
