# Этап A: условия приёмки и независимое ревью — контракт

Статус: контракт, редакция 5h (2026-09-30). Редакция 5g принята внешним ревью как контракт; это не приёмка реализации
этапа A. 5h — адресная правка §3.1.1 по этому ревью. Рабочие пространства ([workspaces-spec](workspaces-spec.md)) приняты
владельцем для macOS с открытыми ограничениями, и этап A начат по порядку развития
([Автоматический цикл задач](../AUTOMATIC-TASK-CYCLE.md)): подэтап A0 (§2.2, §5) реализован и ждёт внешнего ревью, A1–A4
не начаты. Этот документ этап 13 не принимает.

Цель — принципы 1–5 и 9 цикла задач:
- у требований пользователя и условий приёмки есть постоянные id и доказательства;
- этап и запуск признаёт готовыми приложение по фактам, а не по слову агента;
- ревью делает отдельный проверяющий без переписки исполнителя;
- у замечаний есть id, признак «блокирует / пожелание», доказательство и условие закрытия;
- перепланирование не удаляет и не ослабляет требования и условия без решения человека.

Доска задач (B), параллельные исполнители (C) и EXP-SPEC-01 (D) в этап не входят.

## 0. Исходное состояние кода

Пути относительно `src/main/services/orchestration/`, если не указано иное; `svc` — `orchestrationService.ts`.

- **Цель.** `Goal.criteria: string[]` (1–32 строки до 500 символов, `svc` `checkGoal`). Критерии входят только в текст
  задания каждого хода (`svc:1257`) и в итог (`RunPanel.tsx`, «Критерии») списком без доказательств. Код их не
  проверяет.
- **План.** `REPORT_SCHEMAS.plan` (`svc:199-208`): `{stages: [{title, task}], question}`, `additionalProperties: false`.
  Условий у этапа нет. Текст плана — в `texts/`, запись `plan.recorded {turnId, version, plan, firstStage, stageCount}`.
  Новая версия заменяет все непринятые этапы; номера этапов сдвигаются.
- **Перепланирование** (`cycle.ts:133-138`, `:209`): по вердикту `replan` ревью этапа или финала, а также когда
  финальное `complete` пришло при упавшей проверке. Сравнения нового плана со старым нет.
- **Ревью** делает тот же поток лида, что планировал: роль `lead` покрывает `plan`, `review`, `final_review`
  (`svc:679`), `sessionFor` возобновляет последнюю сессию роли (`svc:795-804`). Ответ (`svc:190-197`):
  `{verdict: accept|fix|replan|question, findings: string[], question}`; финал — `complete|replan|question`.
- **Что получает ревью** (`buildTask`, `svc:1250-1307`): цель, критерии, команды проверок, план, текущий этап,
  результаты проверок на текущем состоянии (статус и последние 1500 символов вывода). Diff и отчёта исполнителя нет;
  лид читает код сам. Истории замечаний в задании ревью нет.
- **Замечания** — строки без id, признака, доказательства и условия закрытия. Исполнитель получает замечания
  последнего ревью запуска (`st.orch.reviews.at(-1)`, `svc:1287-1296`), не своего этапа.
- **Приёмка этапа** (`cycle.ts:176-200`): все обязательные проверки прошли на текущем `checkKey` **и** свежее (тот же
  `runKey`) ревью ответило `accept`; `accept` при упавшей проверке возвращает этап исполнителю. Финал: проверки прошли и
  свежий `complete` на том же `runKey` и `clarificationVersion` (`cycle.ts:203-209`). Прогресс и петли
  (`progress.ts`) считаются по нормализованным строкам замечаний.
- **Права** задаются по CLI (`access.ts`), не по роли. В нативном режиме у Codex нет значения «только чтение», и в
  режиме проекта лид может менять дерево. `lead_modified_tree` — только в режиме копии (`svc:754-756`), где лид —
  `structured-readonly` (`agents.ts:77-81`); причина входит в `STOP_ONLY` (`svc:183`, `runModel.ts:20`).
- **Роли.** `AgentRole = "lead" | "executor"`. Роль валидируется в `turn.intent` (`journal.ts:344-346`,
  `oneOf(d.role, ["lead", "executor"])`), в `orch.turn` её нет. Роль зашита также в `store.ts:92`, `:157`;
  `activity.ts:79`, `:472`, `:542`; `src/shared/orchestration.ts:154`, `:265`, `:332`; `agents.ts:137`;
  `manager.ts:823`, `:842` (`roles`); `svc:679` (роль из `purpose`), `svc:684-688` (лимит хода: не-лид получает
  `executorTurnMs`), `svc:428-429` (`askPerson`: lead = codex, иначе claude).
- **Сессии.** Новую сессию открывает `sessionId: null` (`agents.ts:151`): Codex `thread/start`, Claude — новый UUID.
- **Diff.** `workspace.ts`: `snapshotCopyTree`, `diffTreeNames(ws, from, to, max)`, `diffTreePath(ws, from, to, path,
  maxBytes)` — по объектам `control.git`, во всех режимах.
- **Журнал** (`journal.ts`). `JOURNAL_VERSION = 1`; `v: 1` пишется в **каждую** запись и входит в её хеш

  значение закрытого перечисления (роль, причина паузы, `LIMIT_KINDS` `:291`) → `invalid_event` → журнал `corrupt` с
  валидным префиксом. Открытый запуск на таком журнале невозможен (`store.ts:746`), `snapshot()` без состояния

  (`src/shared/orchestration.ts:223`). Решения человека структурно записываются командами (пример —
  `recovery.decided {commandId, action, turnId}`, `journal.ts:418`).
- **Итог в renderer** строится из сырых записей: `runStatus.ts:329-346` и `runModel.ts:102` читают только
  `review.recorded`, `runStatus.ts:392` приводит замечания к строкам.

## 1. Сущности и идентификаторы

| Сущность | Что это | Id | Кто задаёт |
|---|---|---|---|
| **Требование** | Критерий цели в формулировке пользователя | `R1`…`Rn` — номер в `goal.criteria` | Пользователь; неизменно |
| **Условие приёмки** | Проверяемое условие работы | `C1`, `C2`… — сквозной номер в запуске | Лид предлагает, **номер присваивает приложение**; текст, `covers` и `evidence` после создания неизменны |
| **Доказательство** | Факт, закрывающий условие или замечание | `seq` записи журнала | Приложение (проверка, проверка пути по diff), человек (команда) |
| **Замечание** | Дефект или пожелание проверяющего | `F1`, `F2`… | Проверяющий; номер присваивает приложение |
| **Проверяющий** | Отдельная сессия CLI без переписки исполнителя | роль `reviewer` | Приложение |

Этап плана не часть id условия: условие можно перенести в другой этап без смены id.

## 2. Данные

### 2.1. Версия запуска

- Запуски этапа A пишут записи с `v: 2`. Версия запуска задаётся первой записью `run.created`; все записи журнала
  обязаны иметь ту же `v`, смешение — `invalid_event`. Писатель берёт `v` из состояния запуска, а не из константы.
- Парсер новой сборки принимает `v ∈ {1, 2}`. Запуски v1 продолжаются по прежним правилам (ревью лидом) и в v2 не
  переводятся.
- **v2 только для нативных запусков** (цели с `commands`, [stage-12](stage-12-native-sessions.md)) во всех их режимах
  работы: папка проекта, worktree и нативная «отдельная копия» (`workMode: "copy"`, `svc:250`). Запуски
  structured-режимов (`structured-readonly`/`structured-edit`, до stage 12) остаются v1.
- Схема `run.created` в v2 та же, что в v1 (цель расширяется только необязательными ключами, которые читатели уже
  игнорируют). На этом держится мост A0.

Почему не журнал активности: он — представление, ограничен 4 МиБ, пишется без гарантий (`activity.ts`, `writeFailed`)
и вне цепочки хешей. Почему не отдельный файл: без ссылки из цепочки хешей нет гарантий порядка и целостности, а
старая сборка продолжила бы такой запуск по старым правилам, не видя условий.

### 2.2. Мост A0 (совместимость с откатом)

Сборка A0 выходит **до первой сборки, пишущей v2** (A4, §5). A0 не разбирает записи v2: она смотрит только `v` первой
записи. Для журнала с `v > 1`:
- `integrity: "newer_version"` (новое значение в `src/shared/orchestration.ts:223`), `state: null`;
- в списке — цель из `run.created` (её схема не меняется, §2.1) и плашка «создан более новой версией Raoden Loom»;
- «история» — сырые записи с проверкой только цепочки хешей, без `applyRecord`;
- `openRun`, `acceptTornTail` и любые записи не вызываются; действий нет, кроме закрытия панели;
- этот путь нужен в `store.readRun`, `manager.snapshot()` (сейчас отказывает `journal_corrupt`, `manager.ts:297`),
  `manager.journal()` (сейчас `parseJournal`, `manager.ts:315`) и в списке запусков;
- другие запуски не затрагиваются.

С A4 и дальше правило моста — `v` больше максимально поддерживаемой версии (для A4 — `> 2`), чтобы будущая
версия журнала тоже читалась как «создан более новой версией». Сборки ≤ 1.5.6 моста не имеют: запуск v2 для них — `unsupported_version`/`journal_corrupt`, история не видна,
остальные запуски целы (проверяется пробой S-A3). Это пишется в CHANGELOG и INSTALL сборки A4.

#### 2.2.1. Поправка к §2.2 (принята владельцем 2026-09-30)

Принята владельцем 2026-09-30 вместе с расширением R6a (все запуски более новой версии на связи отпускаются вместе,
пункт 1). Дополняет §2.2; текст §2.2 не менялся.

1. **Отпустить связь.** Сборка A0 может отпустить связь, которую держит запуск более новой версии (`newer_version`
   или `newer_version_compatible`): отдельная команда `orchestration:link-release-newer` `{ commandId, linkId, runId }`.
   Main проверяет, что все три id — UUID, что запуск именно этой связи и что по правилу занятости он запуск более
   новой версии. Другие запуски более новой версии на той же связи отпускаются вместе с ним (по записи на каждый, с
   одним `commandId`); незавершённый запуск этой версии на той же связи отказывает (`link_active_run`). Связь удаляется, папка проекта освобождается, владелец запуска
   фиксируется (`owners`), в `canvas.json` добавляется запись `releasedNewerRuns: [{ runId, linkId, folder, releasedAt,
   appVersion, commandId }]`. Повтор с тем же `commandId` возвращает ту же запись и ничего не меняет; тот же `commandId`
   для другой связи — `request_conflict`. Файлы `runs/<id>/` не меняются. Запуск остаётся в истории пространства только
   для просмотра. Запускам v1 команда отказывает (`run_not_newer`).
2. **Обязанность будущих версий.** Версия, создавшая такой запуск, обязана читать `releasedNewerRuns` и показывать
   запуск без связи (не восстанавливать связь молча и не считать папку занятой им), оставляя запуск доступным в своих
   правилах.
3. **`minReaderVersion`.** Первая запись журнала `v > 1` может нести целое поле `minReaderVersion` — наименьшую версию
   читателя, способную воспроизвести журнал по своим правилам. Если `1 ≤ minReaderVersion ≤ READER_VERSION` (у A0 —
   1), журнал получает статус `newer_version_compatible`: цепочка хешей проверяется как обычно, записи применяются по
   правилам v1, неизвестные поля конверта и данных игнорируются, панель показывает полное состояние. Всё остаётся только
   для чтения, как в §2.2: `openRun`, recovery, усечение хвоста, команды, `changes`/`diff`, `create` с тем же id,
   `deleteRun` и запуск CLI запрещены. Поле отсутствует, не целое, меньше 1 или больше `READER_VERSION` — режим §2.2
   без изменений. Запись, которую v1 не применяет (неизвестный тип, данные, которые v1 отвергает, конфликт
   воспроизведения), возвращает показ всего журнала к режиму §2.2 с пометкой `fallback: { line, code }`
   (`unknown_record` / `invalid_event` / `replay_conflict` / `version_changed`).
4. **Что вправе объявлять `minReaderVersion: 1`.** Только журнал, который читатель v1 понимает без потери смысла:
   добавлены лишь необязательные поля (в конверте или в данных существующих записей), значение которых v1 может
   игнорировать, и записи, которые v1 может пропустить без изменения состояния. Новые типы записей, меняющие состояние
   (например, записи v2 из §2.4), новые значения перечислений, изменённый смысл существующих полей или переходов —
   `minReaderVersion` не ниже 2. Журналы v1 это поле не пишут никогда; новые запуски A0 пишутся в v1 без изменений.
   Журнал v2+ вправе объявлять `minReaderVersion: 1`, только если все новые виды записей помечены `skippable: true`
   (пункт 5) и новые поля в известных записях необязательны.
5. **Пропускаемые записи.** В журнале `newer_version_compatible` запись неизвестного типа с полем конверта
   `skippable: true` (строго boolean `true`) пропускается: состояние строится без неё. Неизвестный тип без этого
   признака или с любым другим его значением (`"true"`, `1`, `false`) — откат к режиму §2.2 с пометкой
   `unknown_record`. У известного типа признак игнорируется: запись применяется как обычно. Цепочка хешей проверяется
   по всем записям, включая пропущенные. Панель показывает число пропущенных записей: «Пропущено записей новой
   версии: N».
6. **Версия журнала фиксируется первой записью.** Версия (`v`) и `minReaderVersion` берутся из первой записи и дальше
   не меняются; `minReaderVersion` в других записях не рассматривается. Запись с другим `v` посреди журнала — откат
   показа к режиму §2.2 с пометкой `version_changed`.

### 2.3. План v2

Текст плана — в `texts/`.

```json
{
  "stages": [{
    "title": "…", "task": "…",
    "conditions": [
      {"keep": "C3"},
      {"text": "…", "covers": ["R1"], "evidence": {"kind": "check", "check": "cmd-1"}}
    ]
  }],
  "dropped": [{"condition": "C4", "why": "…"}],
  "dropRequirements": [{"requirement": "R2", "why": "…"}],
  "question": null
}
```

- Новое условие приходит без id: `text` 1–500, `covers` ⊆ `R1…Rn` (может быть пустым), `evidence.kind`:
  - `check` — одна из `goal.checks`; выполнено, если она `passed` на текущем `checkKey` (выводится, отдельной записи нет);
  - `change` — выполнено, когда проверяющий отметил его `met` и указал пути, изменённые с начала запуска (§3.3);
  - `person` — выполнено решением человека (§3.5).
- `keep` сохраняет существующее непринятое условие (в любом этапе нового плана).
- На этап 1–12 условий. Приложение присваивает новым условиям `C<n>` в порядке появления в плане от счётчика
  `nextCondition` состояния; номера входят в канонический текст плана. Счётчик растёт и на `plan.proposed`: номер
  условия из отклонённого предложения не переиспользуется, так что `C<n>` везде означает один текст.
- `dropped` — явное предложение снять непринятое условие; `dropRequirements` — явное предложение снять требование.
  Оба применяются только решением человека (§3.6).

**Проверка плана** (по порядку; первое нарушение → `invalid_report` с перечнем, план не записывается):
1. Схема и id: `keep` и `dropped` ссылаются только на существующие непринятые условия, без повторов; `dropRequirements`
   — только на неснятые `R`.
2. **Каждое непринятое условие прежнего плана** — ровно в одном из `keep` или `dropped`.
3. **Покрытие.** Считается так, как будто предложения уже применены: каждое `R`, которое не снято раньше и не входит в
   `dropRequirements`, покрыто хотя бы одним условием среди действующих условий принятых этапов, `keep` и новых
   условий. `R`, потерявшее покрытие без явного `dropRequirements`, — случайная потеря, а не предложение.

План без `dropped` и `dropRequirements` записывается `plan.recorded` (в v2 — с полем `conditionsAssigned`, как у
`plan.proposed`) и сразу действует, как сейчас. План с ними
записывается `plan.proposed` и **не заменяет действующий план** до решения человека (§3.6). Ход плана даёт ровно
одну из записей `plan.recorded` / `plan.proposed` или ни одной (`invalid_report`); воспроизведение это проверяет.

**Перечень нарушений** не хранится отдельно: следующий ход плана получает его, пересчитанный из отчёта отклонённого
хода (`turn.finished.report`) и текущего состояния, поэтому перезапуск его не теряет и лид видит, что исправлять.

### 2.4. Новые записи журнала (только v2)

Каждое действие, меняющее состояние условий, замечаний или плана, — **одна запись**. Её эффекты либо все есть в
журнале, либо их нет (§3.10).

| Запись | Поля | Смысл |
|---|---|---|
| `review.assessed` | `turnId, stage\|null, request: "none"\|"replan"\|"question", report:TextRef, applied:TextRef, clarificationVersion, runKey` | Результат ревью целиком: исходный отчёт и его применение (§3.10). В v2 заменяет `review.recorded` |
| `review.discarded` | `turnId, treeBefore, treeAfter` | Отчёт хода не применён: дерево изменилось во время хода (§3.1). «Не применён из-за аварии» отдельной записи не имеет (§3.10) |
| `plan.proposed` | `turnId, plan:TextRef, firstStage, stageCount, conditionsAssigned` | План с `dropped`/`dropRequirements`; ждёт решения, действующий план не меняет. Версии нет: её присваивает `plan.decided(accept)`; `conditionsAssigned` — сколько номеров `C` занято |
| `plan.decided` | `commandId, proposalTurnId, decision: "accept"\|"return", version\|null, choices:TextRef, note:TextRef\|null` | Решение человека по предложению (§3.6): все снятия и судьба каждого затронутого замечания в одной записи; при `accept` `version` = действующая + 1 |
| `person.decided` | `commandId, subject: "condition"\|"finding"\|"disputed", target, decision, finding\|null, runKey` | Решение человека вне плана (по образцу `recovery.decided`). `condition`: `target` = `C`, `decision` `met`\|`not_met`. `finding`: `target` = `F`, `decision` `close`\|`to_wish`. `disputed`: `target` = `{reviewTurnId, index}` спорного пункта, `decision` `new`\|`repeat`; при `new` `finding` = присвоенный номер (`nextFinding` на момент записи, проверяется при воспроизведении), у нового `F` `possibleRepeatOf` = кандидаты пункта, владелец — по §3.4 от пункта отчёта; при `repeat` `finding` = выбранный кандидат, дальше правило повторного открытия по id |

Роль `reviewer` — в `turn.intent` и во всех местах из §0 «Роли». `orch.turn` хода проверяющего в v2 несёт `tree` —
дерево до хода (для §3.1 и §3.10). Новые причины паузы: `coverage_lost`,
`tree_changed_during_review`, `awaiting_person_decision`. Новые значения — только в v2. `LIMIT_KINDS` не меняется.

`report` проверяющего (текст, схема ответа хода):

```json
{
  "conditions": [{"id": "C2", "status": "met" | "not_met", "paths": ["src/a.ts"], "note": "…"}],
  "requirements": [{"id": "R1", "status": "met" | "not_met", "note": "…"}],
  "findings": [{"id": "F3" | null, "severity": "blocking" | "wish", "condition": "C2" | null,
                "problem": "…", "evidence": "…", "closeWhen": "…", "status": "open" | "closed",
                "paths": ["src/a.ts"],
                "relation": null | {"repeatOf": "F1"} | {"distinctFrom": "F1", "why": "…"}}],
  "request": "none" | "replan" | "question",
  "question": null
}
```

`requirements` обязательно только в финальном ревью. Новое замечание — `id: null`; номер присваивает приложение. Новое
`blocking` обязано указать `paths`; без них — `invalid_report`. `relation` — ответ на пометку «возможный повтор»
(§3.4).

`applied` (текст, канонический JSON) — что приложение сделало с отчётом, с уже присвоенными номерами:

```json
{
  "report": {"sha256": "…", "bytes": 0},
  "conditionsMet": ["C2"],
  "opened": [{"id": "F7", "index": 0, "severity": "blocking", "condition": "C2", "stage": 2, "paths": ["src/a.ts"],
              "possibleRepeatOf": null | "F1"}],
  "closed": [{"id": "F3", "index": 1}],
  "reopened": [{"id": "F1", "index": 2}],
  "refused": [{"index": 3, "finding": "F1", "reason": "same_run_key" | "no_new_evidence" | "declared_repeat"}],
  "disputed": [{"index": 4, "candidates": ["F1"]}],
  "unchanged": [{"id": "F5", "index": 5}],
  "nextFinding": 8
}
```

`index` — позиция в `report.findings`. Каждое замечание отчёта попадает ровно в одну из групп `opened`, `closed`,
`reopened`, `refused`, `disputed`, `unchanged` (открытое замечание, повторённое по id без изменений). Смена `severity`
или `condition` существующего `F` по id — `invalid_report`: повысить `wish` можно только новым `blocking` (§3.4) или
решением человека.

## 3. Правила main

### 3.1. Роли

- **Лид** планирует и перепланирует; этапы и финал не проверяет.
- **Исполнитель** — без изменений; получает открытые `blocking` и невыполненные условия **своего этапа**.
- **Проверяющий** — роль `reviewer`, провайдер лида (Codex), **новая сессия на каждое ревью**; лимит хода —
  `leadTurnMs`; диалог разрешений показывает провайдера проверяющего (`askPerson` по карте ролей, а не
  «lead = codex, иначе claude»). Настройки CLI пользователя — те же, что у лида: права не расширяются и не сужаются
  тихо.
- **Дерево во время ревью.** Снимок до и после хода проверяющего. Если дерево изменилось (правка проверяющего,
  артефакт команды, работа пользователя в папке — различить нельзя):
  - ревью недействительно: пишется `review.discarded`, отчёт не применяется;
  - ревью повторяется **один раз** на новом `runKey`; второе подряд отброшенное ревью ставит паузу
    `tree_changed_during_review` (не `STOP_ONLY`), итог показывает diff изменений. Действия: «продолжить с
    изменениями» и Stop. Точные правила счёта, выхода из паузы и восстановления — §3.1.1. Отката изменений в этапе A нет: существующая команда `recover` работает только для
    `outcome_unknown` и откатывает к checkpoint, а не к дереву до ревью; в папке проекта и worktree восстановления нет
    вовсе (`workspace.ts:64`, `:748`, `svc:1487`). Откат к `orch.turn.tree` — вне этапа (§8);
  - проверка дерева идёт **раньше** `pauseForOutcome` и `invalid_report`: ход, изменивший дерево и давший плохой
    отчёт, тоже пишется `review.discarded`;
  - ход, результат которого не записан (из-за аварии или потому что исход не дал записи), сравнивается
    `orch.turn.tree` с деревом **при решении цикла** (§3.1.1), а не при открытии: к тому моменту в папке могли
    появиться правки пользователя, но сравнение нужно именно перед следующим ревью. Расхождение пишется
    `review.discarded` и считается (§3.10).
  Сессию «только для чтения» у Codex проверяет проба S-A1; до неё запрет обеспечивается только обнаружением.

#### 3.1.1. Последовательность отброшенных ревью и выход из паузы

Механизм обходится без новых записей: всё выводится из существующих `orch.turn`, `turn.intent`, `turn.finished`,
`run.status` и записей результата ревью. Порядок записи хода в коде: `orch.turn` → `turn.intent` → запуск процесса
(`svc:695-712`); отдельной записи «процесс стартовал» нет.

**Ключ.** Счёт ведётся отдельно для каждого ключа `(planVersion, purpose, stage)`, где `purpose` — `review` или
`final_review`, для финала `stage = null`. Ревью этапа и финала подчиняются одинаковым правилам; финалы разных
версий плана — разные ключи и не объединяются.

**Счёт** `discardedRun(ключ)` — число подряд идущих **последних** ходов проверяющего этого ключа, отброшенных
`review.discarded`. Ходы берутся по порядку `turn.intent`; учитываются только ходы с `turn.finished`:
- `review.discarded` → +1;
- `review.assessed` → счёт обнуляется;
- ход с `turn.finished` без записи результата, **после которого уже есть** следующий `orch.turn` этого ключа, —
  дерево за этот ход не менялось (иначе до следующего хода был бы записан `review.discarded`, §3.10) → обнуляется.
  Так ошибка или невалидный отчёт при неизменном дереве прерывают последовательность, но успехом не считаются: их
  исход обрабатывается как сейчас (`pauseForOutcome`, `invalid_report`);
- последний ход ключа с `turn.finished` без записи результата разбирается **при каждом решении цикла** по текущему
  снимку (`nextAction` его уже получает): `orch.turn.tree` = текущему дереву → счёт обнуляется, как у разобранного
  хода; ≠ → сначала пишется `review.discarded` (+1), затем решение (в чистой функции цикла это отдельное действие
  вида `discard(turnId)`, как `checkpoint`, после которого решение вычисляется заново). Так одинаково работают обычный поток (ошибка или
  невалидный отчёт при неизменном дереве, пауза исхода, продолжение) и авария до записи результата. Правки
  пользователя в папке во время паузы засчитываются консервативно — как изменение дерева;
- ход без `turn.finished` (`outcome_unknown`) не меняет счёт.

**Что прерывает последовательность** (исчерпывающий список; всё, что в нём не названо, последовательность не
прерывает): `review.assessed` хода этого ключа; разобранный ход
этого ключа при неизменном дереве (выше); смена ключа — новая действующая версия плана (`plan.recorded`,
`plan.decided(accept)`), `stage.accepted` (следующий этап — другой ключ), переход от ревью этапов к финалу.
**Не прерывают**, в частности: открытие приложения и `run.recovered`, `run.status` pause/resume/step,
`clarification.added`, `limits.changed`, вопросы и ответы, `person.decided`, `recovery.decided`, `plan.proposed`,
`plan.decided(return)`, `check.*`, `prepare.*`, `checkpoint.created`, `workspace.*`, `finish.*`, записи и ходы других
ключей, голый `orch.turn` без `turn.intent`.

**Решение о следующем ходе проверяющего** для ключа:
- `discardedRun = 0` → ход;
- `discardedRun = 1` → ход (единственный автоматический повтор);
- `discardedRun ≥ 2` → ход, только если есть **неиспользованное разрешение** этого ключа; иначе пауза
  `tree_changed_during_review` без хода.

**Разрешение** на один ход ключа даёт одно из двух явных решений человека, других источников нет:
- переход `run.status(running)` командой resume или step, когда запуск стоял на паузе `tree_changed_during_review`;
- `recovery.decided` с `retry_turn` или `reset_to_checkpoint` для хода проверяющего этого ключа с неизвестным исходом
  (ниже).

Оба используются одинаково. Первое при воспроизведении видно по состоянию до записи (`pausedReason`), новая запись не
нужна; второе — сама запись `recovery.decided`. Для первого причина входит в `RESUMABLE` (`svc`, команды resume/step, `svc:1451-1455`). Разрешение привязано к ключу (последнего отброшенного хода или хода с неизвестным исходом) и **используется** первым `turn.intent` хода
проверяющего этого ключа после него. Одно разрешение — ровно один ход; повторно его не использовать: использование
выводится из журнала. Смена ключа делает неиспользованное разрешение недействительным. Продолжение из других пауз
(`recovered`, `outcome_unknown`, `user_request`, `invalid_report` и т. д.) разрешением не является.

**Переход «пауза → решение → ход → результат»:**
1. Два подряд отброшенных ревью ключа → пауза `tree_changed_during_review`.
2. «Продолжить с изменениями» → `run.status(running)` = разрешение.
3. Ровно один новый ход проверяющего на текущем дереве (его `turn.intent` использует разрешение).
4. Результат:
   - дерево снова изменилось → `review.discarded`, `discardedRun ≥ 3`, разрешение использовано → снова пауза, без
     автоматического повтора;
   - дерево не изменилось → обычная обработка: `review.assessed` при валидном отчёте; при ошибке хода или
     невалидном отчёте — пауза этого исхода, как сейчас (успехом не считается); последовательность прервана.

**Перезапуск** нового хода не разрешает. `run.recovered` заменяет причину паузы на `recovered`/`outcome_unknown`
(`journal.ts:528`); продолжение из неё — не разрешение. Если на момент аварии было `discardedRun ≥ 2` и не было
неиспользованного разрешения, после продолжения цикл снова вычисляет паузу `tree_changed_during_review` без хода. Уже
выданное и не использованное разрешение перезапуск сохраняет: оно выводится из журнала (первая строка таблицы ниже), и
после продолжения выполняется ровно один ход.

**Восстановление на границах** (всё выводится из журнала):

| Граница аварии | Что в журнале | После перезапуска и продолжения |
|---|---|---|
| разрешение записано, намерение хода нет | `run.status(running)` из паузы, нет `turn.intent` ключа после него (голый `orch.turn` без `turn.intent` допустим: процесс запускается только после `turn.intent`) | разрешение не использовано и не потеряно → ровно один ход |
| намерение записано, старт не подтверждён | `turn.intent` без `turn.finished` | как сейчас: `outcome_unknown`, автоматического повтора нет; разрешение **использовано**. Дальше — решение человека `recover` (ниже) |
| ход начался, результат неизвестен | то же, что предыдущая строка (записи о старте нет) | то же |
| результат записан, следующая пауза нет | `turn.finished` и `review.discarded` разрешённого хода | `discardedRun ≥ 3`, разрешение использовано → пауза без хода |
| результат записан, дерево ещё не сравнивалось | `turn.finished` без записи результата | при решении цикла сравнение `orch.turn.tree` с текущим: изменилось → `review.discarded` → пауза без хода; не изменилось → счёт обнулён, обычная обработка (для валидного отчёта без `review.assessed` — повтор ревью по §3.10) |

**Неизвестный исход разрешённого хода.** Он не повторяется автоматически. Решения `recover`
(`recovery.decided`, существующий механизм): `retry_turn` (и `reset_to_checkpoint` в нативной «отдельной копии») —
второй источник разрешения (см. «Разрешение»): ровно один новый ход проверяющего этого ключа, используется его
`turn.intent`, счёт при этом не сбрасывается. `recover` переводит запуск в `paused(user_request)` (`svc:1500`), и
разрешение переживает продолжение из этой паузы; `accept` — ход остаётся без результата, следующий ход — по общим правилам (при
`discardedRun ≥ 2` — пауза без хода). Восстановление остальных команд не расширяется.

### 3.2. Пакет ревью

Задание проверяющему строит приложение. Входит:
- требования `R` и условия этапа (для финала — все условия) с текущим статусом доказательств;
- списки изменённых путей: `diffTreeNames(начало этапа → снимок)` и `diffTreeNames(baseline → снимок)` (для условий,
  перенесённых `keep`, и для финала), с признаком усечения. Патчи не входят: проверяющий читает файлы в папке сам;
- результаты проверок на текущем `checkKey` (`checkLines`);
- замечания запуска с id, текстом, путями, статусом, доказательствами, `runKey` открытия и закрытия; для закрытых —
  менялись ли их пути после закрытия;
- решения человека.

Не входит: переписка исполнителя, его отчёт `summary`, задания исполнителю, переписка лида.

### 3.3. Решение о приёмке этапа (приложение, по фактам)

Вердикта «принять / исправить» у проверяющего нет: приложение решает само.
- Условие `change` выполнено, только если проверяющий отметил его `met` и все `paths` входят в
  `diffTreeNames(baseline → снимок ревью)`. Иначе отчёт — `invalid_report`. Пустой `paths` для `met` недопустим.
  База — `baseline`, а не начало этапа: условие, перенесённое `keep`, могло быть выполнено раньше. **Это ограничитель,
  а не доказательство:** под него подходит любая правка, даже пробельная. Доказательство — суждение независимого
  проверяющего плюс то, что он сослался на реально изменённые файлы (принцип 2 выполняется частично; см. §8).
- Этап принят, только если одновременно:
  1. все обязательные проверки `passed` на текущем `checkKey`;
  2. каждое условие этапа выполнено (`check` — выводится на текущем `checkKey`; `change` — в `applied.conditionsMet`
     действующего `review.assessed` на текущем `runKey`; `person` — действующее `person.decided` по §3.5) либо снято
     решением человека;
  3. нет открытых `blocking`, привязанных к этому этапу (§3.4), и нет спорных пунктов, ждущих решения;
  4. отчёт проверяющего свежий (тот же `runKey` и `clarificationVersion`), применён целиком (§3.10) и
     `request = "none"`.
- Иначе, если есть спорный пункт — сначала пауза `awaiting_person_decision`, и только после решения — дальше по этому
  правилу. Если `request = "none"`: этап возвращается исполнителю с невыполненными условиями и открытыми `blocking`.
  `request = "replan"` → ход плана; `"question"` → вопрос человеку, как сейчас.
- **Прогресс и петли** (`progress.ts`): ключ раунда — множество id открытых `blocking` и невыполненных условий;
  прогресс — закрытие хотя бы одного id. Лимиты `roundsPerStage` и `noProgressRounds` работают как сейчас.

### 3.4. Замечания

- `wish` не блокирует этап и не уходит исполнителю автоматически; в итоге — отдельным списком.
- `blocking` закрывается:
  - проверяющим — только на `runKey`, отличном от `runKey` открытия, с **непустым** `paths`, и если каждый путь из
    `paths` входит в `diffTreeNames(снимок открытия → текущий снимок)`. Пустой `paths` или путь вне этого diff →
    `invalid_report` для всего отчёта **до** его применения: `review.assessed` не пишется, `F` остаётся открытым,
    этап не принимается. Это ограничитель, а не доказательство исправления: непустой diff лишь не даёт закрыть
    замечание без изменений в названных файлах; оценку «исправлено» даёт проверяющий;
  - или решением человека (`person.decided` / `plan.decided`) — отдельный механизм, ограничение на пути к нему не
    относится.
- Понижение `blocking → wish` — только решением человека.
- **Повторное открытие закрытого `F` по id** принимается, только если `runKey` отличается от `runKey` закрытия и
  хотя бы один путь **из `paths` самого `F` на момент закрытия** изменён после закрытия. Пути, добавленные в новом
  отчёте, не считаются. Иначе — `refused` (`same_run_key` / `no_new_evidence`).

**Повтор или новый дефект.** Совпадение путей — только **признак возможного повтора**, не основание для отклонения.
Приложение не определяет тождество дефектов: ни сравнение текста, ни оценка модели этого не гарантируют. Правило:
1. Новое `blocking` (`id: null`) — **возможный повтор** закрытого `F`, если их `paths` пересекаются и общие пути не
   менялись после закрытия `F`. Замечания того же отчёта, который закрыл `F`, возможными повторами не считаются.
2. Пакет ревью показывает закрытые замечания с путями и признаком «пути менялись после закрытия», поэтому проверяющий
   для возможного повтора обязан указать `relation` к одному из кандидатов (закрытых `F`, с которыми есть пересечение):
   - `{"repeatOf": "F1"}` — это тот же дефект: применяется правило повторного открытия по id; без новых изменений —
     `refused` (`declared_repeat`);
   - `{"distinctFrom": "F1", "why": "…"}` — другой дефект: открывается новый `F` с пометкой `possibleRepeatOf: F1`,
     видимой в итоге и в задании исполнителю. `why` 1–500 символов и должно называть отличие (другая функция,
     другое поведение); приложение проверяет только наличие, не истинность.
3. **Неопределённость** — `relation` отсутствует или указывает не на кандидата, либо **хотя бы у одного** кандидата
   лимит (п.4) исчерпан (при любом `relation`: иначе лимит обходится добавлением пути другого закрытого `F`), →
   пункт спорный (`applied.disputed` с кандидатами): пауза
   `awaiting_person_decision` с текстами обоих замечаний и путями; человек выбирает «новый дефект» (открыть новый `F`)
   или «повтор `F1`» (правило повторного открытия; без новых изменений — отклонено). Остальная часть отчёта
   применяется.
4. **Защита от бесконечного возврата.** Для закрытого `F` на неизменённых путях автоматически принимается не более
   одного `distinctFrom`. Следующий возможный повтор того же `F` на тех же неизменённых путях — `disputed` независимо
   от `relation`: дальше решает человек. Решение человека не распространяется на следующие пункты: каждый следующий
   возможный повтор того же `F` снова спорный, а пакет ревью и вопрос показывают прошлые решения по нему. Так новый
   дефект не теряется молча, а возврат одного замечания не идёт без участия человека.
5. Честное новое замечание в том же файле, найденное позже, проходит через п.2 (`distinctFrom`) без участия человека,
   если это первое такое замечание к закрытому `F`.

**Привязка к этапу.** В ревью этапа `condition` замечания может ссылаться только на условие этого этапа; ссылка на
другое условие → замечание привязывается к текущему этапу без условия. Правила владельца, по старшинству:
1. замечание с `condition` принадлежит этапу, где это условие в действующем плане (переходит с `keep`); если условие
   принадлежит принятому этапу (после финального ревью), замечание ждёт следующего плана, где условие вернётся в
   непринятые по §3.8 и получит этап;
2. замечание без условия принадлежит этапу, на котором открыто; если этот этап заменён перепланированием или это
   финальное ревью (`stage: null`), — первому непринятому этапу следующего действующего плана. Судьба замечаний
снимаемого условия — только по решению человека (§3.6). **Инвариант:** у каждого открытого `blocking` в действующем
плане есть непринятый этап-владелец, либо следующее действие запуска — ход плана или решение человека; замечания, которое блокирует финал, но не
попадает исполнителю, не бывает.

### 3.5. Решения человека

Условие `person`, спорное замечание, закрытие и понижение замечания решаются **командой**, а не свободным ответом:
пауза `awaiting_person_decision` с кнопками; команда пишет `person.decided`. Решения по плану — §3.6. Вопрос агента
(`question.asked`) остаётся для пояснений.
- **Когда спрашивать** про условие `person`: только когда остальные условия приёмки этапа (§3.3 п.1–4) выполнены на
  текущем `runKey`, чтобы решение принималось о готовой работе.
- **Сколько действует:** до следующего хода исполнителя на этом этапе; для принятого этапа — до восстановления ниже
  его checkpoint (§3.7). После этого — спросить снова.
- **Команды** идут по общему протоколу (`stage-5-contract.md` §6): `command.received` → запись решения →
  `command.completed`. Повтор с тем же `commandId` возвращает записанный результат без повторного действия. Если после
  аварии есть `command.received` без `command.completed`, при открытии запуска v2 приложение ищет запись решения с
  тем же `commandId` (`plan.decided`, `person.decided`, а также существующие `question.answered`,
  `clarification.added`, `limits.changed`, `recovery.decided`): найдена — пишется `command.completed(accepted)`, нет —
  `command.completed(rejected, "interrupted")`, и человек повторяет решение новой командой. **Это изменение
  `openRun` только для запусков v2:** сейчас он отклоняет все незавершённые команды как `interrupted`
  (`svc:345-346`, `journal.ts:528`, `stage-5-contract.md` §12), и для v1 так остаётся.
  Ограничения: команды, чья запись не несёт `commandId` (pause, resume, stop пишут `run.status`, `journal.ts:338`),
  по-прежнему получают `interrupted`, даже если применены; `recover` пишет `recovery.decided` на каждый ход
  `outcome_unknown` (`svc:1490`), поэтому `accepted` — только если решение записано для всех таких ходов, иначе
  `interrupted`. Решение, уже не относящееся к текущему
  состоянию (например, предложение уже решено), — `rejected(invalid_state)`.

### 3.6. Перепланирование не ослабляет требования

Порядок для плана лида (проверка — §2.3):
1. **Случайная потеря** (непринятое условие не упомянуто, `R` без покрытия и без `dropRequirements`, ссылка на
   несуществующее условие) → `invalid_report`; действующий план не меняется.
2. **Явное предложение** (`dropped` или `dropRequirements` непусты) → `plan.proposed`, пауза `coverage_lost`.
   Действующий план **не заменяется**. Пока предложение ждёт, ходов и проверок нет; допустимы только команды
   `plan.decided` и Stop. Эта пауза проверяется в цикле раньше любых поводов для хода плана.
3. **Решение человека** — одна команда на всё предложение, `plan.decided`:
   - `accept`: перед записью приложение **заново проверяет** предложение против текущего состояния (снятые раньше
     требования, принятые этапы, открытые замечания, полнота `choices`). При разрешённых на паузе командах состояние
     меняться не должно, поэтому проверка защитная (журнал, изменённый вне приложения, повреждённый текст); не
     прошло — команда `rejected(invalid_state)`, предложение ждёт дальше. Прошло — запись `plan.decided(accept)` **одна** применяет всё: предложенный план становится действующим
     (версия = прежняя + 1), условия из `dropped` и требования из `dropRequirements` сняты, замечания обработаны по
     `choices`;
   - `return`: действующий план сохраняется; ход плана с этим решением. Такой ход плана **не расходует** `replans`.
     Цепочка «предложение → вернуть» ограничена только лимитом `turns`: каждое звено запускает человек.
   `replans` считается по действующим версиям плана (`planVersion`, `cycle.ts:132`): предложения и возвраты версию не
   дают, поэтому лимит не расходуют.
   Частичного принятия нет: чтобы снять часть условий, человек возвращает план лиду с пояснением — необязательный
   текст `note` в той же записи `plan.decided(return)`; следующий ход плана получает его вместе с решением. При
   `accept` `note` = `null`. `note` — не `clarification.added`: `clarificationVersion` и свежесть отчётов он не меняет.
4. **Замечания снимаемого условия.** Снятие условия само по себе замечание не закрывает. Для каждого открытого
   `blocking`, привязанного к условию из `dropped`, `choices` обязан содержать один выбор:
   - `move` — замечание переходит к указанному условию или этапу нового плана (только непринятому) и уходит его
     исполнителю;
   - `close` — закрыть решением человека (в итоге — «закрыто человеком при снятии C4»);
   - `to_wish` — понизить до пожелания.
   В новом плане всегда есть непринятый этап (`stageCount ≥ 1`, `journal.ts:401`), поэтому `move` доступен всегда. Кнопка «Принять» недоступна, пока выбор не сделан для
   каждого такого замечания; команда без полного `choices` → `rejected(invalid_command)`. `wish`, привязанные к
   снимаемому условию, остаются пожеланиями без условия.
5. **Интерфейс до подтверждения** показывает для каждого снимаемого условия и требования: текст, `covers`, причину от
   лида, какие требования остаются без покрытия и снимаются вместе с ним, какие открытые замечания затронуты и что с
   каждым будет по текущему выбору, и что действующий план останется в силе при «Вернуть лиду».
6. **Поводы для хода плана в v2:** нет действующего плана; `request = "replan"`; отказ финала (§3.8);
   `plan.decided(return)`; предыдущий ход плана отклонён `invalid_report` (после решения человека продолжить).
7. **Перезапуск.** Ожидающее предложение выводится из журнала (`plan.proposed` без `plan.decided`): после перезапуска
   запуск снова стоит на `coverage_lost` с тем же предложением.
- Ослабления условия под тем же id не бывает: текст, `covers` и `evidence` условия неизменны; замена — только
  `dropped` + новое условие.
- Снятое требование обратно не возвращается (вне этапа, §8).

### 3.7. Свежесть доказательств между этапами

- Доказательство `change` принятого этапа действует, пока пути из его `paths` не менялись после checkpoint
  этого этапа: `diffTreeNames(checkpoint этапа → текущий снимок)` не пересекается с `paths`. Пересечение делает
  условие «требует подтверждения» — оно включается в финальное ревью.
- Только в нативной «отдельной копии» (в папке проекта и worktree восстановления нет): восстановление ниже checkpoint этапа
  (`workspace.restored`) делает условия этого и следующих этапов невыполненными:
  их нужно выполнить заново, а не подтвердить. Этапы остаются принятыми в журнале (`journal.ts:583`), но финал
  (§3.8) их не засчитывает и ведёт к ходу плана.
- Решения человека по условиям `person` живут по §3.5.
- База путей для финального подтверждения — `diffTreeNames(baseline → финальный снимок)`.

### 3.8. Финал

Запуск `completed`, только если:
- все этапы приняты по §3.3, условия действительны по §3.7 (или подтверждены финальным ревью);
- обязательные проверки `passed` на финальном `checkKey`;
- каждое `R` снято решением человека **или** одновременно покрыто выполненными условиями и имеет `met` в
  `requirements` свежего финального отчёта проверяющего;
- нет открытых `blocking`, `disputed` и ожидающих предложений плана;
- финальный отчёт свежий, применён целиком (§3.10) и `request = "none"`.

**Спорный пункт финального отчёта — первым.** Если в `applied` финального отчёта есть неразрешённый спорный пункт
(§3.4), запуск сначала встаёт на `awaiting_person_decision`: пока решения нет, финал не принимается и ход плана не
начинается. После решения приложение оценивает финал заново:
- «новый дефект» → открыт `blocking` → отказ финала, ход плана исправлений (ниже);
- «повтор» → правило повторного открытия по id (§3.4): открыт — отказ финала; отклонён — пункт ничего не блокирует,
  и если остальные условия финала выполнены, запуск завершается без лишнего плана;
- если за время ожидания отчёт стал несвежим (другой `runKey` или `clarificationVersion`), завершить по нему нельзя:
  нужен новый `final_review` (несвежесть — не отказ финала, правило `planVersion` ниже к ней не относится).

Иначе — не успех: требование без доказательства даёт «не завершено». **Любой отказ финала** (после разрешения
спорных пунктов) при свежем отчёте с `request = "none"` (требование `not_met`, открытое `blocking`, условие без действующего доказательства или
неподтверждённое по §3.7) ведёт к ходу плана с перечнем причин. Повторный `final_review` допускается только после
нового плана (по `planVersion`, а не по `runKey`: этап исправлений может вернуть доказательство, не меняя дерева).
Число таких ходов ограничено `replans`.

**Возврат условий принятых этапов.** При отказе финала условия принятых этапов, которые недействительны (§3.7),
не подтверждены или связаны с `not_met`-требованием или открытым `blocking`, становятся **непринятыми**: следующий
план обязан перечислить их в `keep` или `dropped` (§2.3), а этап, где они выполнены заново, возвращает им
доказательство. Сами принятые этапы и их checkpoint в журнале не меняются; меняется только статус условий.

### 3.9. Лимиты

Ход проверяющего считается в `turns`. Раунд — ход исполнителя и ревью. `budgetLine` описывает раунд как «ход
исполнителя и ход проверяющего». Новые лимиты не вводятся.

### 3.10. Применение результата ревью и восстановление

Механизм — одна запись на результат, в духе существующего журнала: строка пишется целиком, тексты адресуются хешем и
проверяются при чтении (`readTextFile`: `text_missing` / `text_corrupt`).

**Оборванная последняя строка.** Сейчас `openRun` без опции отказывает `journal_torn_tail` (`store.ts:747`), и
автоматически это не делается (TROUBLESHOOTING T39). Для запусков v2 `openRun` принимает оборванный хвост сам:
байты уходят в `quarantine/`, журнал усекается, пишется `journal.tail_repaired` — то же, что `acceptTornTail: true`.
Основание то же, что в T39: неподтверждённая запись ничего не запускала. Для v1 поведение не меняется; T39 уточняется
при реализации A2.

**Запись.** После хода проверяющего приложение:
1. строит `applied` из отчёта и состояния **до** записи: присваивает номера `F` подряд от `nextFinding` состояния,
   проверяет пути по diff, решает повторы (§3.4);
2. пишет текст `applied` в `texts/` (отчёт уже лежит там как `turn.finished.report`);
3. пишет **одну** запись `review.assessed` со ссылками на оба текста.

**Когда результат применён полностью.** Только когда в журнале есть целая запись `review.assessed` для этого хода.
Все эффекты ревью (выполненные условия, открытые, закрытые, отклонённые, спорные замечания, номера) выводятся из её
`applied`; отдельных записей эффектов нет, поэтому «условия подтверждены, а замечание из того же отчёта потеряно»
невозможно.

**Проверки при воспроизведении** (нарушение → `replay_conflict`, запуск нельзя продолжить, этап не принимается и запуск
не завершается):
- `review.assessed`: ход `turnId` — завершённый (`completed`, отчёт сохранён) ход проверяющего нужной цели и
  **последний** `orch.turn` журнала;
- `review.discarded`: ход проверяющего с `turn.finished` любого исхода, последний `orch.turn` журнала;
- вторая `review.assessed`/`review.discarded` для того же хода — конфликт;
- `review.assessed.report` совпадает с `turn.finished.report.ref` этого хода, `applied.report` — с ним же;
- номера в `applied.opened` идут подряд с `nextFinding` состояния, ни один не встречался раньше; `closed`, `reopened`,
  `refused`, `unchanged` и кандидаты `disputed` ссылаются на существующие `F`; каждый `index` отчёта учтён ровно один
  раз; номер в `person.decided(disputed, new)` равен `nextFinding` на момент записи.

**Два этапа разбора.** Первый — как сейчас: `parseJournal`/`applyRecord` только по записям (порядок, ссылки на ходы,
одна запись результата на ход, версии планов). Второй — вывод по текстам: номера `F` и `C`, группы `applied`, владельцы
замечаний, условия планов; его выполняют сервис при открытии запуска и `readRun`/`manager.snapshot()` для показа.
Проверки, требующие текстов (номера подряд, каждый `index` учтён, `conditionsAssigned` = число новых условий в тексте
плана, номер нового `F` в `person.decided`), — во втором этапе. Их нарушение: `readRun`/`snapshot()` возвращают
`integrity: "corrupt"` с `detail.phase: "texts"` и валидным префиксом; `openRun` проходит (первый этап цел), но
сервис отказывает в продолжении с той же причиной — запуск только для чтения.

Отсутствующий или повреждённый текст (`text_missing`/`text_corrupt`): первый этап проходит, запуск виден в списке и
истории, но состояние условий и замечаний не выводится — итог показывает «результаты ревью недоступны: повреждён текст»,
продолжение запрещено, этап не принимается, запуск не завершается.

| `review.discarded`, нет нового хода и паузы | не применён, решение записано | по §3.1.1 из журнала: `discardedRun = 1` — один новый ход; `discardedRun ≥ 2` без неиспользованного разрешения — пауза `tree_changed_during_review` без хода; с разрешением — ровно один ход. Перезапуск счёт не сбрасывает и разрешения не даёт |

Новый ход проверяющего делает запись для прежнего хода невозможной: она разрешена только для последнего `orch.turn`.

Повторная авария во время восстановления попадает в одну из строк той же таблицы: каждое действие восстановления —
одна запись или ни одной, до неё состояние то же, после — уже следующее. Повторных эффектов нет: эффекты существуют только в одной
записи, а повторная запись для того же хода — конфликт. Номера не присваиваются дважды: они фиксируются только
записью `review.assessed`, а следующий номер берётся из состояния, выведенного из журнала.

Те же правила — для `plan.proposed`, `plan.decided` и `person.decided`: каждое — одна запись; команды — по §3.5.

## 4. Интерфейс

- **Итог запуска v2.** Таблица требований: `R`, текст, условия с id, доказательство каждого (проверка и её результат;
  пути изменений и ревью; решение человека), статус «выполнено / не выполнено / снято решением человека». Под ней —
  открытые `blocking`, закрытые (с доказательством или «закрыто человеком»), пожелания, отклонённые повторы, новые
  замечания с пометкой «возможный повтор `F1`».
- **Решения человека:** спорное замечание (оба текста и пути, кнопки «новый дефект» / «повтор»); предложение плана
  (§3.6 п.5, кнопки «Принять» / «Вернуть лиду», выбор для каждого затронутого замечания).
- **Панель запуска.** Участник «Проверяющий» (вкладка роли, строка состояния); карточки на холсте нет — это сессия
  CLI лида.
- **Renderer:** `runStatus.ts` и `runModel.ts` читают `review.assessed` (с текстом `applied`), `plan.proposed`,
  `plan.decided` и `person.decided` для v2; для v1 — как сейчас (`review.recorded`, критерии списком). Новые причины
  паузы — в `NEEDS_DECISION` (`runModel.ts:303`), не в `STOP_ONLY`; тексты ru/en без старого имени продукта
  (`tests/rename-identity.test.mjs`).

## 7. Критерии приёмки

Локально, на поддельных CLI (`tests/fixtures/orchestration/mock-*.mjs`) и временном профиле:

1. **Невыполненное условие не принимает этап:** проверки прошли, проверяющий не отметил условие `change` → этап
   уходит исполнителю с этим условием; `stage.accepted` нет.
2. **Путь вне diff:** `met` условия с путём, не изменённым с `baseline`, → `invalid_report`, условие не выполнено.
3. **Закрытое замечание не возвращается без нового доказательства:** `F1` закрыто на `runKey` K; повтор по id на K →
   `refused`; на K′, где изменён путь из `paths` `F1`, — открывается; на K′, где изменён только путь, добавленный в
   новом отчёте, — `refused`.
4. **Закрытие без изменения:** закрыть `blocking` на том же `runKey`, что открытие, нельзя.
5. **Пожелание не держит этап:** единственное открытое — `wish` → этап принят. Отчёт с `F5` (`wish`) как `blocking`
   по id → `invalid_report`; открытое `F5`, повторённое по id без изменений, → `unchanged`.
6. **Замечания своего этапа:** исполнитель этапа 2 получает открытые `blocking` этапа 2, а не замечания ревью другого
   этапа или перепланирования. Ревью этапа 2 открывает `blocking` с `condition: C1` принятого этапа 1 → замечание
   принадлежит этапу 2 без условия, этап 2 без его закрытия не принимается. Условие `C2` перенесено `keep` в этап 4,
   первый непринятый — 3 → замечание `C2` принадлежит этапу 4.
7. **Проверяющий не видит переписку исполнителя:** задание проверяющего не содержит `summary` исполнителя, его
   задания и маркеров из его ответов; `sessionId` проверяющего новый на каждом ревью.
8. **Повтор и новый дефект в одном файле** (замечание 1 внешнего ревью):
   - a. `F1` в `service.ts` закрыто; следующее ревью на неизменённом `service.ts` приносит новое `blocking` с
     `distinctFrom: F1` и отличием → открыто `F2` с пометкой `possibleRepeatOf: F1`, этап ждёт его исправления;
   - b. то же с `repeatOf: F1` → `refused` (`declared_repeat`), нового `F` нет;
   - c. то же без `relation` → спорный пункт, пауза `awaiting_person_decision` до возврата исполнителю; «новый
     дефект» → открыт `F` с номером `nextFinding`; «повтор» → отклонено; остальные замечания того отчёта применены
     сразу; два спорных пункта одного отчёта против `F1` решаются по отдельности (`target = {reviewTurnId, index}`);
   - d. после `F2` (distinctFrom) третье возможное повторение `F1` на тех же неизменённых путях → спорный пункт даже с
     `distinctFrom`; после решения «повтор» следующее возможное повторение снова спорное, прошлое решение видно;
   - d2. новое `blocking` пересекается с закрытыми `F1` (лимит исчерпан) и `F9`: `distinctFrom: F1` или
     `distinctFrom: F9` → спорный пункт с кандидатами `F1`, `F9`; решение «повтор» указывает выбранного кандидата;
   - e. после правки `service.ts` новое замечание к тем же путям не считается возможным повтором `F1`;
   - f. новый дефект в том же файле в отчёте, закрывшем `F1`, → открыт без пометки.
9. **Покрытие одной проверкой не даёт успеха:** все `R` покрыты одним `check`-условием, проверки прошли, финальный
   проверяющий отметил `R1` `not_met` → не `completed`, ход плана.
10. **Свежесть:** этап 2 меняет путь из доказательства этапа 1 → условие этапа 1 требует подтверждения в финале.
11. **Дерево во время ревью:** одно изменение → `review.discarded`, один повтор ревью; повторное →
    `tree_changed_during_review`, не `STOP_ONLY`; то же после SIGKILL main между ними. Авария после хода,
    изменившего дерево, до записи результата → при решении цикла (§3.1.1) `review.discarded` по `orch.turn.tree`, счёт
    тот же, что без аварии. Ход с исходом `failed`/`timeout`, изменивший дерево, → `review.discarded` без
    `replay_conflict`. На паузе только «продолжить с
    изменениями» и Stop. Ход с `invalid_report`, изменивший дерево, → `review.discarded`; ход с `invalid_report` без
    изменения дерева прерывает последовательность (счёт обнуляется).
11e. **Закрытие `blocking` без путей:** `F1` открыт на K; изменён посторонний файл → K′; отчёт закрывает `F1` с
    `paths: []` → `invalid_report`, `review.assessed` не записан, `F1` открыт, этап не принят. То же с непустым `paths`,
    где путь не входит в `diffTreeNames(снимок открытия → K′)`. Закрытие с непустым `paths` из этого diff —
    принимается. Закрытие человеком без путей — принимается.
11f. **Спорный пункт в финале:** финальный отчёт без других отказов содержит спорный пункт → пауза
    `awaiting_person_decision`, хода плана нет, запуск не завершён; «повтор» (отклонён) → `completed` без хода плана;
    «новый дефект» → ход плана исправлений; дерево изменилось во время ожидания → после решения новый
    `final_review`, завершения по старому отчёту нет.
11g. **Выход из паузы `tree_changed_during_review`** (§3.1.1):
    - a. два изменения дерева → пауза → «Продолжить с изменениями» → ровно один новый ход проверяющего, без паузы
      перед ним;
    - b. разрешённый ход снова изменил дерево → `review.discarded` → пауза, без автоматического повтора;
    - c. разрешённый ход не изменил дерево, отчёт валиден → `review.assessed`, последовательность прервана; отчёт
      невалиден или ход с ошибкой → пауза этого исхода, не успех; после продолжения из неё при неизменном дереве —
      обычный ход без паузы `tree_changed_during_review`; если пользователь во время паузы изменил папку →
      `review.discarded` и пауза `tree_changed_during_review` (консервативно);
    - d. перезапуск на паузе → после открытия и продолжения из `recovered` новых ходов нет, снова пауза
      `tree_changed_during_review`;
    - e. аварии на границах: после разрешения до `turn.intent` → после продолжения ровно один ход; после
      `turn.intent` до `turn.finished` → `outcome_unknown`, автоматического хода нет, разрешение использовано,
      `recover retry_turn` → ровно один ход; после `review.discarded` разрешённого хода до паузы → пауза без хода;
      после `turn.finished` валидного отчёта до `review.assessed` при неизменном дереве → повтор ревью без паузы
      `tree_changed_during_review`; после `recover retry_turn` → `paused(user_request)` → resume → ровно один ход;
      ни в одном случае не два хода на одно разрешение;
    - f. одинаковые правила для ревью этапа и финала (`stage: null`); два отброшенных финала версии плана 2 не
      влияют на счёт финала версии 3; `stage.accepted` и новая действующая версия плана прерывают
      последовательность, а `run.recovered`, pause/resume, `clarification.added` — нет.
12. **Отказ финала:** финальный отчёт открывает `blocking` → ход плана с перечнем, повторного `final_review` на том
    же `planVersion` нет; после нового плана без изменения дерева финал проходит заново. Сквозные случаи:
    - папка проекта: финал отмечает `R1` `not_met` → план с `keep` условий этапа 1 → этап исправлений → `completed`;
    - нативная «отдельная копия»: восстановление (`recover` → `reset_to_checkpoint` после `outcome_unknown`) ниже
      checkpoint этапа 1 → финал отказывает → план с `keep` условий этапа 1 →
      этап исправлений → `completed`.
13. **Порядок перепланирования** (замечание 4):
    - a. план теряет покрытие `R2` без `dropRequirements` → `invalid_report`, действующий план прежний; следующий ход
      плана (в том числе после перезапуска) получает перечень нарушений;
    - b. непринятое условие не упомянуто → `invalid_report`;
    - c. план с `dropped: C4` → `plan.proposed`, пауза `coverage_lost`, действующий план и его этапы прежние, ходов

    - d. «Принять» → одна запись `plan.decided(accept)`: новый план действует, `C4` снято, в итоге «снято решением

## 9. Выбранные направления контракта

Выбраны пользователем 2026-09-30 как направление контракта. Это не приёмка этапа A и не разрешение его реализации.

1. Новая сессия проверяющего на каждое ревью (§3.1).
2. Отчёт и переписка исполнителя не входят в пакет ревью (§3.2).
3. Мост A0 выпускается до первой сборки, создающей запуски v2 (§2.2, §5).
4. При изменении дерева во время ревью — один повтор, затем пауза (§3.1).
