## 1. Сценарии

1. **Разбить работу на задачи.** В пространстве проекта человек записывает несколько задач: заголовок, текст, требования (как в цели), необязательно — от каких задач она зависит. Задачи стоят в колонке «Очередь». Агенты пока не работают.
2. **Запустить задачу.** «Запустить» на задаче выбирает связь пространства, у лида которой та же папка (сравнение по realpath, как в `requestIdentity`):
   - одна связь — она;
   - несколько — выбор в диалоге;
   - ни одной — предложение создать связь.

   Затем открывается диалог цели этой связи. Текст и требования уже заполнены из задачи; права, режим, проверки — из настроек проекта, как сейчас. Запуск идёт по обычному циклу этапа A. Задача сама переходит в «Работу», потом в «Проверку». В «Готово» она попадает, только когда приложение разрешило завершение (`completion` → `confirmed`).
3. **Увидеть, почему стоит.** Задача, которая не идёт, называет причину одной строкой:
   - ждёт задачу T-3;
   - ждёт ответа на вопрос лида;
   - ждёт разрешения: `curl …`;
   - ждёт решения о командах проверки;
   - лимит раундов исчерпан;
   - последний запуск остановлен.
   Эту же причину показывают карточка агента, виджет активности и итог, потому что источник один.
4. **Повторить.** Запуск остановлен (`stopped`) или упал (`failed`) — задача возвращается в «Очередь» с причиной и числом попыток. «Запустить снова» создаёт новый запуск той же задачи. Старые запуски остаются в истории задачи. Исчерпанный лимит — это пауза (`paused(limit_reached)`): запуск держит связь и папку. Поэтому повтор — либо «Поднять лимит» в панели запуска, либо сначала «Стоп», потом «Запустить снова».
5. **Автопилот доски.** Человек включает «Вести доску» на связи. Когда задача становится «Готово», приложение само запускает следующую готовую к работе задачу этого пространства на той же связи. Автопилот останавливается и объясняет причину, если:
   - нужен человек;
   - задача кончилась не успехом;
   - исчерпан бюджет доски.
6. **Перезапуск приложения.** После перезапуска доска показывает те же колонки и причины, что и до него. Сама она ничего не продолжает: незавершённый запуск ведёт себя по правилам восстановления (`paused(recovered)` / `outcome_unknown`).
7. **Откат на 1.5.12/1.5.13 и обратно.** Старая сборка доски не видит, её запуски — обычные запуски связи. После возврата доска цела. Запуски, созданные старой сборкой, показаны в разделе «Без задачи».

Вне B (это этап C): несколько исполнителей одновременно, объединение результатов, задачи в разных worktree параллельно.

## 2. Модель данных

### 2.1. Что хранится

Хранится только то, что задал человек. **Статус не хранится** (принцип 8 цикла: доска и оркестрация не могут разойтись).

```
Task {
  id: uuid                   // постоянный
  key: "T-<n>"               // номер в пространстве для людей; n не переиспользуется
  workspaceId: string        // владелец, как у запусков (workspaces-spec §2); не переезжает вслед за карточками
  project: realpath          // папка проекта; задача запускается только связью с этой папкой
  title: 1..200
  text: 1..8000              // становится goal.text
  criteria: 1..32 × 1..500   // становятся goal.criteria → требования R<n> (journal-v2 §2.3)
  dependsOn: uuid[]          // задачи того же пространства; без циклов
  order: number              // место в колонке «Очередь» (ручная сортировка)
  createdAt, updatedAt
  archivedAt: string | null  // архив вместо удаления, пока у задачи есть запуски
  accepted: { runId: uuid, at: string } | null   // «Принять результат» (решение 2)
}
```

`accepted` — решение человека о конкретном запуске, а не статус задачи. Оно действует, только пока проходят все
проверки по самому запуску:
- запуск `runId` — последний запуск задачи;
- он `completed` с `completion.kind = "no_checks"` по своему журналу.

Если хоть одно не так, запись игнорируется: новый запуск задачи, другой исход или правка файла. Поэтому правка
`board.json` может дать только «Готово (принято вами, без проверок)» и только для запуска, который действительно
завершился без проверок. Подтверждённое «Готово» по-прежнему получается одним путём, из журнала.

Набор полей `text` + `criteria` — тот же, что у цели. Поэтому задача не вводит второго языка требований: требования и условия этапа A работают внутри каждого запуска как сейчас.

### 2.2. Связь запуска с задачей

Ссылка хранится **в цели запуска**: `goal.task = { id, key }`. Цель лежит в `run.created` (TextRef под цепочкой хешей) и после создания не меняется. Свойства такой ссылки:
- её нельзя потерять или подменить, не сломав цепочку;
- она пишется той же атомарной записью, что и сам запуск: отдельного шага «привязать запуск» нет, а значит, нет и сбоя между шагами;
- список запусков задачи **выводится**: запуски пространства (владелец — `owners`), у которых `goal.task.id` совпадает с id задачи. Хранимого `task.runIds` нет.

`goal.task.key` нужен, если задача удалена из `board.json` или файл утерян. Такой запуск показан как «задача T-3 (удалена или утеряна)», а не «Без задачи».

### 2.3. Что выводится

`runStatus.ts` сейчас живёт в renderer, зависит от языка и от ленты активности (`viewCause(view, entries)`), а в `RunView` нет ни цели, ни времени создания. Поэтому в B1:
- main выводит из журнала для каждого запуска `RunTaskFacts { taskId, taskKey, createdAt, lastTurnPurpose, limit, taken }` (`taken` — из `taken.json` рабочей копии). Цель неизменна, так что факты кешируются по `runId` и не перечитываются на каждое событие;
- коды причин (без текста) переезжают из `runStatus` в `shared`; renderer только переводит их в слова;
- решения автопилота зависят только от снимков и фактов, никогда от ленты.

Чистая функция в `shared`:

```
taskStatus(task, runs: (RunView & RunTaskFacts)[], deps: Map<id, TaskStatus>) → {
  column: "queue" | "work" | "review" | "done",
  reason: null | Reason,          // §4.3
  attempts: number,               // запусков задачи
  current: runId | null,          // последний по created
  completion: "confirmed" | "no_checks" | null,
  done: "confirmed" | "accepted" | null   // «Готово» подтверждённое / принятое человеком без проверок
}
```

Она использует только снимки запусков с фактами и статусы задач-зависимостей. Зависимости считаются устойчиво к циклам (файл можно поправить руками): задача в цикле получает `waits_task` с пометкой «цикл». Доска, карточки агентов, виджет и итог вызывают её и `runStatus` с одними данными, поэтому одинаковые данные дают одинаковый показ (критерий B из цикла).

## 3. Хранение и совместимость

### 3.1. Файл

`<userData>/orchestration/board.json`, рядом с `canvas.json`:

```
{ v: 1, tasks: Task[], counters: { [workspaceId]: n } }
```

- Запись атомарная: tmp, затем rename. Одна очередь записи на файл, как у `canvasStore`.
- Повреждённый файл отодвигается (`.damaged-<uuid>`), доска пуста, появляется предупреждение. Запуски не затрагиваются: их связь с задачами живёт в целях.
- Счётчик `T-n` пространства при чтении — максимум из файла и наибольшего `goal.task.key` в целях запусков пространства. Так номер не повторится и после потери файла.
- Файл новой версии (`v > 1`) не трогается: доска только для чтения или недоступна, как `workspaces.json` (workspaces-spec §3 п. 2).

**Почему не `canvas.json`.** Сборка 1.5.12 читает `canvas.json` с выбором известных ключей и пишет обратно только их (`canvasStore.ts`: `parsed = { agents, links, owners, releasedNewerRuns }`, затем `JSON.stringify({ v: 1, ...next })`). Если положить задачи в `canvas.json`, после отката первое же перемещение карточки в старой сборке молча удалит доску. Отдельный файл старые сборки не читают и не пишут, поэтому при откате он цел.

**Почему не только журнал.** Задача существует до первого запуска и между запусками (сценарии 1, 4). Журнал принадлежит запуску.

### 3.2. Журнал

**Формат журнала не меняется: остаётся v2, без новых записей и без новых полей конверта.** Новое — только необязательный ключ `task` внутри текста цели. Это та же разрешённая форма расширения, что `models` (journal-v2 §1: «новые ключи цели живут только внутри текста цели»). Разбор по §2.2.1 п. 4:

| Читатель | Что видит | Верно? |
|---|---|---|
| 1.5.8–1.5.13 (v2 включён с 1.5.8) | цель читается без строгой схемы (`JSON.parse(...) as Goal`), `task` игнорируется; запуск показан и продолжается как обычный | да: ключ не влияет ни на один переход запуска, ход, проверку или завершение |
| 1.5.7 (A0) | журнал v2 — режим §2.2 («создан более новой версией»), как любой v2 | да, без изменений |
| ≤ 1.5.6 | `unsupported_version`, как для любого v2 | без изменений |

Поэтому `minReaderVersion` остаётся 2, записи `skippable` не нужны. В отличие от `models`, потеря `task` старой сборкой не меняет поведение запуска. Она меняет только принадлежность запуска к задаче, а это видит лишь новая сборка.

Ограничения:
- цель собирается заново из известных полей, поэтому `task` протягивается через три места, иначе ключ молча пропадёт:
  - `checkGoal` — только для v2, `{ id: uuid, key: /^T-\d{1,6}$/ }`, без лишних ключей, по образцу `checkModels`;
  - `resolveGoal` в `manager.ts`;
  - `requestIdentity`: идемпотентный повтор сравнивает не цель целиком, а хеш явного списка полей. `task` добавляется условно (`...(g.task ? { task: g.task } : {})`), чтобы ключи уже созданных запусков не изменились. Тест: тот же `requestId` с другой задачей → `request_conflict`;
- запуск v1 (structured-режимы) задачи не получает. Доска запускает только нативные цели.

### 3.3. Откат и порядок записи

| Действие | Что пишется | Сбой посередине |
|---|---|---|
| Создать / изменить задачу | `board.json` | файл прежний или новый целиком |
| Запустить задачу | только запуск (`canvas.json` резервирование + `owners`, журнал с `goal.task`) — как сейчас | запуска нет — задача в «Очереди»; запуск есть — задача в «Работе». Резервирование без журнала `read()` скрывает, как сейчас; повтор с тем же `requestId` идёт в идемпотентную ветку |
| Изменить задачу с запусками | `board.json`; уже созданные цели не меняются | следующий запуск возьмёт новый текст; старые запуски в истории задачи показывают свой текст |
| Удалить задачу | без запусков — удаляется; с запусками — только `archivedAt`. Пока по задаче идёт `create`, удаление отказывает. Перед удалением показываются зависимые задачи | — |

Откат:
- на 1.5.13 — доски нет, запуски задач показаны как обычные;
- обратно — доска как была.

Задачи — содержимое пространства: пространство с задачами не удаляется (дополнение к workspaces-spec §4, «Удаление», и M8).

Запуски, созданные старой сборкой, — «Без задачи». Их можно привязать к задаче только новым запуском: старую цель не переписываем.

## 4. Машина состояний

### 4.1. Состояние запуска → колонка задачи

Колонка определяется **последним** запуском задачи (`current`) и его снимком:

| Последний запуск | Колонка | Причина (§4.3) |
|---|---|---|
| нет запусков | «Очередь» | `waits_task` при незавершённых зависимостях, иначе `null` («можно запускать») |
| `preparing`, `running` с ходом исполнителя или плана | «Работа» | — |
| `running` с ходом проверяющего, проверкой или финальным ревью | «Проверка» | — |
| `running` между ходами, `halted` | по последнему `orch.turn` (`lastTurnPurpose`); без ходов — «Работа» | `halted` — `paused_other` |
| `paused(...)` — любая причина (`user_request`, `recovered`, `outcome_unknown`, `app_closed`, `stage_done`, `step_done`, `limit_reached`, вопросы и решения) | по последнему `orch.turn`, как выше | по причине паузы (§4.3) |
| `pausing`, `stopping` | по последнему `orch.turn` | `stopping` |
| `completed`, `completion.kind = confirmed` | «Готово» | — |
| `completed`, `kind = no_checks`, без `accepted` на этот запуск | «Проверка» | `no_checks` — «Завершено без проверок — примите результат или запустите снова» |
| `completed`, `kind = no_checks`, `accepted.runId` — этот запуск | «Готово (принято вами, без проверок)», `done = "accepted"` | — |
| `stopped`, `failed` | «Очередь» | `last_stopped` / `last_failed`, число попыток |
| журнал не читается (`journal_corrupt` и др.) | та же колонка, что по последнему читаемому запуску | `run_unreadable` |
| `newer_version` | «Очередь», только просмотр | `run_newer` |

«Работа» и «Проверка» определяются тем же признаком, что сейчас различает карточку исполнителя и проверяющего: активный ход `view.active` и его `purpose`, а также активная проверка. Без активного хода колонка берётся по последнему ходу из журнала, чтобы задача не мигала между колонками.

«Завершено без проверок» не становится «Готово» само: подтверждённых проверок не было (принцип 4). Действие
человека «Принять результат» переводит задачу в «Готово (принято вами, без проверок)». У этого состояния свой значок
и подпись, отличные от подтверждённого «Готово». Для зависимостей и автопилота оно равно «Готово» (решение 2).
Без принятия зависимые задачи можно начать только «Запустить всё равно» (§4.2).

«Готово» получается одним путём: `run.status(completed)` с `kind: "confirmed"`. Эту запись пишет только функция `completion` (journal-v2 §2.3), а воспроизведение проверяет её дважды. Поэтому «готово» нельзя получить ни отметкой в файле, ни правкой `board.json` (в нём нет поля статуса).

### 4.2. Зависимости

- `dependsOn` — задачи того же пространства. Цикл отклоняется при сохранении (`task_cycle`). Задачу, от которой зависят другие, удалить можно только после явного подтверждения со списком зависимых: зависимость снимается у них открыто, а не молча. Ссылка на архивную задачу остаётся.
- Задача «готова к запуску», если каждая зависимость в «Готово». «Запустить» на неготовой задаче возможно, но требует подтверждения: «T-3 ещё не готова — запустить всё равно?». Автопилот доски такие задачи не запускает никогда.
- Если зависимость потеряла «Готово» (новый запуск той задачи остановлен), уже готовые зависимые задачи **не** откатываются. Это показано пометкой «зависимость менялась после готовности». Пересчёт результата — этап D (EXP-SPEC-01), не B.

### 4.3. Причины

Одна строка, по приоритету (показывается первая):

1. `run_unreadable` — «Журнал запуска не читается».
2. `waits_permission` — «Ждёт разрешения: <команда>» (`view.permission`).
3. `waits_answer` — «Ждёт ответа на вопрос <роли>».
4. `waits_decision` — решение о командах, плане, спорном пункте или push/QA (`checks.proposed`, `plan.proposed`, `disputed`, `finish_awaiting_person`).
5. `limit_reached` — «Исчерпан лимит: <какой>». Вид лимита не входит в `run.status`; main берёт его из записи паузы хода в журнале (`RunTaskFacts.limit`). Если он не определён — «Исчерпан лимит».
6. `waits_task` — «Ждёт T-3, T-5».
6а. `waits_result` — «Результат T-3 не забран» (§5.2, «База зависимой задачи»). Основание — факт `taken` в `RunTaskFacts` запуска зависимости.
6б. `waits_merge` — «Нужно объединить результаты T-2 и T-3 (этап C)»: у задачи в режиме копии несколько зависимостей со своими ветками результата (решение 11).
7. `last_stopped` / `last_failed` — «Последний запуск остановлен (попытка 2)».
8. `no_checks` — «Завершено без проверок — примите результат или запустите снова».
9. `stopping` — «Останавливается».
10. `run_newer` — «Создан более новой версией — только просмотр».
11. `paused_other` — текст паузы из `runStatus` (включая `halted`).

Пункты 2–5 и 11 — существующие строки `runStatus.ts`. Новые в B — `waits_task`, `waits_result`, `waits_merge`, `last_*`, `no_checks`, `run_unreadable`, `run_newer`, `stopping`.

## 5. Автопилот доски

### 5.1. Что делает

Включается на связи («Вести доску»), выключен по умолчанию.

**Хранение.**
- Включённость не хранится: это состояние процесса main. После перезапуска автопилот выключен без записи в файл, поэтому сбой записи не может оставить его включённым.
- В `board.json` хранится только бюджет связи `autopilot: { [linkId]: { runs, minutes } }`.
- Использованный бюджет выводится: запуски с `goal.task` на этой связи после момента включения.
- Причина последней остановки живёт в памяти main.

**Сборка цели.** Сейчас цель (команды, режим, finish, права, модели) собирает диалог в renderer. Для автопилота это вторая реализация, и она разошлась бы с первой. Поэтому B4 начинается с одной функции `goalFor(task, profile)` в main. Диалог «Запустить» только показывает её результат и даёт его поправить. Автопилот использует её без правки.

**Снимок настроек.** При включении автопилот запоминает отпечаток профиля проекта — новый, по полям:
- `access`;
- `mode`;
- `models`;
- `workMode`;
- `finish`;
- команды проверки;
- сохранённые разрешения проекта.

Это не `grantFingerprint`: тот — отпечаток одного действия для сохранённого разрешения. Любое расхождение перед стартом — остановка с причиной «настройки проекта изменились» (принцип 7).

**Выбор задачи** — чистая функция `(tasks, statuses, link) → taskId | null`. Она берёт задачу, которая:
- в том же пространстве, что связь;
- той же папки, что лид связи;
- не в архиве;
- в «Очереди» без причины (все зависимости в «Готово»);
- **без попыток**: повтор после `stopped` или `failed` — всегда решение человека.

Из подходящих берётся задача с минимальным `order`.

**Старт.** Тот же `create`, что у кнопки, с `requestId`, который main запоминает до ответа. Повтор после сбоя идёт в идемпотентную ветку и не создаёт второй запуск. Перед стартом — та же готовность (`readiness`, без ходов модели) и сверка снимка.

**Одна задача — один активный запуск.** Это проверяется в main внутри `startOnLink`, в той же очереди `canvasStore.change`, что `link_busy` и `folder_busy`. Так два старта одной задачи не пройдут оба, в том числе в C, когда `folder_busy` ослабнет. Добавить тест на гонку.

Правило одно: автопилот доски не делает ничего, чего не сделала бы кнопка «Запустить» с теми же настройками.

### 5.2. Когда останавливается

Два разных исхода. **Ждёт** — продолжит сам, когда условие уйдёт. **Выключен** — с причиной, включает человек.

| Событие | Исход |
|---|---|
| Последний запуск ждёт человека: вопрос, разрешение (`view.permission`, запуск в `running`), решение о командах (`awaiting_checks_decision`), плане, спорном пункте, push/QA | ждёт; после ответа запуск идёт дальше, а при «Готово» автопилот берёт следующую задачу |
| Пауза по шагам (`stage_done` / `step_done`: профиль в режиме «по шагам») | ждёт; поэтому включение автопилота доски с режимом «по шагам» предупреждает, что каждый этап потребует «Продолжить» |
| Запуск кончился не «Готово»: `stopped`, `failed`, пауза `limit_reached` | выключен |
| Запуск завершён без проверок (`no_checks`) | ждёт: после «Принять результат» задача — «Готово», автопилот идёт дальше |
| Задача стала «Готово» (подтверждённое или принятое) | автопилот забирает результат: «Создать ветку в проекте» (решение 8), затем выбирает следующую задачу |
| Исчерпан бюджет доски: запусков (по умолчанию 5) или минут (по умолчанию 240, время ожидания человека не считается) | выключен |
| Настройки проекта изменились (снимок) | выключен |
| Нет задач без причины | выключен: «Всё готово» или «Остальные ждут: T-4 (ждёт T-3)» |
| Человек выключил автопилот | выключен; текущий запуск продолжается, новые не начинаются |
| Перезапуск приложения | выключен (состояние в памяти) |

| Прочие паузы (`user_request`, `environment_error`, `external_failure`, `needs_user_action`, `coverage_lost`, `tree_changed_during_review`, `check_needs_permissions`, `sandbox_unavailable` и новые) | выключен |

Ответ «Разрешить для проекта» внутри запуска автопилота меняет сохранённые разрешения, а значит, и снимок. Следующая задача выключит автопилот. Причина называет изменение: «добавлено разрешение проекта: <что>», а не общее «настройки изменились».

Минуты бюджета — сумма по запускам автопилота интервалов вне пауз, ждущих человека, по записям `run.status` журнала. Ожидание разрешения в журнал не пишется (оно в памяти и в ленте), поэтому оно считается рабочим временем. Оценка консервативная: бюджет кончается раньше, а не позже.

**База зависимой задачи.** В режимах «отдельная копия» и worktree результат задачи не попадает в папку проекта, пока человек его не заберёт. Как именно забран — важно:
- «Создать ветку» не трогает рабочую папку, индекс и HEAD (`workspace.ts`, «Забрать результат»). Зависимая задача из папки проекта изменений не увидит.
- «Применить» пишет файлы в рабочую папку без коммита. Копия снимает базу с рабочей папки, так что увидит их. Worktree стартует от HEAD, так что не увидит.
- Если зависимость работала в режиме «папка проекта», её изменения уже в папке.

Правило B: зависимость годится как база, если она работала в папке проекта, или если в `taken.json` её успешного запуска есть `applied` для его дерева и зависимая задача идёт в режиме копии. Иначе у задачи причина `waits_result` («результат T-3 не забран» или «для worktree результат T-3 должен быть в коммите»). Автопилот её не берёт, ручной старт требует того же подтверждения, что «Запустить всё равно».

Известное ограничение: `taken.json` фиксирует, что результат применили, но не видит, что человек потом откатил файлы.

Забор результата — событие для автопилота: после него выбор задачи пересчитывается, иначе автопилот из ожидания не выйдет.

**Решение 11 (2026-10-09) меняет правило B для режима копии.** Зависимая задача в режиме копии может стартовать от
ветки результата зависимости:
- ветку `raoden/…` создаёт «Создать ветку в проекте» — автопилот сам (решение 8) или человек;
- копия снимает базу с этой ветки, а не с рабочей папки; рабочая папка, индекс и HEAD не меняются;
- в автопилоте это база по умолчанию, вне автопилота человек выбирает в диалоге: «рабочая папка» или «ветка T-3»;
- поддерживается одна зависимость или линейная цепочка. Если у задачи несколько зависимостей со своими ветками, база
  требует слияния: причина `waits_merge` («нужно объединить результаты T-2 и T-3 — это этап C»), автопилот ждёт
  человека;
- worktree — как прежде (правило B), старт worktree от ref — этап C.

**Автоматическое «Создать ветку в проекте» (решение 8).**
- В автопилоте доски, когда задача становится «Готово» (подтверждённое или принятое), main выполняет то же действие,
  что кнопка «Забрать результат → Создать ветку в проекте».
- Тот же код (`manager.take`), та же проверка дерева, то же имя `raoden/<цель>-<id>`.
- Рабочую папку, индекс и HEAD действие не трогает.
- Если ветка для этого дерева уже есть (`taken.json`), второй не создаётся.
- Отказ (`take_conflict` и др.) — остановка автопилота с причиной; задача остаётся «Готово».
- Для запуска в папке проекта действие не нужно: изменения уже в папке.

Решение, нужна ли ветка, — чистая функция `autoTakeOnDone(status, run, taken)`.
- **B1:** функция и её тест.
- **B4:** вызов из автопилота.

**Следствие для зависимых задач.** Ветка не меняет рабочую папку. По решению 11 зависимая задача в режиме копии
стартует от этой ветки, поэтому `waits_result` у неё больше нет, когда ветка есть. Без ветки и без применённого
результата (вне автопилота, результат не забран) причина прежняя — `waits_result`. Цепочка A → B → C идёт по веткам:
база B — ветка A, база C — ветка B. Применить итог к рабочей папке — решение человека в конце цепочки.

### 5.3. Урок части 1 (запуск 7303d772)

В 1.5.12 Claude в «Рабочей папке» спросил 11 раз за один ход. Почти всё это были команды только для чтения: `bash -c '…'`, переменная, фигурные скобки. CLI спрашивает о них не из-за прав, а потому что не может разобрать команду заранее (`decision_reason_type: other / subcommandResults`). Песочница их всё равно не выпустила бы за пределы выданных прав. Автопилот без человека простоял бы на первом вопросе. Выводы для автопилота доски:

1. **Проверить, что вопросы задаёт CLI, а не права.** Это критерий приёмки B4, а не условие в коде: результат пробы зависит от версии CLI и в приложении не хранится. Реальная проба — доска на 3 задачи в «Рабочей папке», в отчёте версия CLI и число вопросов на обычные чтения (ожидается 0, как после исправления 1.5.13). Безопасность обеспечивает п. 2: вопрос останавливает автопилот.
2. **Автопилот прав не расширяет и не переносит.** «Разрешить чтение до конца запуска» действует в своём запуске и только до его переоткрытия: оно живёт в памяти контроллера (`readOnly.allowed`), не в журнале. Автопилот доски не передаёт это решение следующей задаче и не отвечает на вопросы сам. Вопрос — это ожидание с причиной `waits_permission` (§5.2).
3. **Вопрос — данные, а не шум.** Доска показывает число вопросов о правах за запуск. Если у задачи больше 3 вопросов (та же константа, что порог кнопки `readOnly.asks > 3`), рядом подсказка: «Агент часто спрашивает — проверьте режим прав». Так проблема видна на доске, а не только после разбора.
   Источник — записи `permission` ленты активности. Это показ, а не основание решений: лента вне цепочки хешей и пишется без гарантий (`activity.ts`). Автопилот по этому числу ничего не решает.
4. **Причина CLI видна.** Сейчас в ленту попадают инструмент и команда, но не причина вопроса (`decision_reason_type`, `decision_reason` из `can_use_tool`). В 7303d772 её пришлось восстанавливать пробой. B3 добавляет причину в запись ленты (не в журнал). Строка `waits_permission` показывает её как есть, без пересказа.
5. **Автоответы хоста видны.** Исправление 1.5.13 отвечает на вопросы `other` / `subcommandResults` прямо в `sessions.ts` и ничего не пишет. Тогда «0 вопросов» на доске и в пробе п. 1 не отличает «CLI не спросил» от «хост ответил сам». B3 пишет такой автоответ в ленту: `permission`, фаза `applied`, scope `sandbox_static`, с `decision_reason_type`. Показывается отдельно от вопросов человеку.

### 5.4. Чего автопилот доски не делает

- Не запускает задачу с невыполненными зависимостями.
- Не повторяет `stopped` и `failed` сам: повтор — решение человека.
- Не делает push, QA и «Забрать результат». Действия после успеха — как в цели (stage 13), с подтверждением для запусков без проверок (A4).
- Не меняет настройки проекта, права, модели.

## 6. Интерфейс

- **Где.** Доска — карточка на холсте пространства, с изменяемым размером, как карточки агентов: те же ручки, выделение,
  групповое перетаскивание, масштаб. Одна на пространство.
  - Её место и размер хранятся в `board.json` по пространству, не в `canvas.json`: 1.5.13 при записи отбрасывает
    неизвестные ключи `canvas.json`.
  - Кнопка «Доска» в шапке пространства, рядом со счётчиками, показывает её на холсте или создаёт.
  - Отдельного окна нет.
- **Колонки.** «Очередь», «Работа», «Проверка», «Готово». Счётчик в шапке каждой колонки. Архив скрыт, доступен через «Показать архив».
- **Карточка задачи** — 3–4 строки, без обрезки по высоте (урок карточек агентов 1.5.13):
  1. `T-4` и заголовок.
  2. Причина (§4.3) или фаза («Claude выполняет этап 2/3»), из той же функции, что карточка агента.
  3. Факты: «условий 3/5 · блокирующих 0 · попытка 2 · вопросов о правах 4».
  4. Зависимости, если есть: «после T-2, T-3».
  5. Исполнитель и расход последнего запуска (как на карточке агента: вызовы и токены).

  «Готово (принято вами, без проверок)» — свой значок и подпись, не зелёная галочка подтверждённого «Готово».
- **Действия** на карточке — только допустимые для её колонки и состояния (как `availableActions`):
  - «Запустить» / «Запустить снова»;
  - «Открыть запуск» — панель запуска;
  - «Изменить»;
  - «Принять результат» — только у «Завершено без проверок», с пояснением: «Команды проверки не запускались. Принимая,
    вы подтверждаете результат сами; зависимые задачи пойдут дальше»;
  - «В архив».
  Остановка, ответы и разрешения — в панели запуска, не на доске: у этих действий один дом.
- **Создание.** «Новая задача» — форма: заголовок, текст, требования (по строке), зависимости. Это та же форма, что «Новая цель», только без запуска.
- **Связь с холстом.**
  - Карточка агента в работе показывает `T-4 · заголовок` над строкой действия.
  - «Открыть запуск» на доске подсвечивает связь на холсте.
  - Итог запуска начинается с задачи.
- **Порядок в «Очереди»** — перетаскиванием и с клавиатуры (Alt+↑/↓). В остальных колонках порядок по времени последнего события.
- **Автопилот доски** — переключатель «Вести доску» на плашке связи и в шапке доски. Рядом бюджет и причина последней остановки.
- **Доступность.**
  - Колонки — `role="list"`.
  - Карточки — кнопки с названием и причиной в `aria-label`.
  - Всё доступно с клавиатуры.
  - Цвет не единственный признак состояния: у причины есть текст.

## 7. Подготовка к этапу C

B не делает параллельности, но не закрывает к ней дорогу:
- **Задача — единица работы.** Этап C распределяет задачи по исполнителям. Модель задачи не содержит исполнителя: его выбирает запуск (связь). Поле `linkId` в задаче не нужно.
- **Ограничение «у задачи не больше одного активного запуска»** проверяется в main при `create` (`task_active_run`), а не следует из `folder_busy`. Когда C ослабит `folder_busy` для worktree, это правило останется.
- **Режим рабочей копии.** Режим берётся из профиля проекта, как сейчас. В B зависимая задача в копии стартует от ветки результата зависимости (решение 11) или от рабочей папки с применённым результатом; в worktree требует результата в коммите (§5.2, «База зависимой задачи»). В C — несколько зависимостей (слияние веток) и worktree от ref.
- **Выбор следующей задачи.** Функция автопилота §5.1 — чистая: `(tasks, statuses, link) → taskId | null`. В C она станет «следующие задачи для N исполнителей» без смены данных.
- **Результат задачи** = результат её последнего успешного запуска (`refs/canvastty/<runId>/stage-<n>`, «Забрать результат»). Проверка объединения в C добавит свой запуск и свою запись. Задача при этом не меняется.
- **EXP-SPEC-01 (D).** Пометка «зависимость менялась после готовности» (§4.2) — единственный зачаток. Предварительных результатов в B нет.

## 9. Вопросы и решения

Вопросы 1–8 решены владельцем 2026-10-08, вопрос 9 — 2026-10-09 (§0).

1. **Начинать ли B1 до внешнего ревью этапа A?** B1 меняет форму цели (`goal.task`), а она — предмет того ревью (journal-v2 §1).
   **Рекомендация:** store `board.json`, `RunTaskFacts`, `taskStatus` и IPC начать сразу. `goal.task` в `checkGoal` влить после ревью A. B2–B4 — после ревью.
   **Решение (1):** B1 целиком сейчас, включая `goal.task`. Ключ входит во внешнее ревью A.
2. **«Завершено без проверок» и зависимые задачи.** В «Готово» такая задача не попадает (§4.1, принцип 4).
   **Рекомендация:** зависимые задачи запускаются только «Запустить всё равно». Автопилот на ней выключается. Отдельной отметки «принято без проверок» в `board.json` не делать: она выглядела бы как «готово» по записи в файле.
   **Решение (2):** действие «Принять результат» → «Готово (принято вами, без проверок)», отличное от подтверждённого. После него зависимые идут как от «Готово». Запись `accepted` действует только для последнего запуска задачи, завершённого без проверок (§2.1).
3. **Задача в нескольких пространствах или перенос задачи.**
   **Рекомендация:** нет. Задача принадлежит одному пространству, как запуски. Перенос группы агентов (`moveAgentGroup`) задачи не переносит. Если понадобится, перенос задачи без запусков — отдельный PR после B.
4. **Изменение текста задачи после запусков.**
   **Рекомендация:** разрешить. Новый запуск возьмёт новый текст, старые запуски показывают свой (из цели). В истории задачи пометка «текст изменён после попытки N». Это явное решение человека; перепланирование внутри запуска по-прежнему не ослабляет требования (принцип 9).
5. **Где хранить бюджет автопилота доски** — в `board.json` или в профиле проекта.
   **Рекомендация:** `board.json`, по связи. Включённость не хранится нигде (§5.1). Права и режим хода остаются в профиле.
6. **Порядок «Очереди» при зависимостях.** Ручной `order` может противоречить `dependsOn`.
   **Рекомендация:** показывать как задано. Автопилот берёт первую готовую по `order` и пропускает задачи с `waits_task`.
7. **Нужна ли колонка «Ждёт проверки»** (сейчас это «Проверка» с причиной).
   **Рекомендация:** нет. Четыре колонки, как в цикле; причина вместо колонки.
8. **База зависимой задачи в копии и worktree.** Варианты:
   - (а) автопилот только в режиме «папка проекта»;
   - (б) зависимость годится, когда её результат забран;
   - (в) зависимая задача стартует от ref зависимости.

   **Рекомендация:** в B — (б), как в §5.2. Оно закрывает только зависимую задачу в режиме копии (база — рабочая папка с применённым результатом). Для worktree в B автопилот ждёт, пока человек закоммитит результат. Автоматическая проверка «HEAD содержит результат» в B не делается: после cherry-pick хеш другой, сравнение деревьев — работа C. Результат остаётся под контролем человека, папка проекта не меняется без него. (в) — в C вместе с проверкой объединения.
   Ревьюер предлагал также (а) как самый простой. Он отклонён: «папка проекта» — не режим по умолчанию для новых проектов, и автопилот был бы недоступен большинству.

9. **Автоматическая ветка и зависимые задачи (следствие решения 8).**
   - Автопилот при «Готово» создаёт ветку, но рабочая папка остаётся прежней.
   - Зависимая задача в режиме копии ждёт «Применить к рабочей папке» (`waits_result`). Цепочка автопилота
     останавливается на первой зависимости.
   - Варианты:
     - (а) так и оставить: применять результат — решение человека;
     - (б) в автопилоте после ветки ещё и «Применить к рабочей папке», когда в папке нет незакоммиченных правок
       (`git apply --check` уже в коде);
     - (в) база зависимой задачи — ветка зависимости (это и есть старт от ref, этап C).

   **Рекомендация:** (а) в B4; (в) — в C. Вариант (б) меняет папку пользователя без него, а решение 8 выбрало именно
   безопасное действие.
   **Решение (11, 2026-10-09):** (в) для режима копии уже в B4 — одна зависимость или линейная цепочка; несколько
   веток со слиянием — пауза для человека, слияние — этап C. «Применить к рабочей папке» в конце цепочки — решение
   человека. Вне автопилота база выбирается: рабочая папка или ветка зависимости.
