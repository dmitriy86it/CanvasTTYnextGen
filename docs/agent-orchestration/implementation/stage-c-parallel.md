# Этап C: параллельные исполнители

**Статус: Утверждено владельцем (с решениями ниже), 2026-10-10.** Реализация разрешена по подэтапам C1–C4 (§9). Документ
продолжает [Автоматический цикл задач](../AUTOMATIC-TASK-CYCLE.md) (этап C) и [ROADMAP](../ROADMAP.md) (порядок
A → B → C → D). Опирается на:
- утверждённый [этап B](stage-b-board.md) (решения 1–12: `waits_merge`, ветки результатов, автопилот доски);
- [формат журнала v2](journal-v2-format.md) и мост §2.2.1 [контракта A](acceptance-review-spec.md);
- [ARCHITECTURE](../../ARCHITECTURE.ru.md) («Оркестрация агентов»: рабочие копии, «Забрать результат», песочница
  проверок, права агентов);
- реальную пробу B4 ([evidence/real-b4](../evidence/real-b4/README.md)) и код 1.5.16.

**Цель этапа C** (из цикла): несколько задач одного проекта идут одновременно, каждая в своей рабочей копии;
объединённый результат заново проходит обязательные проверки. Критерии цикла:
- при конфликте работа не теряется молча;
- объединение без повторной проверки не считается готовым;
- права каждого исполнителя равны выбранным пользователем.

Принципы владельца для C:
- минимум ручных действий;
- честный итог: ничего не выглядит подтверждённым без проверок, в том числе после слияния;
- безопасность по умолчанию: рабочая папка пользователя автоматически не трогается — ни файлы, ни индекс, ни HEAD,
  ни его ветки;
- журнал v2 и `board.json` меняются только с явной причиной и по правилам совместимости;
- права агентов не расширяются.

Отступления от текста цикла (их принимает владелец, §10):
- в цикле параллельность — «каждый в своём worktree», и `folder_busy` ослабляется только для worktree. Здесь C1 начинает
  с «отдельной копии» — режима по умолчанию для новых проектов; worktree — в C2 (вопрос 2);
- в цикле «конфликты выявляются до объединения». Здесь пересечение задач видно заранее как предупреждение (C2, §4.7),
  а сам конфликт решается при вливании (вопрос 2).

## 0. Что есть сейчас (1.5.16)

- **Одна папка — один активный запуск, в любом режиме.** `folderHolder` (`canvasStore.ts`) отказывает в старте
  (`folder_busy`), если другая связь с лидом в той же папке держит активный запуск. Правило появилось в этапе 12,
  когда агенты стали работать прямо в папке, и режим рабочей копии оно не учитывает. Сейчас даже две «отдельные копии»
  одного проекта не идут одновременно.
- **У связи не больше одного активного запуска** (`link_busy`), у задачи — тоже (`task_active_run`, B4). Запуск,
  созданный более новой версией, держит в старой сборке свою связь и папку (`busy` → `"newer"`, `canvasStore.ts:61`).
- **Рабочие копии.**
  - «Отдельная копия» — клон в `runs/<id>/workspace/repo`. База — рабочая папка (снимок на старте, с
    незакоммиченными и неотслеживаемыми файлами) или коммит (`goal.base`, B4).
  - Worktree — `git worktree add` в репозитории пользователя, ветка `canvastty/<run>` от HEAD.
  - «Папка проекта» — сами файлы пользователя.
  - Зависимости (`node_modules`, `vendor`) клонируются из проекта через APFS clonefile. Lock-файл сверяется до
    клонирования.
- **Результат задачи** — ветка `raoden/<цель>-<id>` в проекте («Создать ветку в проекте»). Действие создаёт только новое
  имя (`update-ref` с нулевым старым значением): рабочая папка, индекс и HEAD не меняются. В автопилоте доски ветку
  создаёт сам main (решение 8).
- **Автопилот доски** ведёт одну связь последовательно: следующая задача — после «Готово» предыдущей. Бюджет: 5 запусков,
  240 рабочих минут. База зависимой задачи — ветка зависимости (решение 11). Несколько зависимостей с ветками —
  `waits_merge`, пауза для человека. «Нет задач без причины» — автопилот выключен.
- **Проверки** идут в песочнице Seatbelt на машине пользователя. Сеть — только localhost, любой порт. Ключ результата
  проверки (`checkKey`, `progress.ts`) — дерево, команда, lock-файл и состояние `node_modules`.
- **Лимит провайдера** во время хода сейчас никак не распознаётся: ход падает как внешний сбой, запуск встаёт на паузу
  `external_failure`.

## 1. Сценарии

1. **Параллельные независимые задачи.** На доске T-1 «форма входа» и T-2 «экспорт CSV», зависимостей нет. Человек
   включает «Вести доску», параллельность 2.
   - Приложение один раз снимает базу с рабочей папки и заводит **общую вершину доски** (§4.1). Обе задачи
     стартуют от неё, каждая в своей отдельной копии.
   - Каждая становится «Готово» по своим проверкам. Приложение по одной вливает их результаты в общую вершину: в
     отдельной копии, с обязательными проверками на объединённом дереве.
   - В шапке доски: «Итог доски: T-1, T-2 · проверки прошли · Создать ветку · Применить». Рабочая папка не изменилась.
     Ветка для человека и применение к папке — его действия.
2. **Задача с двумя зависимостями — снятие `waits_merge`.** T-3 после T-1 и T-2. В B она ждала бы человека. В C
   T-3 стартует, когда оба результата уже влиты в общую вершину и проверены. База T-3 — общая вершина.
3. **Конфликт при слиянии.** T-1 и T-2 правили одну функцию. Пока они шли, доска предупреждала: «T-1 и T-2
   пересекаются в src/auth.ts» (§4.7). Результат T-1 влит первым. При вливании T-2 git сообщает конфликт. Ветка T-2 и
   общая вершина не меняются, работа не теряется.
   - В C1 — пауза для человека: показан путь к копии объединения, где конфликт можно разрешить своим редактором.
   - С C3 по умолчанию конфликт поручается агенту: исполнитель и проверяющий, в правах проекта, с требованиями обеих
     задач. Механическая проверка не даёт выбросить изменения вне конфликтных файлов (§4.3).
   - Не справился (лимит, отказ проверок) — задача T-2 «Готово · не объединено: конфликт в src/auth.ts», решает человек.
4. **Одна из параллельных задач упала или ждёт человека.** T-1 ждёт ответа на вопрос лида, T-2 работает дальше. T-1
   держит свой слот, свободный слот берёт следующую задачу без причины.
   - Если T-2 упала (`failed`), новые задачи не начинаются. Начатые идут дальше: их никто не останавливает.
   - Когда активных запусков не остаётся, автопилот выключается с причиной «T-2 упала» (§5.2). Повтор — решение
     человека, как в B.
5. **Лимит провайдера во время параллельной работы.** Ход Claude в T-1 упал с сообщением о лимите подписки, T-2 в это
   время ждёт ответа Claude.
   - Запуск T-1 встаёт на паузу (как сейчас, `external_failure`).
   - Автопилот перестаёт брать новые задачи с причиной «Ждёт лимита Claude». Это ожидание: автопилот остаётся
     включённым.
   - T-2 упадёт или пройдёт сама, её никто не останавливает.
   - Когда лимит сбросится, человек нажимает «Продолжить» в T-1. Ход прошёл — автопилот снова берёт задачи сам.
     Автоматического повтора по таймеру в C1–C3 нет. С C4 — решение владельца 6: если CLI сообщил время сброса,
     автопилот продолжает сам.

## 2. Параллельность

### 2.1. Сколько задач одновременно

- **По умолчанию 2, настройка автопилота доски от 1 до 4** — рядом с бюджетом, на связи.
- Слот занимает запуск задачи от создания до `completed`, `stopped` или `failed`. Пауза держит слот: запуск может
  продолжиться, и его копия остаётся.
- **Запуск объединения с ходами** (разрешение конфликта, C3) занимает слот. Без ходов (только проверки) слота не
  занимает. Объединения в одну общую вершину идут строго по одному.
- **Ручные запуски** проекта (из задачи или обычная цель) тоже занимают слоты. При занятых слотах кнопка спрашивает:
  «Уже идут 2 задачи этого проекта — запустить третью?». Автопилот ручные запуски не останавливает.
- Параллельность 1 — автопилот берёт по одной задаче, но в «отдельной копии» общая вершина и объединения работают так
  же. Это меняет решение 11 для линейной цепочки: B стартует от общей вершины после вливания A, а не от ветки A
  (вопрос 9).
- **Общая вершина и объединения — только для «отдельной копии».** В режиме «папка проекта» у результата нет своего
  коммита (`takeToBranch` отказывает, `workspace.ts:858`), и он уже в папке. Автопилот в этом режиме работает строго по
  правилам B: по одной задаче, зависимость в папке годится как база (B §5.2). Worktree до C2 — тоже по правилам B; с
  C2 он получает старт от вершины и объединения, как копия.

### 2.2. Ограничения

| Ресурс | Что ограничивает | Как учитывается |
|---|---|---|
| Подписка Codex и Claude (одна на оба провайдера) | частота и объём запросов; у Codex — окна лимита, у Claude — лимит сессий | параллельность по умолчанию 2; лимит провайдера останавливает выбор новых задач (§2.4). Запуск идёт ходами по очереди (лид → исполнитель → проверяющий), поэтому одновременно работает не больше процессов CLI, чем занятых слотов |
| CPU и память | ход CLI — немного; `npm test`, сборка, установка зависимостей — много | проверки идут по очереди в пределах проекта (§2.3); подготовка копии (клонирование, `npm ci`) — тоже по очереди |
| Песочница проверок | Seatbelt без ограничения ресурсов; две проверки одного проекта бьются за порты и CPU | очередь проверок проекта (§2.3) |
| Порты localhost | тесты, поднимающие сервер на фиксированном порту, падают при одновременном запуске | очередь проверок и один повтор упавшей проверки объединения (§2.3) |
| Диск | копия — клон с общими объектами, зависимости — clonefile | без ограничения; размер копий показан в панели запуска, как сейчас |

### 2.3. Как параллельные запуски не мешают друг другу

1. **Отдельная рабочая копия у каждого.** Режим «папка проекта» с параллельностью несовместим: при нём действует
   прежнее правило — один запуск на папку (§3.1).
2. **Очередь проверок проекта.** Команды проверки всех запусков одного проекта и проверки объединения идут по
   одной. Очередь живёт в main, в памяти: проверки короче ходов модели, поэтому ожидание мало.
3. **Тесты агентов в ходах очередь не видит.** Агент в своём ходе может поднять сервер на том же порту, что проверка
   приложения. Ложного «Готово» это не даёт: проверка упадёт, а не пройдёт. Ложный отказ возможен. Поэтому:
   - проверка задачи, упавшая так, — обычная ошибка: исполнитель получит её вывод (как сейчас);
   - **упавшая проверка объединения повторяется один раз.** На время ожидания повтора автопилот не начинает новых
     задач. Повтор идёт, когда ни в одной копии проекта нет хода, но не позже чем через 10 минут. Упала снова — это
     семантический конфликт (§4.3) с пометкой «возможна помеха: порт или процесс другой задачи». Сервер, запущенный
     агентом в фоне, может пережить конец хода, поэтому «нет хода» не гарантирует свободный порт: пометка об этом
     предупреждает.
4. **Очередь git проекта** (§3.3): всё, что пишет в репозиторий пользователя, идёт по одной.
5. **Сессии CLI раздельны.** У каждого запуска свои сессии лида, исполнителя и проверяющего, как сейчас. Codex не
   пишет запись доверия для копий запуска: копия получает `trusted` в `config` потока, `config.toml` не меняется.

### 2.4. Лимит провайдера

- Main распознаёт лимит в тексте ошибки хода по известным строкам CLI (фикстуры в тестах). Класс сбоя остаётся
  `external`, пауза — `external_failure`, журнал не меняется. Распознанный лимит пишется в ленту активности как факт
  для показа.
- Пока у любого запуска проекта пауза с распознанным лимитом, автопилот ждёт с причиной «Ждёт лимита Claude» и новых
  задач не берёт. Пауза ушла (человек нажал «Продолжить», ход прошёл) — автопилот продолжает сам.
- Нераспознанный внешний сбой — как остальные паузы: автопилот ждёт, пока идут другие запуски, и выключается, когда их
  не осталось (§5.2).
- С C4 (решение владельца 6): если в тексте лимита есть время сброса, автопилот после него сам продолжает запуск
  («Продолжить») и показывает уведомление «Лимит сброшен, продолжаю». Без времени сброса — «Продолжить» руками, как
  выше.
- Виджет лимитов (`LimitsService`) показывает окна Codex. Автопилот по нему ничего не решает: это показ, а не
  основание (как число вопросов о правах в B).

## 3. Изоляция

### 3.1. Режимы и правило занятости

| Режим | Параллельно с другими задачами проекта | Почему |
|---|---|---|
| Отдельная копия (по умолчанию для нового проекта) | да, с C1 | клон в `runs/<id>/`, папку пользователя не трогает |
| Worktree | да, с C2 | свой каталог и своя ветка `canvastty/<run>`; старт от общей вершины — с C2 |
| Папка проекта | нет | агенты правят файлы пользователя; второй запуск увидел бы чужие полуготовые правки |

Новое правило занятости (заменяет `folder_busy` этапа 12):
- запуск в режиме «папка проекта» держит папку целиком: при нём не стартует ни один запуск этого проекта, и сам он
  не стартует, пока идёт любой другой запуск проекта;
- запуск в копии или worktree держит только свой слот;
- запуск, созданный более новой версией (`newer`), по-прежнему держит папку целиком: его режим неизвестен;
- запуски объединения (§5.3) не стоят на связях. Правило занятости находит их по журналам (цель с `merge`) и считает
  как запуски проекта: при активном объединении «папка проекта» не стартует.

`link_busy` в C ослабляется для всех запусков в копии и worktree — задач доски и обычных целей: на одной связи может
идти столько запусков, сколько слотов (§2.1). `task_active_run` не меняется: у задачи по-прежнему один активный
запуск.

### 3.2. Общие ресурсы

| Ресурс | Кто пишет | Гонка | Защита |
|---|---|---|---|
| `.git` проекта: объекты | создание копии (`clone --shared`), `fetch` контрольных точек и коммитов слияния | нет: объекты неизменяемы, запись атомарна | — |
| `.git` проекта: ссылки запусков | `baseline`, `stage-n`, `recovery-k` | нет: имена уникальны по `runId` | очередь git проекта |
| Ветки результатов `raoden/<цель>-<id>` | «Создать ветку» | одно имя для двух запусков | имя содержит `runId`; только создание нового имени (`update-ref` с нулевым старым значением, код 1.5.16) |
| Общая вершина доски | только запуск объединения (§4.1) | два объединения сразу; человек двигает ссылку руками | ссылка вне `refs/heads`; двигается только с вершины, которую поставил сам запуск объединения (`update-ref <ref> <new> <old>`); несовпадение — автопилот выключен с причиной |
| `.git/worktrees` | `git worktree add` | две записи одновременно | очередь git проекта |
| Зависимости `node_modules`, `vendor` | clonefile из проекта при создании копии | проект меняется во время клонирования | клон — отдельные файлы (copy-on-write); lock-файл сверяется до клонирования, как сейчас. Новое в C: после клонирования lock-файл сверяется ещё раз; не совпал — подготовка ставит зависимости в копии |
| `board.json` | правка задач, бюджет, место, параллельность | два изменения одновременно | одна очередь записи на файл (как в B); запись атомарная (tmp + rename) |
| `canvas.json` | резервирование запуска, `owners` | два старта одновременно | одна очередь `canvasStore.change`, в ней же проверки занятости и выбор слота |

### 3.3. Очередь git проекта

Одна очередь на `realpath` репозитория, в main. В неё входят:
- создание рабочей копии (`baseline`, worktree);
- контрольная точка этапа (`stage-n`);
- «Создать ветку в проекте» — ручное и автоматическое;
- коммит слияния и движение общей вершины (§4.2).

Внутри очереди операция короткая (секунды): она пишет объекты и ссылки, создаёт каталоги. Тяжёлое (клонирование
зависимостей, `npm ci`, проверки) идёт вне её. Сбой операции не блокирует очередь: следующая операция начинается после
отказа предыдущей.

### 3.4. Гонки, которые нужно закрыть тестами

1. Два старта одной задачи (B4: `task_active_run` в очереди `canvasStore`) — уже есть, остаётся.
2. Автопилот заполняет два слота: выбор задач — чистая функция над снимком, старты — последовательно в очереди
   `canvasStore`. Два вызова выбора на одном снимке не дают одну задачу дважды.
3. «Создать ветку» вручную и автоматически для одного запуска: вторая находит ветку в `taken.json` и не создаёт новую
   (B4, остаётся).
4. Два объединения в одну общую вершину: второе ждёт первое в очереди объединений. Если вершина всё же не та, что
   ожидалась (человек сдвинул ссылку), — отказ, автопилот выключен с причиной. Чужие коммиты в итог не попадают.
5. Запись `board.json` из правки задачи и из настройки параллельности одновременно: обе в одной очереди, ни одна не
   теряется.
6. Перезапуск приложения посреди объединения: §4.6.

## 4. Слияние

### 4.1. Общая вершина доски

У пространства на каждый проект есть **общая вершина доски** — ссылка приложения в репозитории проекта:
`refs/raoden/board/<workspaceId>/<n>`. Это не ветка.
- Её не видно в `git branch`, её не выбрать `git switch`, `git push --all` её не публикует.
- Человек не может стоять на ней своей рабочей папкой. Поэтому, когда приложение её двигает, под ним ничего не
  меняется.

Как она живёт:
- **Начало.** При первом старте автопилота (или первом «Объединить», §4.5) приложение один раз снимает базу с рабочей
  папки, как копия на старте: коммит с незакоммиченными и неотслеживаемыми, но не игнорируемыми файлами. Это первая
  вершина. Имя с `<n>` создаётся, только если оно свободно.
- **Старт задач.** Все задачи автопилота — и независимые, и зависимые — стартуют от вершины на момент старта (`from`,
  как `goal.base` в B4). Так у параллельных задач одна база, и в итог не попадает случайная смесь правок, сделанных в
  папке между стартами.
- **Зависимости.** Зависимая задача стартует, когда результаты всех её зависимостей влиты в вершину. Это снимает
  `waits_merge` и обобщает решение 11.
- **Движение.** Вершину двигает только запуск объединения, завершённый подтверждённо (или принятый человеком, §4.4),
  и только с той вершины, от которой он строился.
- **Итог доски для человека.** На вершине — те же действия, что в «Забрать результат»:
  - «Создать ветку» — новое имя `raoden/board-…-<коммит>`, только создание;
  - «Применить к рабочей папке» — с `git apply --check`, при пересечении с незакоммиченными правками отказывает.

  Оба — только по нажатию человека.
- **Новая вершина.** «Начать новую общую вершину» — действие человека (например, после «Применить»). Старая остаётся
  в репозитории для истории.

Неотслеживаемые файлы рабочей папки на старте попадают в первую вершину, как сейчас в `baseline`. Ветка, созданная
человеком из вершины, их тоже содержит. Это сказано в окне «Создать ветку».

### 4.2. Кто сливает и как

**Сливает приложение, в отдельной копии.** Запуск объединения — запуск оркестрации со своим журналом (§5.2):
1. Main в очереди git проекта создаёт копию от текущей вершины (`from`).
2. В копии main выполняет `git merge --no-ff --no-commit <коммит результата задачи>`, без модели.
3. **Коммит слияния собирает main**, а не копия:
   - дерево — снимок копии (`commitSnapshot`, как контрольные точки);
   - родители — ожидаемая вершина и коммит результата задачи;
   - сообщение называет задачу и её запуск.

   HEAD копии main не читает: при разрешении конфликта исполнитель может делать в `.git` копии что угодно (reset, свои
   коммиты, отмену слияния), на итог это не влияет.
4. **Без конфликта — проверка объединения.** Main прогоняет обязательные команды проверки проекта на дереве слияния,
   по очереди проверок.
   - Прошли — запуск `completed`, `completion.kind = confirmed`, вершина двигается на коммит слияния.
   - Упали — один повтор (§2.3 п. 3), снова упали — семантический конфликт (§4.3).
   - Повторного использования результатов проверок задачи нет: цикл требует, чтобы объединённый результат заново прошёл
     проверки, и копия объединения — новое окружение.
5. **С конфликтом** — §4.3.

Стратегия — **последовательный `merge --no-ff` по одной задаче**, в порядке «Готово».
- Не octopus: при конфликте он не говорит, какая пара столкнулась, и не умеет разрешение.
- Не rebase: он переписывает коммиты задачи. Тогда ветка задачи и контрольные точки её запуска перестают совпадать с
  тем, что проверялось и ревьюировалось.

Ходов модели запуск объединения без конфликта не делает.

### 4.3. Конфликт и упавшие проверки

Ветка задачи, общая вершина и копия объединения остаются как были. Работа не теряется. Автопилот в это время ждёт
(§5.2), а не выключается.
- Задачи, не зависящие от этой, продолжают идти.
- Объединения в эту вершину стоят до решения.

Пути разрешения:
- **Человек (C1 и настройка «Ко мне»).** Запуск объединения на паузе `merge_conflict` со списком файлов и путём к копии
  объединения. Действия:
  - «Открыть папку» — человек правит файлы копии своим редактором и нажимает «Готово, проверить». Main снимает снимок
    копии (шаг 3 §4.2), проверяет механическое условие (ниже) и прогоняет проверки. Рабочая папка пользователя не
    участвует;
  - «Поручить агенту» (с C3);
  - «Пропустить» — задача остаётся «Готово», но не в вершине. Зависимые от неё ждут с причиной «T-2 не объединена».
    Позже «Объединить» на задаче или в шапке доски начинает объединение заново (§4.5).
- **Агент (C3, по умолчанию с C3).** Тот же запуск объединения продолжается ходами:
  - план из одного этапа строит приложение, без лида. Задание исполнителю: «Разрешите конфликт в <файлы>, сохранив
    требования обеих задач». Требования обеих задач входят в цель запуска;
  - исполнитель работает в копии объединения в правах из профиля проекта на момент объединения. Снимок настроек
    автопилота (B §5.1) сверяется перед стартом, как для задач. Права не шире, чем у запусков задач того же профиля;
  - дальше обычный цикл A: проверки, проверяющий (отдельная сессия, видит требования обеих задач и diff слияния),
    замечания, лимиты.

**Механическое условие** (для человека и агента). Main сравнивает дерево разрешения с автоматическим слиянием
(`git merge-tree --write-tree`) вне списка конфликтных путей.
- Совпало — разрешение затронуло только конфликт, дальше проверки (и проверяющий, если разрешал агент).
- Не совпало — это не отказ: правильное разрешение иногда требует правки рядом (сигнатура в конфликте, вызов в
  соседнем файле). Объединение переходит в режим семантического конфликта (ниже). Список файлов вне конфликта, которые
  разрешение изменило, показан отдельно.
  - Если разрешал агент, проверяющий получает этот список. Удаление или откат чужой правки — блокирующее замечание.
  - Если разрешал человек, перед проверками — предупреждение со списком файлов и явное подтверждение «Да, я менял и
    их».

Так ни одна правка вне конфликта не проходит незамеченной: её видит либо проверяющий, либо человек.

**Упавшие проверки слияния** без конфликта — семантический конфликт. Он идёт тем же путём, но конфликтных путей нет, и
механическое условие запретило бы любую правку. Поэтому здесь оно другое:
- разрешению можно менять любые файлы;
- проверяющий (и человек в окне паузы) получает diff разрешения против автоматического слияния и требования обеих
  задач. Удаление чужих правок — блокирующее замечание;
- обязательные проверки должны пройти.

Это слабее механического условия: выброшенную правку здесь ловит ревью, а не сравнение деревьев. Остаток назван в
вопросе 3.

**Объединение не прошло** (агент не справился, лимит, остановка, механическое условие): задача остаётся «Готово» с
пометкой «не объединено: <причина>». Автопилот ждёт человека. Зависимые от неё ждут.

### 4.4. Что считается «Готово»

- **Задача «Готово»** — как в B: её собственный запуск `confirmed` (или «принято вами, без проверок»).
- **«В итоге доски»** — отдельная пометка: запуск объединения с ней завершён и вершина сдвинута. На карточке: «Готово ·
  в итоге доски», «Готово · объединяется», «Готово · не объединено: конфликт в src/auth.ts».
- **Итог доски** — вершина. В шапке: какие задачи в ней и «проверки прошли на <коммит>».
- **Проект без команд проверки.** Запуск объединения завершается `no_checks`: «Объединено без проверок». Это не
  подтверждение. Что дальше — вопрос 5: двигать вершину с пометкой «без проверок» (рекомендация) или требовать
  «Принять результат» на каждом объединении.
- Правкой `board.json` пометку «в итоге доски» получить нельзя: она выводится только из журналов запусков объединения
  (принцип 8).

### 4.5. Кто запускает объединение

- **Автопилот**, пока включён: после каждой задачи «Готово».
- **Сверка** при включении автопилота и при старте приложения. Main находит задачи «Готово» в «отдельной копии»,
  чей запуск стартовал от вершины (`goal.base` есть в истории текущей вершины), а результата в вершине нет
  (`merge-base --is-ancestor <коммит задачи> <вершина>`). Шапка доски показывает их: «Не объединены: T-2, T-4».
  - Включённый автопилот вливает их по одной, в порядке «Готово» по журналам.
  - После перезапуска сам ничего не начинает (как всё в оркестрации).
- **Задачи, стартовавшие не от вершины** (готовые до C, ручные запуски от рабочей папки), автоматически не вливаются.
  Их результат мог уже попасть в первую вершину через рабочую папку («Применить»), а база — другое состояние папки.
  Для них только «Объединить» вручную, с предупреждением: «T-1 стартовала не от общей вершины — возможны лишние
  конфликты».
- **Человек:** «Объединить» на задаче «Готово» и «Объединить все» (только задачи, стартовавшие от вершины) в шапке
  доски. Нужно для ручных запусков, после «Пропустить» и когда автопилот выключен.
- «Объединить» сначала создаёт ветку результата задачи, если её ещё нет («Создать ветку в проекте», тот же код, что
  решение 8). Её коммит — то, что вливается.

Порядок объединений выводится из журналов (время `completed` запусков задач), а не из памяти. После перезапуска он тот
же.

### 4.6. Восстановление

- Запуск объединения восстанавливается как любой запуск (`paused(recovered)` / `outcome_unknown`). После перезапуска
  ничего не продолжается само.
- Коммит слияния записывается в журнал (`merge.committed`) до движения вершины. Вершина двигается последним шагом,
  одной операцией `update-ref` со старым значением, и затем пишется `merge.advanced`. Возможны два сбоя:
  - **до движения** — вершина прежняя, запуск не `completed`;
  - **после движения, до записи** — сверка при старте приложения находит вершину, равную коммиту из `merge.committed`,
    и дописывает `merge.advanced` и `completed`. Проверки уже записаны: движение идёт только после них.

  Зависимые задачи не ждут, пока человек откроет запуск.
- Повтор объединения задачи, уже влитой в вершину (`merge-base --is-ancestor`), ничего не делает и называет этот запуск.

### 4.7. Пересечения заранее (C2)

Пока задачи идут, main после каждой контрольной точки этапа проверяет попарно: `git merge-tree --write-tree` для
последних контрольных точек идущих задач и вершины. Это без модели, в очереди git проекта; рабочую папку и ветки не
трогает. Если результат предсказывает конфликт, на карточках задач: «Пересекается с T-2 в src/auth.ts».
- Это предупреждение, а не решение: автопилот задачи не останавливает.
- Человек может «Остановить» одну из задач.

## 5. Изменения хранилищ

### 5.1. `board.json`

**Версия остаётся `v: 1`.** Новое — только необязательные поля в записи автопилота связи:
- `autopilot[linkId].parallel` — 1–4 (§2.1);
- `autopilot[linkId].conflicts` — `"agent" | "person"` (§4.3, с C3).

Что не хранится в `board.json`:
- общая вершина: её имя и место — ссылка в репозитории, что в неё влито — из журналов запусков объединения;
- пометки «в итоге доски» — из журналов.

Совместимость по образцу B:

| Сборка | Что делает с полями C | Последствие |
|---|---|---|
| 1.5.14 | не знает `autopilot`; при любой записи доски выбрасывает его целиком (как в B) | после возврата бюджет, параллельность и «Конфликты» — по умолчанию |
| 1.5.15–1.5.16 | читает запись автопилота как есть (`isBudget` пропускает лишние ключи) и сохраняет её при других записях; при смене бюджета этой связи пишет только `runs` и `minutes` | после смены бюджета в старой сборке параллельность и «Конфликты» этой связи — по умолчанию |
| ≤ 1.5.13 | файл не читает | файл цел |

Потеря параллельности после отката безопасна: по умолчанию 2 и «Ко мне» (до C3) или «Поручать агенту» — те же
значения, что при первом включении.

Почему не `v: 2`: сборки 1.5.14–1.5.16 открыли бы такую доску только для чтения (`newer_version`). Новые поля
необязательны и ничего не значат без автопилота C.

### 5.2. Журнал

**Обычные запуски задач не меняются: v2, как в B.** База от общей вершины — тот же `goal.base`, что в B4: это коммит
проекта, старая сборка понимает его так же.

**Запуски объединения — новая версия журнала v3** (`v: 3`, `minReaderVersion: 3`).

Почему не v2 по §2.2.1 п. 4. Запуск объединения работает иначе, чем цель v2:
- ходов нет совсем (без конфликта);
- план строит приложение, а не лид (с конфликтом);
- `completed` двигает общую вершину.

Сборка 1.5.16 разобрала бы цель v2 без строгой схемы и, продолжив такой запуск, пошла бы обычным циклом с лидом. Это
изменение смысла, а не необязательное поле, и по §2.2.1 п. 4 оно требует `minReaderVersion` выше читателя.

Что нового в v3 (только в запусках объединения):
- в цели — `merge: { board: <ссылка вершины>, base: <ожидаемая вершина>, task: { id, key, runId, commit } }`;
- запись `merge.prepared` — `{ conflicts: path[], auto: <дерево автоматического слияния> }`: шаг 2 §4.2 и основание
  механического условия;
- запись `merge.resolved` — `{ by: "person" | "executor", tree, outside: path[] }`: снимок разрешения и файлы вне
  конфликта, которые оно изменило;
- запись `merge.committed` — `{ commit }`: коммит слияния до движения вершины (§4.6);
- запись `merge.advanced` — `{ from, to }`: вершина сдвинута;
- план, который пишет приложение (`plan.recorded` с `by: "app"`).

Остальное — записи v2 без изменений.

Совместимость журнала:

| Сборка | Видит запуск объединения | Верно? |
|---|---|---|
| C (v3) | полностью | да |
| 1.5.8–1.5.16 (v2) | мост §2.2: `v > 2` → «создан более новой версией», только просмотр | да: старая сборка его не продолжит и вершину не двинет |
| 1.5.7 и раньше | как любой журнал новее себя | без изменений |

Обычные запуски задач, созданные сборкой C, остаются v2: старая сборка продолжает их как в B. Общая вершина — ссылка
git: после отката она в репозитории, старая сборка о ней не знает.

### 5.3. `canvas.json`

- **Запуски задач и обычных целей** — как сейчас: `link.runIds` и `owners`. Новое — только несколько активных запусков
  на одной связи (§3.1). Формат не меняется.
- **Запуски объединения не регистрируются на связях.** Их владелец — пространство (`owners`, ключ уже известен
  1.5.12+ и сохраняется ими). Список запусков объединения выводится из журналов: цель с `merge`.
  - Почему: запуск v3 на связи в старой сборке был бы `newer` и держал бы связь и всю папку проекта
    (`canvasStore.ts:61`). Отпустить его можно, только когда на связи нет незавершённого запуска v2
    (`link_active_run`), и отпускание удаляет связь целиком.
  - Запуск без связи старая сборка в правиле занятости не учитывает (`folderHolder` смотрит только связи).
- Старая сборка при откате видит несколько активных запусков на одной связи. Её правило `link_busy` не даст начать
  новый, пока они не кончатся; продолжить и остановить каждый она может.

**Проверка отката для C1:** упакованные 1.5.15 и 1.5.16 открывают профиль, где есть:
- запуск объединения (v3, без связи, в `owners`);
- два активных запуска v2 на одной связи;
- общая вершина в репозитории.

Ожидается:
- запуск объединения показан «созданным более новой версией» и ничего не держит;
- оба запуска v2 продолжаются и останавливаются;
- `board.json` и `canvas.json` после закрытия читаются сборкой C без потерь, кроме параллельности по §5.1.

## 6. Интерфейс

### 6.1. Доска

- Колонки те же. В «Работе» и «Проверке» может быть несколько задач. Счётчик в шапке: «Работа 2».
- В шапке доски:
  - «Вести доску · 2 параллельно · бюджет 3/10 запусков, 45/240 мин»;
  - итог доски: «T-1, T-2 · проверки прошли · Создать ветку · Применить» или «Объединение T-3: конфликт — решите»;
  - «Не объединены: T-4 · Объединить все»;
  - «Вершина отстаёт от HEAD рабочей папки на 3 коммита» — без автоматических действий: задачи идут от вершины, а
    «Применить» может начать отказывать. Новая вершина — действием человека (§4.1);
  - причина ожидания автопилота: «Ждёт лимита Claude», «Ждёт вас: T-1».
- Карточка задачи: пометка объединения (§4.4) и пересечение (§4.7) отдельными строками.

### 6.2. Карточки агентов нескольких запусков

Связь — пара карточек лида и исполнителя. При нескольких запусках на связи:
- **карточки не размножаются.** Карточка показывает, сколько задач у неё сейчас и что делает каждая, по строке:
  «T-1 · Claude выполняет этап 2/3», «T-2 · ждёт ответа». Строка — кнопка «Открыть запуск»;
- полоска действия под связью одна, с самой срочной причиной (тот же приоритет, что §4.3 B): «T-1 ждёт вас · ещё 1
  задача работает»;
- панель запуска открывается по задаче, как сейчас по запуску;
- запуск объединения с ходами показан на карточке исполнителя строкой «Объединение T-2 · Claude разрешает конфликт».
  Карточка — та, связь которой ведёт автопилот доски; при ручном «Объединить» — связь, на которой шла задача. Ходы
  идут как у запусков этой связи: её CLI, профиль проекта, свои сессии на запуск. Старт — новой операцией
  `startMerge` в той же очереди `canvasStore.change`, что `startOnLink`, но без записи в `link.runIds` (§5.3).

Так холст не превращается в кашу: число карточек от параллельности не зависит.

### 6.3. Уведомления и значок Dock

- Каждый запуск уведомляет о своём ожидании человека, как сейчас. Два одновременных ожидания — два уведомления с
  названиями задач.
- Новые уведомления доски: «Объединение T-2 — конфликт, решите» и «Итог доски обновлён: T-1, T-2 · проверки прошли»
  (второе выключено по умолчанию).
- Значок Dock считает и запуски объединения, ждущие человека.

## 7. Стоимость

- **Бюджет автопилота доски** (B4) остаётся единственным ограничителем и считает всё:
  - запуски задач;
  - запуски объединения с ходами — как запуск. Объединение без ходов бюджет запусков не тратит, его проверки идут в
    рабочие минуты;
  - минуты — сумма рабочего времени всех запусков, а не время по часам. Две задачи по 10 минут — 20 минут бюджета.
- По умолчанию 5 запусков и 240 минут, как в B. При параллельности 2 бюджет кончается вдвое быстрее по часам. Это
  сказано в окне включения: «2 задачи сразу: 240 рабочих минут — это около 2 часов».
- Исчерпание бюджета: новые задачи не начинаются, начатые доходят сами. Когда активных не осталось — автопилот
  выключен с причиной.
- Расход виден в шапке доски и на карточке каждой задачи (вызовы и токены, как в B). Неизвестная стоимость не
  приравнивается к нулю: Codex стоимость не сообщает, показываются токены.
- Денежного лимита нет (у Codex его нет; ROADMAP, «Вне MVP»).

## 8. Автопилот с N слотами: ожидание и выключение

Заменяет таблицу B §5.2 для параллельности. **Ждёт** — продолжит сам. **Выключен** — с причиной, включает человек.

| Событие | Исход |
|---|---|
| Свободный слот, есть задача без причины | берёт её |
| Нет задач без причины, но есть активные запуски, объединения в очереди или задачи, ждущие объединения | ждёт: «Остальные ждут: T-3 (ждёт объединения T-1)» |
| Нет задач без причины, нет активных запусков и объединений | выключен: «Всё готово» или «Остальные ждут: T-4 (ждёт T-3)» |
| Запуск ждёт человека (вопрос, разрешение, решение, «по шагам», `no_checks`) | ждёт; слот занят, другие слоты работают |
| Запуск `stopped`, `failed`, пауза `limit_reached` или другая не ждущая человека пауза | новые задачи не берёт; выключен, когда активных не осталось |
| Лимит провайдера распознан (§2.4) | ждёт, пока пауза не уйдёт |
| Объединение на паузе (конфликт, проверки, механическое условие) | ждёт человека; задачи, не зависящие от этой, идут |
| Вершина не та, что ожидалась (человек сдвинул ссылку) | выключен с причиной |
| Бюджет исчерпан | новые не начинаются; выключен, когда активных не осталось |
| Настройки проекта изменились (снимок B §5.1) | новые не начинаются; выключен, когда активных не осталось |
| Человек выключил | выключен; начатые идут дальше |
| Перезапуск приложения | выключен (как в B); сверка §4.5 показывает необъединённые |

В каждой строке «ждёт» есть выход: ответ человека, конец запуска или объединения. Ожидание без активных запусков и без
ждущего человека не бывает: такое состояние — выключение с причиной.

## 9. План реализации C1–C4

Каждый подэтап — отдельный PR со своими тестами и smoke; приёмка — по критериям C из цикла.

| | Что | Проверка |
|---|---|---|
| **C1 — две независимые задачи параллельно и итог доски** | новое правило занятости (§3.1) для «отдельной копии»; «папка проекта» и worktree — по правилам B (§2.1); `link_busy` ослаблен; параллельность автопилота 1–4 и таблица §8; очередь проверок и очередь git проекта; общая вершина (§4.1), старт задач от неё; запуск объединения без конфликта (v3, без ходов, коммит собирает main); при конфликте или упавших после повтора проверках — пауза для человека с разрешением в копии объединения и механическим условием; сверка и «Объединить» (§4.5); пометки на доске «в итоге доски / объединяется / не объединено: причина»; «Объединено без проверок» для проекта без команд; кнопка «Создать ветку из итога доски» и «Применить» на вершине; карточка агента: «N запусков» и переключатель между ними | тесты: гонки §3.4; выбор двух задач на одном снимке; вершина двигается только после `confirmed` и только с ожидаемой; механическое условие ловит выброшенную правку вне конфликта; конфликт ничего не теряет; сбой до и после `update-ref` (§4.6); таблица §8 построчно; откат на упакованные 1.5.15 и 1.5.16 (§5.3); smoke `board-parallel-ui` на подставных CLI: 2 задачи сразу, объединение, конфликт, разрешение человеком; реальная проба: 2 независимые задачи + объединение, не больше 12 вызовов |

копия фикстуры, «Рабочая папка», хеши `config.toml` и настроек Claude до и после.

## 10. Связь с этапом D (EXP-SPEC-01)

Что C даёт для D (EXP-SPEC-01 §9):
- параллельные рабочие копии и общую вершину с проверкой объединения. Это база сравнения для D: «обычное исполнение с
  разрешённым параллелизмом» (§6);
- запуск от явной базы (`goal.base`, вершина) — способ записать, на какой версии кода построена работа;
- правило «в итог доски попадает только подтверждённое» — то, на что опирается «предварительный результат не
  объединяется»;
- предсказание пересечений (§4.7) — заготовка для условия отмены предположения.

Что C оставляет D:
- старт зависимой задачи **до** «Готово» зависимости, на предположении;
- состояния «предварительный», «устаревший», «отклонённый»;
- пересчёт после изменения зависимости. Сейчас есть только пометка «зависимость менялась после готовности» (B §4.2).

C не стартует задачу, пока её зависимости не в вершине. Ни одна задача C не работает на предположении.

## 11. Открытые вопросы владельцу

Решены 2026-10-10 — см. «Решения владельца» в начале документа. Вопрос 6 решён иначе, чем рекомендовано.

1. **Несколько запусков на одной связи или несколько связей?**
   - (а) До N запусков на одной связи, карточки не размножаются (§6.2).
   - (б) Параллельность = несколько связей проекта (человек создаёт N пар карточек), правило «один запуск на связь»
     остаётся.

   **Рекомендация:** (а). Меньше ручных действий, холст не растёт, а сессии CLI и так раздельны по запускам.
2. **Отступления от цикла.**
   - C1 на «отдельной копии», worktree — в C2 (цикл: «каждый в своём worktree»).
   - Конфликт решается при вливании, а заранее только предупреждение (цикл: «конфликты выявляются до объединения»).

   **Рекомендация:** принять оба. Копия — режим по умолчанию для новых проектов и не пишет в `.git/worktrees`
   пользователя. Предупреждение заранее (§4.7) выполняет смысл правила: человек узнаёт о конфликте до вливания и
   может остановить задачу. Запрещать старт пересекающихся задач нельзя: пересечение видно только после правок.
3. **Конфликт по умолчанию — агенту или человеку?**
   **Рекомендация:** с C3 — агенту, с механическим условием, проверяющим и общими проверками; в C1 — человеку.
   Разрешение не трогает папку пользователя и идёт в тех же правах, а «Готово» по-прежнему решают проверки.
   Остаток: при семантическом конфликте (проверки упали без конфликта git) потерю чужой правки ловит только
   проверяющий (§4.3). Если это неприемлемо, семантический конфликт всегда идёт к человеку.
4. **Нужен ли проверяющий при объединении без конфликта?** Сейчас — только общие проверки, без модели.
   **Рекомендация:** без проверяющего. Обе задачи уже прошли ревью, механических конфликтов нет, семантический ловят
   проверки на дереве слияния. Проверяющий удвоил бы стоимость каждого объединения.
5. **Проект без команд проверки.** Каждое объединение завершается «без проверок».
   - (а) Вершина двигается с пометкой «Объединено без проверок» — итог доски никогда не выглядит подтверждённым.
   - (б) На каждом объединении «Принять результат» — лишнее действие на каждую задачу поверх «Принять» самой задачи.

   **Рекомендация:** (а): задачи уже приняты человеком без проверок, а итог честно помечен.
6. **Повтор после лимита провайдера.** Сейчас — «Продолжить» руками (§1, сценарий 5).
   **Рекомендация:** в C — руками. Автоповтор по таймеру — когда CLI начнут сообщать время сброса в разбираемом
   виде; отдельная задача.
7. **Журнал v3 для запусков объединения или объединение как обычная цель v2 с лидом?**
   - (а) v3 (§5.2): без конфликта ходов нет, старые сборки только показывают.
   - (б) v2: объединение — обычная цель, которую ведёт лид (план, ход, ревью). Формат не меняется, но каждое
     объединение стоит 3–4 вызова модели, и лид может «разрешить» то, чего не было.

   **Рекомендация:** (а).
8. **Общая вершина — ссылка приложения или ветка?**
   - (а) `refs/raoden/board/…`: двигается только приложением, человек не может на ней стоять, `push --all` её не
     публикует; ветку человек создаёт кнопкой.
   - (б) Ветка `raoden/board-…` в `refs/heads`, которую двигает приложение. Человек может переключиться на неё, и
     тогда движение сдвинет HEAD под его рабочей папкой.

   **Рекомендация:** (а).
9. **Решение 11 при включённой общей вершине.** Линейная цепочка B стартовала от ветки зависимости сразу после её
   «Готово». В C зависимая задача ждёт, пока результат зависимости вольётся в вершину (проверки без модели).
   **Рекомендация:** принять: одна модель для цепочки и для нескольких зависимостей. Цена — время проверок одного
   объединения на каждую задачу цепочки.
10. **Одна общая вершина на пространство и проект или по группе задач?**
    **Рекомендация:** одна на пространство и проект. Новая начинается действием «Начать новую общую вершину».
11. **Режимы без общей вершины.** Общая вершина и объединения — только для «отдельной копии» (с C2 — и worktree). В
    «папке проекта» автопилот работает строго по правилам B: по одной задаче, без объединений (у результата нет своего
    коммита, он уже в папке).
    **Рекомендация:** принять. Иначе зависимые задачи «папки проекта» ждали бы объединения, которое невозможно, —
    регресс B.
