## 1. Четыре слоя имени

1. **Пользовательское название продукта.** Всё, что человек читает:
   - заголовок окна и `<title>`;
   - меню приложения и окно «О программе»;
   - сообщения и тексты интерфейса (i18n: ru и en; документация — три языка);
   - имя `.app` и установочных артефактов;
   - актуальные инструкции.

   → **переименовывается** в Raoden Loom.
2. **Имя пакета и устанавливаемого приложения** — `package.json` `name`, `productName` сборщика, `.app`, каталог
   установки Windows, пакет deb, `.desktop`. Меняется только то, что по §4 не влияет на данные.
3. **Техническая идентичность** — внутреннее имя приложения (`app.getName()`), `appId`, userData, ключ системного
   хранилища, схемы, IPC, API плагинов, переменные окружения, Git refs и трейлеры, имена MCP и служебных файлов.
   → **сохраняется** как `canvastty`.
4. **Внешние ресурсы** — репозиторий, сайт, публикации, Even Hub. → не меняются в этом этапе.

## 2. Главный критерий

После обновления существующий пользователь видит свои:

- настройки;
- пространства и карточки;
- историю;
- плагины;
- браузерные данные;
- сохранённые входы.

**Сохранённые входы и секреты** (вход в GitHub, секреты плагинов в safeStorage):

- **Успех** — выполнены все три условия:
  - новая сборка читает секреты, сохранённые прежней;
  - после проверки отката прежняя сборка продолжает их читать;
  - ни одна ошибка расшифровки не удаляет, не перезаписывает и не обнуляет сохранённые значения.
- Повторная авторизация **не является** равнозначным успешным вариантом.
- Если доступ сохранить нельзя, соответствующее изменение имени **заблокировано** до принятия конкретного решения
  (§4, S0-5). Новая схема хранения молча не вводится.
- Нужно различать два разных события:
  - **запрос macOS на доступ к записи Keychain** — диалог разрешения; данные целы, после разрешения расшифровываются;
  - **потерю возможности расшифровать** — ключ недоступен или другой; это нарушение критерия.

**Данные и профиль:**

- **Данные остаются на месте**, каталоги ради красоты не переносятся.
- **Пустой профиль не открывается незаметно.**
- **Старая и новая сборки не пишут одновременно** в один профиль.
- **Git refs, трейлеры, `runId` и владельцы пространств не меняются.**

**Порядок инициализации** (сохранить и закрепить регрессией):

1. Выбор профиля. Chromium берёт `--user-data-dir` при старте процесса; `CANVASTTY_USER_DATA_DIR` применяется в
   первых строках main (`src/main/index.ts:61`).
2. Регистрация схем.
3. Блокировка единственного экземпляра (`index.ts:141`); второй экземпляр завершается.
4. Только затем `ready` → миграция → хранилища → браузерные сессии → фоновые службы.

**Приоритет профилей** (существующее поведение, измерено в §4):

- задан только `--user-data-dir` → используется он;
- задана только `CANVASTTY_USER_DATA_DIR` → хранилища в ней. Но Chromium успевает создать `Crashpad` в каталоге
  профиля по умолчанию, то есть в настоящем профиле (S0-2);
- заданы оба → хранилища в `CANVASTTY_USER_DATA_DIR`, каталог из `--user-data-dir` создаётся и остаётся пустым (или
  получает `Crashpad`);
- не задан ни один → `appData/<app.getName()>`.

Тесты и проверки используют `--user-data-dir`: только он не трогает настоящий профиль. Поведение
`CANVASTTY_USER_DATA_DIR` не меняется, ограничение описывается в документации.

## 4. Результаты S0 (macOS)

### Условия

- **Среда:** macOS 27.0 arm64, Electron 43.2.0, electron-builder 26.15.3.
- **Где собиралось:** только во временных каталогах scratchpad, `--dir` (без DMG). Команды:
  `electron-builder --mac dir -c.directories.output=<tmp> [-c.productName=…] -c.npmRebuild=false`. Конфигурация
  выпуска и checkout не менялись; `git status` до и после совпадает.
- **Профили и HOME:** временные.
  - Для реального приложения профили лежали в `/tmp/cto-s0-*`: путь сокета агентского браузера
    (`userData/browser/runtime/*.sock`) ограничен 100 байтами, из scratchpad не помещается.
  - `PATH=/usr/bin:/bin:/usr/sbin:/sbin`: CLI агентов не найдены, модели и настройки CLI не затрагивались.
  - Временные каталоги после проверки удалены.
- **Что именно проверялось о данных пользователя** (подробно — в evidence):
  - `lsof` главного процесса в моменты U1–U3 и F: разовые снимки, файлов настоящего профиля нет;
  - список имён в `~/Library/Application Support` до и после совпал;
  - время изменения каталога настоящего профиля то же (01:08), то есть не добавлялись и не удалялись записи
    верхнего уровня;
  - в Keychain по пяти именам записей нет — ни до, ни после.

  **Побайтового сравнения настоящего профиля не было.** Утверждения, что он не изменился побайтово, нет.
- **Доказательства:** [evidence/rename-s0](../evidence/rename-s0/README.md) — обезличенные результаты, в том числе
  неудачные прогоны, скрипты, команды и полные SHA-256.

### Пробелы

- **Вход в GitHub — исправлено до переименования (2026-09-28).**
  - `GithubAuthService` различает «входа нет» и «сохранённый вход недоступен»: новое поле статуса
    `storedSessionUnavailable`; в настройках плагинов показывается отдельное сообщение с собственной кнопкой
    «Отключить».
  - Пока хранилище ключей недоступно, новый вход в файл не пишется.
  - Если файл не расшифровывается, новый вход сначала **копирует** его рядом байт в байт
    (`github-oauth.previous-<мс>-<случайное>.json`; одинаковая копия не дублируется).
  - Основной файл никогда не перемещается. Его заменяет только `rename` полностью записанного нового файла. Поэтому
    при сбое `encryptString`, сбое записи или прерывании между шагами на месте остаются прежние байты или новый файл,
    и копия.
  - Первая версия исправления (2026-09-28) переносила файл до шифрования. При сбое шифрования основного файла не было,
    а `load` при его отсутствии копии не проверял. Внешнее ревью это воспроизвело; исправлено.
  - `load`:
    - сначала читается основной файл, затем копии — новее первыми по времени в имени, при равенстве по имени, имена
      без времени последними; порядок `readdir` не используется;
    - копии проверяются и тогда, когда основного файла нет;
    - «недоступен», если есть хоть один существующий, но нечитаемый файл; «входа нет» — только если сохранённых файлов
      нет;
    - чтение ничего не переписывает.
  - «Отключить» остаётся явным удалением основного файла, всех копий и оставшихся после прерывания `*.tmp`.
  - Отказ или ошибка новой авторизации файлов не меняют.
  - Регрессии: `tests/github-auth-stored-session.test.mjs` (12 тестов) и внешние репро ревью
    (`/private/tmp/raoden-github-storage-review.test.mjs`, до исправления 0/2, после 2/2). Проверки мутациями (набор: оба файла GitHub и репро), сколько
    тестов падает:

    | Мутация | Падает |
    |---|---|
    | перенос вместо копии | 2 |
    | ранний выход при отсутствии основного файла | 4 |
    | нечитаемая копия не учитывается | 3 |
    | лексический порядок | 1 |
    | без устранения дублей | 1 |
    | «Отключить» оставляет `*.tmp` | 1 |
    | без копии | 5 |
    | без кнопки | 1 |

  - Тесты ждут конкретную операцию: запись, поставленную в очередь вместе с новыми токенами, или завершение опроса.
    Фиксированной паузы нет. Прежняя пауза 20 мс скрывала, что тест «обычный вход» не ждал записи.
  - Интерфейс проверен в dev-сборке на временном профиле с ключом Chromium `--use-mock-keychain`, без настоящей связки
    ключей:
    - нечитаемый `github-oauth.json` даёт сообщение с `role="status"`, файл при этом побайтово не меняется;
    - «Отключить» убирает сообщение и файл;
    - записей `… Safe Storage` до и после нет.
  - Ограничение **не закрыто** этим исправлением: прежняя сборка читает только основной файл. Если после ошибки
    расшифровки был выполнен новый вход, при откате она прежний вход не увидит (он сохранён в копии).
- **Секреты плагинов** (`PluginSecretsService.read`). Ошибка расшифровки прерывает операцию, файл не перезаписывается.
  Удаление плагина стирает файл — так и задумано.
- **`CANVASTTY_USER_DATA_DIR`** без `--user-data-dir` создаёт `Crashpad` в настоящем профиле (S0-2). Для проверок
  использовать только `--user-data-dir`. Менять ли поведение переменной — отдельное решение.

## 7. Откат

- Данные не переносятся, `name` не меняется, поэтому прежние сборки открывают тот же профиль (S0-1, S0-4).

  - любая потеря данных в проверках §6;
  - открытие пустого профиля;
  - нечитаемый секрет (S0-5).
