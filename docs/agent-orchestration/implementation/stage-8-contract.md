# Контракт этапа Р8: модель renderer и интерфейс оркестрации на холсте

Строки 7–8 таблицы этапов ROADMAP, поверх принятого Р7 (движок в main, IPC `orchestration:*`, preload). Архитектура — ARCHITECTURE-PROPOSAL §10. Реальные модели в Р8 не запускаются; интерфейс проверяется на тестовых провайдерах (fake CLI через `CANVASTTY_ORCHESTRATION_TEST_PROVIDERS`, только в неупакованной сборке).

## 1. Пользовательский сценарий

1. Правый клик по пустому холсту → «Агент Codex (лид)» / «Агент Claude (исполнитель)». Диалог спрашивает папку проекта (ввод пути или системный выбор). На холсте появляется карточка агента: провайдер, роль, проект, состояние.
2. Пользователь тянет мышью порт карточки Codex (круг справа) на карточку Claude. Связь «лид → исполнитель» рисуется CSS-линией со стрелкой; посередине — плашка связи: состояние последнего run и кнопки «Новая цель», «Открыть запуск», «×» (удалить). Если связь недопустима, main её отклоняет, а карточка лида показывает причину (8 с или до следующего действия).
3. «Новая цель» на плашке связи открывает диалог: проект (папка лида, только чтение), задача, критерии (по строке), проверки из каталога main, лимиты (ходы, раунды на этап, перепланирования, минуты), «Показать план перед выполнением» (выключено). «Старт» создаёт run: лид сам разбивает задачу на этапы.
4. «Открыть запуск» (на плашке или на карточке) открывает панель запуска справа. Пока run связи активен, на плашке нет ни «Новой цели», ни «×»; main всё равно отказывает `link_busy` / `link_active_run`. Удаление карточки, у которой есть связь, спрашивает подтверждение на самой карточке.
5. На панели запуска (история — §1.1):
   - состояние и понятная причина паузы;
   - текущий этап, кто работает (лид, исполнитель, проверка);
   - план, история, результаты проверок, итог;
   - кнопки — только допустимые в текущем состоянии;
   - ответ на вопрос агента и уточнение.

### 1.1. Содержание истории (ревью Р8)

Строка истории со ссылкой на текст журнала раскрывается кнопкой; текст читается через `orchestration:text` (только по ссылке из журнала этого run):

- «Отчёт исполнителя» — `turn.finished.report.ref` хода `execute`;
- «Замечания лида» — `review.recorded.findings`, если `findingsCount > 0`; показываются списком;
- «Вывод проверки» — `check.finished.output`. Строка проверки показывает id проверки, результат, причину `not_verified` словами и код выхода упавшей проверки; при обрезанном выводе — сколько байт отброшено.

Отчёт хода, который не завершился, тоже раскрывается. Если журнал не сохранил текст (`ref` нет), так и сказано вместе с причиной: ход не завершился, отчёта нет, отчёт не прошёл схему или ошибка хранения. Ошибка загрузки (отказ main или транспорт) показывается с причиной и кнопкой «Повторить».

## 2. Владение состоянием

- **Main — источник истины.** Run и его состояние — `OrchestrationService` (Р5–Р7). Карточки агентов и связи — `canvasStore.ts`: `<userData>/orchestration/canvas.json`, атомарная запись, одна очередь записи. Геометрия карточек хранится там же, отдельно от журналов run, поэтому перемещение не меняет `revision` run и не инвалидирует `expectedRevision`.
- **Renderer** хранит только отображение:
  - снимок холста (ответы main на операции);
  - подписки на run через `watch` (снимок + события по `(seq, tick)`, Р7 §2.2);
  - черновики форм и ожидающие команды.
  Второй машины состояний нет. Доступные кнопки вычисляются из `view` (статус и причина) по тем же правилам, что у сервиса; окончательное решение — за main (`rejected` показывается).
- **Идемпотентность.**
  - `requestId` создания run живёт, пока не меняется форма цели: повтор «Старт» после транспортной ошибки отправляет тот же id.
  - Команда запуска хранится **целиком** (`commandId`, `expectedRevision`, payload), пока main не ответил (ревью Р8). Действие определяется парой «run + payload»; revision, с которой команда ушла, остаётся при ней. Повтор после транспортной ошибки отправляет тот же запрос, даже если состояние run уже сменилось, — main находит `commandId` в журнале раньше проверки revision и возвращает записанный ответ, ничего не делая повторно. Подставить новую revision к старому id нельзя: это другой payload (`command_id_reused`). Ожидающие запросы хранятся в `sessionStorage` и переживают перезагрузку окна; панель показывает «результат неизвестен» и кнопку «Повторить» для каждого. Любой ответ main (принято, отказ, `stale_revision`) завершает запрос; следующее нажатие — новое действие.
  - `stale_revision` → обновить снимок (`get`) и не повторять.
  - Карточка и связь создаются с id от renderer; повтор той же операции возвращает существующую сущность.
- **Ошибки.**
  - Транспорт (`invoke` отклонён) показывается как «нет связи с приложением, повторите».
  - Отказ операции (`{ok:false, code}`) и отказ команды сервиса (`{status:"rejected", code}`) показываются локализованной причиной.
- **Перезагрузка окна** не создаёт run и не продолжает остановленный: renderer только читает холст, `list` и подписывается.

## 3. Карточки и связи в main

| Операция (IPC) | Проверки в main |
|---|---|
| `orchestration:canvas` | — (читает `canvas.json`; процессов нет) |
| `orchestration:agent-create {agentId, provider, project, bounds}` | provider `codex`/`claude` (роль следует из провайдера: Codex — лид, Claude — исполнитель), `project` — существующий каталог (хранится `realpath`), bounds — конечные числа в пределах холста; повтор того же `agentId` с теми же данными — та же карточка |
| `orchestration:agent-move {agentId, bounds}` | карточка существует; меняется только геометрия |
| `orchestration:agent-delete {agentId}` | если у карточки есть связь с активным run → `link_active_run`; иначе удаляет карточку и её связи |
| `orchestration:link-create {linkId, fromAgentId, toAgentId}` | карточки существуют; `link_self`; `link_roles` (только Codex-лид → Claude-исполнитель); `link_duplicate` (пара уже связана); `link_projects` (разные `realpath` проектов); повтор того же `linkId` и пары — та же связь |
| `orchestration:link-delete {linkId}` | активный run связи (`preparing`, `running`, `pausing`, `paused`, `stopping`) → `link_active_run`; иначе удаляет связь; журналы, refs и карточки остаются |
| `orchestration:link-start {linkId, requestId, goal}` | связь существует; у связи нет активного run (`link_busy`); источник — проект лида (renderer его не передаёт); далее `manager.create` (Р7: идентичность запроса, провайдеры, зависимости); `runId` добавляется в историю связи |

Связь хранит `runIds` (история запусков); панель показывает последний. После удаления связи прежние run остаются в `orchestration:list`.

### 3.1. Запуск на связи и его принадлежность (ревью Р8)

`runId` = `requestId`, поэтому принадлежность записывается **до** создания run (упреждающая запись):

1. В очереди `canvas.json`: проверка занятости (собственный run этого `requestId` не учитывается, любой другой активный → `link_busy`).
2. `requestId` дописывается в `link.runIds` атомарной записью. Не удалось записать → `store_failed`, run не создаётся.
3. `manager.create`. Созданный run уже принадлежит связи; больше писать нечего, и сбой записи после создания невозможен.
4. Создание отказало, и run с этим id не существует (или `request_conflict`: id принадлежит другому запросу) → резерв снимается. Если и эта запись не удалась, резерв остаётся «пустым».
5. Повтор того же `requestId` (id уже в `runIds`) снова вызывает `create`, который отвечает идемпотентно (`created:false`) или создаёт run, если прошлая попытка остановилась до создания.

Пустой резерв — id без журнала (`runs/<id>/journal.jsonl` нет): процесс завершился между шагами 2 и 3, или не удалось снять резерв. `orchestration:canvas` его не показывает, занятость его не учитывает. После перезапуска связь находит свой run по журналу; run не открывается и не продолжается сам (Р7 §5). Блокировка в памяти — только очередь записи внутри процесса; согласованность между процессами и перезапусками даёт упреждающая запись. Ошибки файловой системы при записи холста приходят как `store_failed`.

## 4. Жесты

- Порт — кнопка на правом крае карточки лида. Нажатие захватывает указатель. Группового перемещения нет: порт — контрол карточки. Панорамирования тоже нет: карточка `data-interactive`. Во время жеста рисуется линия предпросмотра в мировых координатах, с учётом масштаба. Отпускание над карточкой агента → `link-create`; над пустым местом — отмена.
- Карточка агента — слой `agent:<id>`: перемещение за заголовок, snapping, выделение рамкой и групповое перемещение как у заметок. Изменение размера не нужно: размер фиксирован.
- Связь — линия под карточками (без событий указателя) и плашка с кнопками в середине линии. Плашка рисуется после карточек с z-index старшей из двух карточек связи: свои карточки её не закрывают, даже вплотную, а окна, поднятые выше, остаются сверху; выбора линии и клавиши Delete нет — удаление кнопкой «×».
- Клик по порту без перетаскивания (или Enter/Space на порту) включает режим связывания: внизу подсказка, у карточек Claude кнопка «Связать сюда»; Escape или повторное нажатие порта отменяет. Так связь создаётся без мыши: Tab до порта, Enter, Tab до «Связать сюда», Enter.
- Панель запуска и диалоги — поверх холста (`data-interactive`, `data-wheel-owner="local"`, `data-canvas-wheel-priority="local"`: колесо прокручивает панель, а не холст — до ревью Р8 холст забирал колесо); нативный вид браузера скрывается, пока открыты диалог или панель. Escape закрывает диалог и панель.

## 5. Критерии готовности

- Сценарий §1 проходит в настоящем интерфейсе Electron на тестовых провайдерах:
  - completed;
  - пауза на плане;
  - виден активный исполнитель;
  - Stop;
  - перезагрузка окна без дублей и без продолжения;
  - перезапуск приложения с сохранёнными карточками и связью;
  - удаление связи после остановки.
  Снимки основных состояний прикладываются.
- Проверки связи действуют в main (тесты без renderer).
- Перемещение карточки не меняет `revision` run.
- Терминальные карточки не меняются (регрессии `npm test`); строки в обеих локалях (ru, en).
- Не входит в Р8:
  - следование карточек агентов за регионом при его перемещении;
  - отображение на миникарте;
  - пункты в палитре команд (`Cmd/Ctrl+K`) и радиальном меню — только контекстное меню холста;
  - «Новая цель в этой папке» из меню терминала;
  - выбор более старого run связи в панели (история run доступна через `list`).

## 6. Проверка

- `tests/orchestration-canvas.test.mjs` — хранилище холста и IPC в main (5).
- `tests/orchestration-renderer-model.test.mjs` — допустимые действия, состояние карточек, свёртка журнала, стабильные id, порядок `(seq, tick)`, строки ошибок/причин/статусов в ru и en (7).
- `tests/orchestration-r8-review.test.mjs` — регрессии ревью Р8 (6): сбой записи холста после и до создания run, пустой резерв, перезапуск; clarify и Step с потерянным ответом; сохранение ожидающего запроса при перезагрузке окна.
- `npm run smoke:orchestration-ui` (после `npm run build`) — настоящее окно Electron через DevTools Protocol: события мыши и клавиш как у пользователя, снимки. Каждая точка нажатия проверяется попаданием (`elementFromPoint`): карточка ставится только на пустой холст, найденный перебором; недоступный элемент показывается панорамированием перетаскиванием пустого холста или колесом над панелью; клик только если элемент действительно под указателем. Сценарии и результаты — VALIDATION-MATRIX U1–U19.
