# Troubleshooting: оркестрация «Лид → Исполнитель»

Только реально обнаруженные проблемы и проверки, которыми их подтверждали. Эксперименты: `docs/agent-orchestration/experiments/`.

## Безопасность рабочей копии

### T1. Hook, записанный из linked worktree, исполняется в исходном репозитории

- **Симптом:** файл `post-checkout`, созданный в `$(git rev-parse --git-common-dir)/hooks` из worktree, выполнился при `git checkout` в исходном репо.
- **Причина:** linked worktree делит с исходным репо `config`, `hooks`, `refs` и `objects`.
- **Проверка:** `experiments/permissions/README.md`, раздел git, шаги 3–5; lead повторил независимо.
- **Решение:** рабочая копия — `git clone --shared --no-checkout`, а не worktree.

### T2. Plumbing-снимок оркестратора исполняет `core.fsmonitor` и `reference-transaction` hook

- **Симптом:** при `git add -A` во временный индекс и `update-ref` сработали fsmonitor (4 раза) и hook `reference-transaction`.
- **Причина:** plumbing-команды читают локальный config и запускают хуки.
- **Решение:** все вызовы git из оркестратора — `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`. С этими флагами журнал хуков пуст.

### T3. Подмена `commondir` или файла `.git` перенаправляет discovery

- **Симптом:** после замены `<common>/worktrees/<wt>/commondir` на поддельный каталог с `core.fsmonitor` код исполнялся и при `git -C <wt> status`, и при `GIT_DIR=<common>/worktrees/<wt>`.
- **Решение:** не использовать discovery. Вызывать только `GIT_DIR=<gitdir> GIT_WORK_TREE=<copy> GIT_INDEX_FILE=<tmp>` с hardened-флагами.

### T4. Обычный локальный `git clone` делает жёсткие ссылки на объекты

- **Проверка:** `stat` объекта показывает 2 ссылки.
- **Решение:** только `--shared` (или `--no-hardlinks`).

## Runner проверок

### T5. Probe Seatbelt давал ложное «denied»

- **Симптом:** `bash sb.sh sh probe.sh` показывал `read-secret: denied`, но `ls-secret: ALLOWED` и `write-tmp: denied`.
- **Причина:** обёртка не передавала `SECRET` и `TMP`; `cat $SECRET/key` превращался в `cat /key`, и отказ был не от песочницы.
- **Решение:** `sb.sh` сам передаёт все переменные; `probe.sh` завершается `FAIL: X is empty` (rc=2) при пустой переменной. Правило для любых probe: контрольный прогон без песочницы должен давать `ALLOWED` на всех строках.

### T6. Проба keychain неинформативна

- **Симптом:** `security find-generic-password` для несуществующего элемента даёт отказ и без песочницы.
- **Решение:** использовать только косвенную пробу `security show-keychain-info` (rc 0 без песочницы, 206 в ней) и явно пометить её как косвенную.

### T7. PTY-проба в песочнице падает при stdin-сокете

- **Симптом:** `script` внутри профиля падает с `tcgetattr/ioctl`, если stdin — сокет.
- **Решение:** запускать с `</dev/null`.
- **Связанное ограничение (не решено):** openpty требует read+write на все `/dev/ttys*`, поэтому opt-in `pty` открывает и чужие tty того же uid (проверено на pty, созданном вне песочницы). `(allow pseudo-tty)` + только `/dev/ptmx` даёт `openpty: Operation not permitted`. Сузить не удалось; это **не обеспечено**, а не принятый риск. Минимальный профиль PTY не даёт.

### T8. localhost в runner не различает владельца порта

- **Наблюдение:** в ревизии 2 профиль разрешал `localhost:*` целиком. Сужение до `localhost:PORT` работает по номеру порта, но чужой сервис на том же порту доступен; bind `0.0.0.0:PORT` разрешён, и сервер в песочнице принимает подключения на LAN-IP машины. Хост в правиле Seatbelt — только `localhost` или `*`.
- **Статус:** **не обеспечено**; ревизия 2 ошибочно называла это «принятым риском MVP» — пользователь его не принимал. Минимальный профиль сети не даёт; unix-сокеты внутри `TMP` (opt-in `unix`) изолируются и рекомендуются вместо TCP.

### T15. Сетевые пробы ревизии 2 ничего не доказывали

- **Симптом:** `net.js` в песочнице давал «denied» для внешнего TCP и DNS.
- **Причина:** корневой `package.json` задаёт `"type":"module"`; `net.js` (CommonJS) падал с `require is not defined` и внутри, и снаружи — «denied» было ошибкой скрипта, а не песочницы. Контрольный прогон вне песочницы не сверялся построчно. То же касается `detach.js` (VALIDATION-MATRIX P14 → H).
- **Решение:** пробы переименованы в `.cjs`; `validate.sh` выполняет каждую проверку сначала вне песочницы и падает (rc≠0), если положительный контроль не прошёл. Повтор урока T5.

### T16. Узкий allow внутри запрещённого каталога ломает `cd`, `realpath` и git

- **Симптом:** в копии внутри запрещённого userData: `Not a directory`, `unable to normalize alternate object path`, `bad object HEAD` у `git log` в `clone --shared`.
- **Причина:** deny на предков запрещает и их stat; alternates копии указывают на `.git/objects` исходного репо, которое запрещено целиком.
- **Решение:** `file-read-metadata` (stat, не readdir) через `path-ancestors` для разрешённых путей; read-only allow на `SRCREPO/.git/objects`. Следствие: объекты истории исходного репо читаемы тестами.

### T17. Seatbelt сравнивает реальные пути

- **Симптом:** правило с `/tmp/...` не срабатывает: реальный путь — `/private/tmp/...`.
- **Решение:** `sb.sh` отказывается запускаться (rc=2), если параметр не равен своему `pwd -P`. Лимит `sun_path` 104 байта: unix-сокет в `<userData>/runs/<id>/tmp` открывается по относительному пути.

### T18. Deny на чтение каталога не запрещает запуск бинарника из него

- **Симптом:** в opt-in `denyhome` `node -e 0` из запрещённого `$HOME` запускается; падает только чтение его библиотек.
- **Статус:** запрет exec не обеспечен. Toolchain под `$HOME` передаётся явным `TOOLCHAIN=<prefix>` (read-only).

## Процессы

### T9. `terminate` из `ProviderElectronSmoke` оставляет живых потомков

- **Симптом:** если лидер группы уже вышел, функция возвращается без сигнала; потомок жив через 2,5 с.
- **Решение:** kill группы независимо от статуса лидера; ждать пустой группы (supervisor).

### T10. `close` не приходит, пока потомок держит stdout

- **Симптом:** `turn.completed` и `exit` получены, но `end` и `close` не приходят 3 с; затем приходит «позднее» событие.
- **Решение:** конец хода = `exit` + конец stdout; если конца нет за 2 с после `exit` — kill группы и `protocol_error(stdout_held_open)`.
- **Пересмотрено 2026-09-29** (контракт хода, ревизия 6): таймер от `exit` в main гонялся с ожиданием потомков в supervisor, который сам держал stdout, — ложный сбой при потомке со `stdio: 'ignore'`. Теперь supervisor пересылает вывод и сам решает, закрылся ли поток до очистки группы; см. T129.

### T11. Electron `utilityProcess` непригоден как supervisor

- **Симптом:** при SIGKILL main utility-процесс умер за < 300 мс, JS-очистка не выполнилась, группа осталась сиротой.
- **Решение:** отдельный процесс через `ELECTRON_RUN_AS_NODE=1` с lifeline по stdin.

### T19. Supervisor ревизии 2 не доставлял задание и протекал окружением

- **Симптом:** цель запускалась с `stdin=ignore` — задание не доходило до CLI; цель наследовала `ELECTRON_RUN_AS_NODE=1` и `SUP_*`; подстрока `stop\n` в любом месте fd0 останавливала запуск.
- **Решение:** fd4 — канал задания (as-is в stdin цели, EOF → EOF stdin цели, не остановка); fd0 — только lifeline и целые строки `{"cmd":"stop"}`; env цели — allow-list `SUP_ENV_ALLOW` без `ELECTRON_RUN_AS_NODE` и `SUP_*`. Проверка: `supervisor.test.mjs` на `mock-cli.mjs`, 14/14.

### T20. Гонки stop/exit в supervisor

- **Симптом (чтение кода и тест):** обработчик `exit` вызывал `process.exit(0)`, пока `stop()` ещё эскалировал; два независимых цикла ожидания/сигналов (Stop во время ожидания leftover запускал вторую эскалацию); сигнал слался опустевшей группе.
- **Решение:** один путь завершения `run()`, обработчики только записывают факты; сигнал лидеру только до reap, группе — только пока `kill(-pgid,0)` успешен; `done` ровно один раз. Проверка: гонка Stop/выход, 20 прогонов × 4 тайминга.

### T21. `reconcile` превращал ошибку в успех при Stop

- **Симптом:** терминальное событие успеха + `exitCode=42` + `stopRequested=true` → `completed`.
- **Решение:** порядок «результат → завершение процесса → решение цикла»; `completed` при ненулевом выходе только если Stop отправлен после результата и процесс завершён нашим сигналом (`signalsToLeader`); `nextTurnAllowed=false` после принятого Stop. Проверка: `jsonl.test.ts`.

### T22. `oversized` сообщался только на `\n`/EOF; замер памяти описан неверно

- **Симптом:** строка без `\n` копилась в режиме skip без сигнала до конца потока; в ревизии 2 «строка 200 МБ при пике 18,8 МиБ» — но 200 МБ отбрасывались, а 18,8 МиБ было только `arrayBuffers`.
- **Решение:** ошибка один раз сразу в `push()`; `TurnCollector` ограничивает накопление; `mem-check.ts` измеряет heapUsed, arrayBuffers, external и RSS с описанием метода (ARCHITECTURE §5).

### T12. env-маркер не виден у системных бинарников Apple

- **Симптом:** `ps -E -ww -o command= -p <pid>` показывает токен у node, но не у `/bin/sleep`, `/bin/sh`, `/usr/bin/perl`.
- **Причина:** macOS скрывает env платформенных бинарников (вероятно, ограничение `KERN_PROCARGS2`).
- **Ложный след:** проба `ps -axE | grep TOKEN` находила токен в argv собственной оболочки, а не в env целевого процесса. Искать нужно по конкретному pid.
- **Решение:** sweep беглецов — best effort (env + cwd через `lsof`); Stop не обещает завершить процессы, вышедшие из группы.

### T13. `ps -o lstart` локализован

- **Симптом:** дата старта выводится на языке системы.
- **Решение:** `LC_ALL=C` для всех вызовов `ps`, которые разбираются программно.

### T23. Проверка очистки через `ps` в ограниченной среде даёт EPERM

- **Симптом:** у внешнего ревью ревизии 3 проверки `supervisor.test.mjs` через `ps` и after-hook завершились EPERM.
- **Причина:** тест опирался на глобальный `ps`, который в песочнице ревьюера запрещён; ошибка `ps` не отличалась от «процессов нет».
- **Решение:** `proc-ledger.mjs` — основная проверка по pid, созданным самим тестом (`kill(pid,0)`: ESRCH — нет, успех — жив и тест падает, EPERM — «UNVERIFIABLE», не засчитывается как чисто). `ps` по маркеру — дополнительная проверка; её сбой печатается как «global check unavailable». Проверено прогоном с подменённым `ps`, возвращающим «Operation not permitted»: 73/73, 42 сообщения «unavailable». Убиваются только pid из своего ledger.

### T24. Mock-процесс теряет вывод при `process.exit`

- **Симптом:** последние JSONL-строки mock'а не доходили до обвязки.
- **Причина:** на macOS запись в pipe у Node асинхронна; `process.exit()` сразу после `write` отбрасывает неотправленное.
- **Решение:** mock'и ждут `drain` и завершаются естественно, без `process.exit`. Для реальных CLI это означает: `exit` раньше конца stdout — нормальная ситуация, конец хода определяется по концу stdout (P4).

### T27. Ошибка доставки задания не влияла на итог хода

- **Симптом (ревью ревизии 4):** Claude, задание 8 МиБ, mock не читает stdin и выдаёт успешный `result` → диагностика `sup_task_write_error=EPIPE`, `task_write_error=EPIPE`, но `outcome=completed`, `nextTurnAllowed=true`.
- **Причина:** ошибки записи задания только попадали в `diagnostics`; `done` мог уйти раньше, чем EPIPE по уже поставленной в очередь записи доходил до supervisor.
- **Решение:** состояние `delivery` (`ok` — main закрыл fd4 без ошибки, supervisor прислал `task_eof` и `task_written`; любая ошибка — `failed`; иначе `unconfirmed`) и правило `delivery_failed` раньше анализа ответа. Supervisor перед `done` ждёт завершения stdin CLI (ограниченно). Регрессия — оба провайдера.

### T28. Таймаут после полученного ответа давал `completed`

- **Симптом (ревью ревизии 4):** mock выдал валидный результат и продолжил работать; `timeoutMs=500`, SIGINT → `outcome=completed`, `stopCause=timeout`.
- **Причина:** `reconcile` правомерно считает транспорт завершённым (результат до Stop, выход нашим сигналом), а `outcome` брал транспорт раньше причины остановки.
- **Решение:** `decideOutcome` — 10 правил по порядку; `timeout` и `stopped` стоят раньше транспорта и ответа; ответ сохраняется в `report`. Транспорт (`reconcile`) и итог пробы (`outcome`) остаются разными уровнями.

### T29. Реальная K1: `init.tools unexpected` при правильном ответе

- **Симптом (серия 1):** K1 выполнила все условия, кроме списка инструментов: план ожидал `[]` из `--tools ""`.
- **Причина:** при `--json-schema` Claude Code 2.1.278 добавляет синтетический инструмент `StructuredOutput`, через который модель отдаёт структурированный ответ. В транскрипте тестовой сессии модели передан только он. Отчёт серии 1 не сохранил фактический список — только имя проваленного условия.
- **Решение:** ожидание — ровно `["StructuredOutput"]` для `--tools ""` + `--json-schema`, `[]` без `--json-schema`; прочие сочетания — отказ без ожидания; сравнение точное (лишний Bash/MCP — провал). Отчёт хранит ожидаемые и фактические имена tools/MCP и все критерии. Серия 2 подтвердила ожидание фактическим `system/init`. Повторный модельный запуск для диагностики не делался.

## Авторизация CLI

### T25. Claude при очищенном окружении «не залогинен»

- **Симптом:** `env -i HOME=$HOME PATH=… claude auth status` → `loggedIn=false`.
- **Причина (точно не установлена):** наблюдение — без `USER` и при фиктивном HOME статус `false`, с настоящими HOME и `USER` — `true`; вероятно, учётные данные ищутся в keychain пользователя по этим значениям.
- **Решение:** в env Claude передаются настоящий `HOME` и `USER` (имена, значения не логируются). Codex, напротив, видит авторизацию при фиктивном HOME, если задан `CODEX_HOME`. Обе проверки — только статус, не модельный запрос.

### T26. `--max-turns` отсутствует в Claude Code 2.1.278

- **Симптом:** ревизии 2–3 планировали пробы с `--max-turns`; в `claude --help` такого флага нет.
- **Решение:** в базовых пробах не используется; `probe-plan.mjs --check` сверяет каждый флаг плана с `--help` установленной версии.

## Окружение разработки

### T14. В zsh команды экспериментов ломаются

- **Симптом:** zsh не делит `$VAR` на слова и трактует `:r` в `+$W:ref` как модификатор.
- **Решение:** запускать эксперименты в bash (указано в README экспериментов). В этой среде нет `timeout` (coreutils), используйте таймауты внутри скриптов.

### T30. `npm run build` падает на `build:speech` с MacOSX27.0.sdk

- **Симптом (этап реализации 1):** clang++ с SDK 27.0: `libc++.1.tbd: unknown architecture arm64e.x1-macos … linker command failed`.
- **Причина:** сломанный SDK 27.0 в Command Line Tools этой машины; к оркестрации не относится.
- **Решение:** `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk npm run build` (и так же для упаковки).

## Движок одного хода (этап реализации 1)

### T31. Smoke Stop на mock, не читающем stdin, давал бы `delivery_failed`

- **Симптом:** большое задание во втором ходе smoke (Stop) + mock без чтения stdin → по правилу 3 ревизии 5 итог `delivery_failed`, а не `stopped`.
- **Решение:** это верное поведение (доставка проверяется раньше остановки). В ходе Stop задание короткое (помещается в буфер pipe); доставку большого задания проверяет первый ход (116 736 байт, длина и `cksum` сверяются mock-ом).

### T32. Аннотации схемы (`title`, `description`, `$schema`) отклоняются

- **Симптом:** `compileSchema` бросает `UnsupportedSchemaError` на схеме с `description`.
- **Причина:** валидатор — явное ограниченное подмножество (контракт этапа 1); прототип аннотации молча пропускал. Сейчас любое ключевое слово вне `SUPPORTED_SCHEMA_KEYWORDS` — отказ до запуска процесса.
- **Решение:** убрать аннотации из схемы ответа. Разрешение аннотаций — отдельное решение.

### T33. Stop в smoke — по таймеру

- **Симптом:** второй ход smoke вызывает `stop()` через фиксированные 1500 мс.
- **Причина:** у `startTurn` пока нет событий прогресса (появятся с `OrchestrationService`).
- **Решение:** не требуется для этапа 1; mock в этом ходе живёт 60 с, поэтому Stop всегда приходит во время работы.

### T34. Провайдерский ход с лишним инструментом давал `completed`

- **Симптом (внешнее ревью этапа 1):** Claude `structured-no-tools`, mock с `init.tools=["StructuredOutput","Bash"]` → `startTurn` `completed`, `nextTurnAllowed=true`; отдельный `verifyClaudeInit` — `ok=false`.
- **Причина:** проверка контракта была необязательной функцией, её вызов зависел от вызывающего кода.
- **Решение:** единственный публичный путь `startProviderTurn` всегда проверяет контракт (`system/init` / `thread.started`); нарушение → `contract_violation`, `nextTurnAllowed=false`. Транспорт `startTurn` из публичного API убран. Элементы `tools` не приводятся к строкам (прежний `map(String)` принял бы `[["StructuredOutput"]]`).

### T35. Неизвестный `modelParams` молча отбрасывался

- **Симптом:** Codex, `modelParams={unsupportedParameter:"ignored"}` принимался адаптером.
- **Решение:** разрешённые ключи и значения — в `PROVIDER_MODES[provider].modelParams`, проверка во время выполнения до файлов и процессов. Заодно: неизвестные поля входа — отказ; id потока Codex, начинающийся с `-` (`-s`), раньше проходил шаблон — теперь отказ.

### T36. Electron-тест: stderr `codesign_util.cc … task_name_for_pid`

- **Симптом:** под песочницей вокруг запуска тестов Electron-тест supervisor падает на `stderr === ""`, функциональные проверки проходят.
- **Причина (воспроизведено):** Electron в Node-режиме проверяет подпись родителя; при запрете `task_name_for_pid` (`sandbox-exec (deny mach-task-name)`) пишет лог и работает дальше.
- **Решение:** тест отделяет только эту строку лога и выводит её в диагностику; прочий stderr supervisor и CLI по-прежнему роняет тест. Подробности — evidence/stage-1-electron-diagnostics.md.

### T37. Packaged smoke внутри Seatbelt-песочницы завершается до маркера

- **Симптом:** маркера нет; у ревью SIGABRT, локально под `sandbox-exec (deny mach-task-name)` — SIGTRAP после `sandbox initialization failed` и `FATAL … GPU process isn't usable`.
- **Причина:** собственная песочница Chromium не инициализируется внутри другой. Для локального воспроизведения доказано; для случая ревью не доказано (другой сигнал).
- **Решение:** smoke печатает режим, версии и распознанные сообщения рантайма и остаётся проваленным. Запускать packaged smoke вне внешней песочницы. `--no-sandbox` и изменения fuses не применяются.
- **Р10 (2026-09-24):** на новой локальной сборке вне внешней песочницы orchestration smoke и sandbox smoke прошли, SIGABRT не воспроизвёлся (VALIDATION-MATRIX P6).

## Журнал и восстановление (Р2)

### T38. Секрет-аудит репозитория срабатывает на маркер в тесте

- **Симптом:** `repository-security.test.mjs` — `hard-coded secret assignment` в `tests/orchestration-store.test.mjs`.
- **Причина:** тестовый маркер утечки был присвоен ключу `OPENAI_API_KEY: \`…\`` — шаблон аудита (`api[_-]?key … = "…12+"`) совпал. Реального секрета не было.
- **Решение:** ключ переименован в `CTTY_LEAK_PROBE`; аудит не ослаблялся. В тестах утечек не использовать имена, похожие на ключи API.

### T39. `openRun` отказывает: `journal_torn_tail`

- **Причина:** последняя запись оборвана (крах посреди записи или короткая запись). Append не был подтверждён, значит сервис по нему ничего не запускал.
- **Решение:** посмотреть `readRun(...).integrity.detail`; открыть с `acceptTornTail: true` — байты хвоста сохраняются в `quarantine/`, журнал усекается, пишется `journal.tail_repaired`. Автоматически это не делается.

### T40. `openRun` отказывает: `journal_corrupt`

- **Причина:** повреждена строка внутри файла (хэш, цепочка, схема, версия, replay). Файл не меняется, продолжение запрещено.
- **Решение:** расследование вручную; экспорт/чтение через `readRun` (state до повреждения). Автоматического ремонта нет. Удаление целого корректного хвоста этим не обнаруживается (нет внешнего якоря).

### T41. `writer_locked` без живого писателя

- **Причина:** последнее поколение `locks/writer-<N>.json` не разбирается или его pid занят другим процессом (`EPERM`/жив, в том числе переиспользованный pid).
- **Решение:** убедиться, что приложение и тесты не держат run, затем пометить последнее поколение `"released": true` вручную (не удалять файлы поколений: их удаление ломает взаимное исключение). Автоматически следующим поколением сменяется только владелец с мёртвым pid (`ESRCH`).

### T42. Два писателя одного run после краха владельца

- **Симптом (внешнее ревью Р2):** два процесса одновременно захватывают одну устаревшую `writer.lock`; оба получают писателя, оба подтверждают append, журнал → `corrupt/bad_seq`. Воспроизведено управляемым порядком операций (`/tmp/canvastty-r2-lock-review.mjs`).
- **Причина:** замена устаревшей блокировки `rename` поверх не атомарна относительно её прочтения: второй процесс заменял уже новую блокировку по ранее прочитанным данным. Повторное чтение токена этого не закрывает.
- **Решение:** блокировка поколениями `locks/writer-<N>.json`: претензия — эксклюзивное создание `N+1` (`link`), файлы поколений не удаляются, проигравший получает `writer_locked` и ничего не трогает. Тест: `tests/orchestration-store-lock.test.mjs` (два процесса, барьеры, оба порядка, `deleteRun` против `openRun`).

### T43. Повтор `commandId` с другим `kind` принимался как дубликат

- **Симптом (ревью):** `recordCommand(id, "pause_after_turn", {})` → `new`; `recordCommand(id, "stop", {})` → `duplicate_in_progress`, после завершения — `duplicate_completed`.
- **Причина:** сравнивался только `payloadHash`.
- **Решение:** сравниваются `kind` и `payloadHash`; `kind` проверяется до поиска дубликата. Тест: `tests/orchestration-store-review.test.mjs`.

### T44. Валидный отчёт больше 64 КиБ исчезал, ход оставался `completed` с продолжением

- **Симптом (ревью):** `recordTurnResult` писал `ref: null` и `nextTurnAllowed: true`; тест на 70 000 символов закреплял это.
- **Решение:** лимит отчёта движка = лимиту хранения (65 536 байт). Несохранённый отчёт: `turn.finished` с фактическим `outcome`, `nextTurnAllowed: false`, `report.storeError`, затем отказ `report_not_stored`. Если не записалось и `turn.finished` — ход `in_flight` → после повторного открытия `outcome_unknown`, без автоповтора.

## Рабочая копия и снимки (Р3)

### T45. `read-tree -m -u` молча перезаписывает игнорируемые файлы

- **Симптом:** при восстановлении к checkpoint игнорируемый файл копии, путь которого есть в цели, заменялся содержимым цели без ошибки; содержимого не было ни в одном снимке.
- **Причина:** Git (проверено на 2.50.1) при `read-tree -m -u` считает игнорируемые файлы расходуемыми и не отказывает; неотслеживаемый неигнорируемый файл он бы отказался перезаписать.
- **Решение:** `applyTreeToCopy` до `read-tree` проверяет каждый добавляемый путь: занят файлом вне recovery-дерева (или каталогом с игнорируемыми файлами) → `restore_conflict {path}`, копия не меняется. Пользователь переносит файл сам и повторяет восстановление. Тесты: `orchestration-workspace.test.mjs` (applyTreeToCopy), `orchestration-snapshots.test.mjs` (restore conflict).

### T46. `createWorkspace` падал на `git init --bare` с `ENOENT`

- **Симптом:** `git_spawn`/`ENOENT` при создании `control.git`.
- **Причина:** cwd процесса Git был `gitDir`, который ещё не существует (`init`, `clone`).
- **Решение:** cwd = `workTree`, иначе служебный HOME (`git.ts`). Найдено workspace-tests до интеграции.

### T47. После краха найден `refs/canvastty/<runId>/stage-<n>` без события в журнале

- **Это не ошибка.** Ref создаётся раньше события. `inspectWorkspaceRefs` вернёт его в `unjournaled`. Этап не принят, ref не удаляется.
- **Действие:** доверенный сервис повторяет `createCheckpoint(ws, n)`. То же дерево → `reused: true`, затем `recordCheckpoint`. Дерево другое → `checkpoint_conflict`, решение принимает пользователь.

### T48. Остались refs `refs/canvastty/<runId>/tmp-<uuid>`

- **Причина:** сбой между `fetch` во временный ref и его удалением в `publishRef`.
- **Действие:** объекты защищены, вреда нет. `inspectWorkspaceRefs` показывает их в `temporary`. Удаление явное: `git update-ref -d <ref>` в исходном репо. Автоматической чистки нет.

### T49. `workspace_tampered` / `copy_git_tampered`

- **`workspace_tampered`:** изменён `control.git` (config, alternates, `info/*`, hooks, HEAD), раскладка (symlink вместо каталога), маркер или baseline в `control.git` и исходном не совпадают.
- **`copy_git_tampered`:** изменён `.git` копии (config, alternates, `info/*`, hooks), появились `commondir`/`gitdir`, `.git` стал файлом.
- **Действие:** операции с копией останавливаются. Автоматического восстановления нет. Исходный репо не трогается. Копию пересоздаёт пользователь (новый run).

### T50. `baseline_conflict` при повторном `createWorkspace`

- **Причина:** baseline ref этого run уже опубликован (прошлая попытка упала после `publishRef`), а дерево исходного репо с тех пор изменилось.
- **Действие:** существующий ref не перезаписывается, `workspace/` удаляется. Нужен новый `runId`. Старый ref удаляется только явно.

### T51. Файл из глобального игнора пользователя (`core.excludesFile`) попал в baseline

- **Причина:** `createWorkspace` вызван без `userHome`, и глобальный config не читается (единственное исключение из схемы запуска Git, см. контракт Р3).
- **Действие:** передавать `userHome`. Снимки копии глобальный игнор не применяют никогда: в них попадает больше, а не меньше.

## Восстановление копии: исправления по внешнему ревью (Р3)

### T52. `restore_incomplete`: копия восстановлена частично или её состояние неизвестно

- **Симптом:** `applyRestore` отказал с `restore_incomplete`; в каталоге run остался файл `workspace/restore.json`. Дальнейшие операции с копией (`createSnapshot`, `createCheckpoint`, `prepareRestore`, `applyRestore`) отказывают с тем же кодом.
- **Причина:** сбой произошёл после начала записи файлов (например, каталог стал недоступен для записи, кончилось место, процесс убит). `read-tree -m -u` меняет файлы по одному, атомарности нет.
- **Что гарантировано:** recovery-снимок создан до записи и сохранён в исходном репо; событие `workspace.restored` не записано; в журнале стоит `restore_failed`, а `pendingRestore` сохраняется; этап принять нельзя.
- **Действие:** решение принимает пользователь. Автоматического откота нет намеренно: вторая неудачная попытка записи ухудшила бы состояние. Варианты: (1) `clearIncompleteRestore(ws)` и новая попытка восстановления (будет создан свежий recovery-снимок уже частичного состояния); (2) `clearIncompleteRestore(ws)` и ручной разбор копии; (3) откат к recovery-снимку как к обычной цели восстановления.
- **Ранее (дефект ревью №1):** любой ненулевой выход `read-tree` объявлялся `restore_conflict` с обещанием «копия не менялась», хотя часть файлов уже была восстановлена.

### T53. `restore_state_changed`: копия изменилась между подготовкой и применением

- **Симптом:** `applyRestore` отказал с `restore_state_changed {expected, actual}`, копия не менялась.
- **Причина:** после `prepareRestore` в копии изменили файл или добавили новый неигнорируемый файл. `read-tree -m -u` трогает только пути, различающиеся между recovery-деревом и целью, поэтому такое изменение молча осталось бы в копии.
- **Действие:** остановить исполнителя и других писателей, затем заново вызвать `prepareRestore` (новый recovery-снимок зафиксирует текущее состояние) и повторить применение.
- **Ограничение:** это проверки до и после операции, а не защита от конкурентной записи во время самого `read-tree`. Требование «во время восстановления нет активного исполнителя и других писателей» обеспечивает сервис, а не этот модуль.

### T54. Файл, принятый в checkpoint, исчезал из recovery-снимка

- **Симптом:** файл принят в `stage-1`, затем попал под новое правило `.gitignore`; recovery-снимок перед восстановлением его не содержал, изменения на диске терялись без записи.
- **Причина:** `createSnapshot` брал базу `ws.baseline`, а `prepareRestore` базу не передавал. По базе baseline такой файл неотслеживаемый и игнорируемый.
- **Решение:** база снимка — обязательный параметр и берётся из доверенного состояния журнала (`RunState.workspace.current`): baseline, затем подтверждённые checkpoint и восстановления. Ref без события журнала применимой базой не считается.
- **Проверка:** в тестах сверяется содержимое recovery-коммита, а не наличие ref.

### T55. Checkpoint отвергается журналом: `checkpoint while a restore is unfinished`

- **Причина:** есть `pendingRestore` — восстановление начато и не подтверждено. Содержимое копии не подтверждено, принимать из неё этап нельзя.
- **Действие:** завершить восстановление (подтвердить `workspace.restored`) либо, после `restore_incomplete`, разобраться по T52. Новая попытка восстановления допускается только после записи `restore_failed`.

### T56. `restore_incomplete {path}` после корректного восстановления, если файл стал каталогом

- **Симптом (второе ревью):** в копии каталог `item` заменён обычным файлом; восстановление вернуло `item/child.txt` с верным содержимым, но `applyRestore` отказал с `restore_incomplete {path: "item"}`, `workspace/restore.json` остался и заблокировал работу.
- **Причина:** `diff-tree --diff-filter=D` считал прежний файл `item` удалённым, а `exists("item")` возвращал `true`, потому что на его месте уже стоял необходимый цели каталог.
- **Решение:** отброшенный путь допустим в виде каталога, только если цель требует его как каталог для своих файлов (список путей цели читается из временного индекса). Оставшийся файл, лишний каталог и неверный тип пути по-прежнему дают `restore_incomplete {path, directory}`.
- **Если уже упёрлись в это на старой версии:** копия при этом корректна; снимите блокировку `clearIncompleteRestore(ws)` и запишите событие восстановления, либо повторите восстановление — оно подтвердится.

## Runner проверок (Р4)

### T57. `not_verified(sandbox_unavailable)`: самотест профиля не прошёл

- **Симптом:** ни одна проверка проекта не запускается, в результате — список провалившихся операций самотеста.
- **Что это значит:** профиль не даёт того, что обещает таблица §2 контракта Р4, либо `sandbox-exec` недоступен, либо платформа не macOS. Команда проекта в такой ситуации **не запускается никогда**; ветки «запустить без песочницы» в коде нет.
- **Диагностика:** имя операции говорит, что именно сломалось. `control.<имя>` означает, что не удался **положительный контроль** вне песочницы: ресурс отсутствует или недоступен и сам по себе, поэтому запрет внутри ничего не доказывал бы (например, пустой `node_modules`). `child.*` и `detach.*` — ограничения не наследуются потомком.
- **Electron:** под минимальным профилем Electron в режиме `ELECTRON_RUN_AS_NODE` проверен — `npm run smoke:check-sandbox` (Electron из `node_modules`) и `npm run smoke:check-sandbox -- --packaged` (собирает приложение во временный каталог, `release/` не трогает; нужен `npm run build`). Если самотест падает в приложении, а smoke проходит, сравните путь Electron и `Contents/Resources/orchestration/`. Профиль расширять ради зелёного результата нельзя.
- **`deny.signal-outside` / `allow.signal-own-child`:** не выполняется предпосылка скана очистки (T59): сигналы из песочницы не ограничены её экземпляром. Проверки запускать нельзя — очистку нечем подтвердить.

### T58. `not_verified(deps_changed)`

- **Причины до запуска (события в журнале нет):** sha256 lockfile в копии не совпал с `preparedDeps.lockfileSha256`; `node_modules` в копии — обычный каталог (свой у проекта или созданный агентом) или ссылка не на подготовленный каталог; в копии есть ещё какой-то `node_modules` (вложенный); подготовленный каталог отсутствует, не каталог или лежит внутри данных оркестрации. `detail` называет причину.
- **Ссылка в подготовленном `node_modules` ведёт наружу:** `detail` вида `{ link, target, resolves, error: "points outside the prepared dependencies" }` или `error: "does not resolve"`. Принимаются только ссылки, чья конечная цель внутри подготовленного каталога (`.bin`, псевдонимы, цепочки внутри). pnpm store, `npm link` и workspace-пакеты вне `node_modules` в MVP не поддерживаются: подготовьте зависимости с копиями пакетов внутри `node_modules`. Runner ссылку не трогает, песочница наружу не расширяется.
- **Причины после запуска (событие `not_verified/deps_changed`):** проверка заменила ссылку каталогом, удалила ссылку или пересоздала её (даже с той же целью — это уже не та ссылка, которую сверяли), изменился lockfile, либо подготовленный каталог изменился во время проверки (штамп по `mtime`/`ctime`/`ino`/размеру — например, параллельный `npm install` в исходном проекте).
- **Действие:** чужой `node_modules` в копии runner **не удаляет и не заменяет** — уберите его сами или подготовьте зависимости заново и обновите `preparedDeps`. `npm install` и `npm ci` runner не выполняет никогда.
- **Тонкости:** ссылка создаётся до снятия дерева «до» — правило `node_modules/` к symlink не применяется. Зависимости сверяются раньше дерева, поэтому замена ссылки каталогом даёт `deps_changed`, а не `tree_changed`. Запись в подготовленный каталог изнутри проверки запрещена профилем (EPERM).

### T59. `not_verified(cleanup_unverified)` и что значит «очищено»

- **Причины:** `groupCleared !== true`; скан песочницы не подтвердил очистку (`sandboxCleared: false`, в `detail.sandbox` — `not_sandboxed` или `deadline`); supervisor вышел с кодом ≠ 0; supervisor без поддержки скана (нет поля `done.sandbox`).
- **Как подтверждается:** supervisor работает внутри той же песочницы, что и проверка, и перебирает pid: `kill(pid, 0)` оттуда успешен только для процессов этого экземпляра песочницы, поэтому видны все потомки, включая ушедших через `setsid`, `/bin/sh`, `/bin/sleep` и процессы без токена. Найденные убиваются SIGKILL, очистка засчитывается после двух пустых сканов подряд. `killed` в `cleanup` — сколько процессов пришлось добить.
- **`not_sandboxed`:** supervisor не в песочнице (например, `launch` указывает не на тот путь) — сигналов он не шлёт вовсе, иначе скан задел бы процессы пользователя.
- **Граница:** процесс, который непрерывно делает fork и exit быстрее одного скана (≈200 мс), может в него не попасть. Зомби отфильтрованы через `getpriority`: они видны из любой песочницы.
- **Прежнее поведение (до исправления ревью):** sweep по `CANVASTTY_RUN_TOKEN` не видел платформенных бинарников и давал `passed` при живом `/bin/sleep`. Удалён.

### T60. `not_verified(tree_changed)`: проверка изменила исходники

- **Причина:** дерево копии после проверки не совпало с деревом до неё (правка отслеживаемого файла, новый неигнорируемый файл, удаление). Игнорируемые артефакты сборки в дерево не входят и расхождения не дают. `treeBefore` и `treeAfter` — в `detail.post`. До исправления ревью `treeAfter` вычислялся, но не сравнивался, и такая проверка давала `passed`.
- **Смысл:** результат не подтверждает прежнее дерево, поэтому это не `failed` и не `passed`. Проверка, которая правит исходники, должна либо перестать это делать, либо её результат принимается по новому дереву отдельным запуском.

### T61. `not_verified(store_failed)`: результат не подтверждён

- **Причина:** не записалось событие `check.finished` или вывод проверки.
- **Следствие:** `passed` в этом случае невозможен, даже если команда завершилась с кодом 0. Ошибка записи `check.started` не оставляет события вовсе и процесс не запускается.
- **После перезапуска:** проверка, чей `check.started` в журнале есть, а результата нет, становится `not_verified(interrupted)`; автоматического повтора нет.

### T62. Проверка вернула `failed`, хотя команда не запускалась

- **Причина:** лидер процесса — `sandbox-exec`, поэтому отсутствующий, перемещённый или подменённый `executable` дал бы ненулевой выход, то есть «вердикт инструмента».
- **Решение:** реестр проверяет executable при создании, а координатор — ещё раз перед запуском (существование, совпадение с realpath, тип файла, sha256 для evidence). Несовпадение → `not_verified(spawn_failed)` до запуска процесса.

## OrchestrationService (Р5)

### T63. Прогон сразу встаёт в `paused(permission_denied)` с `unsupported_capability`

- **Причина:** реальный адаптер (`createProviderAgents`) не даёт исполнителя: Claude разрешён только в `structured-no-tools` и копию менять не может; лид поддерживается только Codex `structured-readonly`.
- **Решение:** это ожидаемый явный отказ, а не сбой. Права провайдеров не расширяются без отдельной проверки; цикл проверяется тестовым адаптером.

### T64. `paused(limit_reached)`, хотя ходов «почти не было»

- **Причина:** правило 2 срабатывает до следующей **внешней** операции (ход или проверка); проверка тоже не начнётся, если бюджет ходов исчерпан. Внутренние шаги (checkpoint, приём этапа, `completed`) лимит не блокирует.
- **Решение:** `raise_limit` с большим значением (пишет `limits.changed`, переводит в `paused(user_request)`), затем `resume`.

### T64a. `paused(limit_reached)` посреди хода или проверки

- **Причина:** истёк дедлайн run (`createdAt + runMs`, по часам; время закрытого прогона тоже считается). Сервис остановил операцию, подождал её результат не дольше `stopGraceMs` и поставил паузу. Поздний ответ агента записан как `turn.finished`, но ревью и план из него не создаются.
- **Решение:** `raise_limit runMs` со значением, дающим дедлайн в будущем (иначе `invalid_command`), затем `resume`. Ход без записанного ревью повторяется новым ходом.

### T64b. `paused(environment_error)` после долгого хода

- **Причина:** ход дольше `leadTurnMs`/`executorTurnMs`: сервис вызвал `stop()` сам (агенту эти лимиты передаются как `timeoutMs`, урезанный остатком run).
- **Решение:** `resume` повторит ход новым; при систематических таймаутах — пересмотреть лимиты цели.

### T64c. Checkpoint есть в Git, а в журнале нет

- **Причина:** запись `checkpoint.created` упала после публикации ref. После `openRun` прогон в паузе; `resume` сверяет ref `stage-N` строго с записанным `stage.accepted` и записывает событие с тем же коммитом.
- **Решение:** `resume`. Если после этого `paused(shared_git_tampered)` — ref не совпал с намерением (другое дерево, родитель, автор или сообщение): его кто-то изменил; автоматически он не принимается.

### T64d. После замены программы проверки run снова её запускает

- **Причина:** ключ актуальности содержит sha256 содержимого executable; прежний результат относится к другой программе.
- **Решение:** это ожидаемо. Результат переиспользуется только при неизменных дереве, зависимостях, определении и содержимом программы.

### T65. `paused(loop_suspected)`

- **Причина:** §10 контракта: `noProgressRounds` раундов без прогресса, два ревью с одинаковыми замечаниями на разных состояниях, или возврат к прежнему состоянию с тем же исходом проверок.
- **Решение:** уточнить цель (`clarify`) или ответить на вопрос — ввод пользователя считается прогрессом; простое `resume` продолжает, и та же петля не поднимается повторно до следующего ревью.

### T66. Тест ждёт проверку `in_flight` через `readRun`, а видит `not_verified(interrupted)`

- **Причина:** `readRun` (Р2) — вид для закрытого прогона: он всегда помечает незавершённые проверки прерванными.
- **Решение:** для живого прогона смотреть событие `check.started` в самом журнале или `RunHandle.view().active`.

### T67. Прогон `halted`, все команды → `store_failed`

- **Причина:** запись в журнал не удалась (писатель отравлен): решение нельзя сохранить до действия, поэтому цикл останавливается, активная операция отменяется.
- **Решение:** устранить причину (диск, права), закрыть и заново открыть прогон — он откроется в паузе без автоматического повтора незавершённой операции.

## Claude-исполнитель и реальная серия (Р6)

### T68. Исполнитель: `unavailable` с `unproven_mode`

- **Причина:** `structured-edit` — кандидатный режим; без `allowCandidate: true` (в `createProviderAgents`) или `candidate: true` (в `startProviderTurn`) он не строится.
- **Решение:** это ожидаемо до реальной серии и ревью. Допуск включает только скрипт серии; после подтверждения статус меняется на `proven` отдельным решением.

### T69. Claude отказывает `unsupported_version` после обновления CLI

- **Причина:** режимы привязаны к измеренным версиям: `structured-no-tools` доказан только для 2.1.278, `structured-edit` — кандидат для 2.1.280. Установлен 2.1.280, поэтому no-tools больше не строится.
- **Решение:** не расширять список версий без реальной пробы; для новой версии — dry-run и серия.

### T70. `contract_violation`: `system/init.tools differs …` у исполнителя

- **Причина:** настоящий CLI сообщил другой набор инструментов, чем `{Read, Edit, Write, Glob, Grep, StructuredOutput}` (гипотеза H1), или `permissionMode` не `dontAsk`.
- **Решение:** не ослаблять ожидание. Посмотреть `contract.actual` в отчёте серии; если набор отличается безопасно (например, переименован синтетический инструмент), изменить ожидание отдельным решением с ревью.

### T71. Самотест проверки: `refused: directory is empty` (`allow.readdir-node-modules`)

- **Причина:** самотест Р4 читает подготовленный `node_modules`; пустой каталог он считает неготовым.
- **Решение:** у проекта без зависимостей в подготовленном каталоге должен быть хотя бы `.package-lock.json` (так делает `real-series.mjs`). Самотест не ослабляется.

### T72. `real-series.mjs --real` сразу выходит с кодом 2

- **Причина:** нет точного разрешения: `CANVASTTY_REAL_SERIES` должна совпадать со списком сценариев (по умолчанию `E1,E2,E3,C1`, без пробелов). Разрешение одной серии не покрывает другую.
- **Решение:** сначала `--dry-run`, затем согласование и команда из его вывода.

### T73. Что не доказывает режим `structured-edit`

- Рабочий каталог и режим разрешений — политика CLI, не изоляция ОС: процесс Claude работает без песочницы, а правила действуют только для встроенных инструментов. Сервис не обнаружит запись вне копии в произвольное место; серия проверяет её канарейками (E1). Managed settings администратора применяются всегда: dry-run показывает, есть ли их файлы.


### T74. E1: `not_confirmed` для H4/H5, хотя файл вне копии не создан и секрет не прочитан

- **Причина:** отказ засчитывается только по наблюдаемому вызову (контракт Р6 §5.1): `tool_use` Read канарейки или Write внешнего файла, `tool_result` с `is_error` **и** запись `result.permission_denials` с тем же `tool_use_id`, инструментом и файлом. Обычная ошибка инструмента (ENOENT, `Invalid tool arguments`, прерванный вызов), отсутствующий результат, отсутствующий, пустой или чужой `permission_denials` отказом по правам не считаются. Текст результата на слова вроде «denied» не проверяется.
- **Решение:** посмотреть `refusals.read/write.attempts` в отчёте: `result` и `permissionDenial` (`field_absent`, `not_listed`, `mismatch`, `listed`). Если настоящий CLI не присылает `permission_denials`, отказ этим способом не доказывается: E1 остаётся непройденной, критерий не ослаблять.

### T75. Checkpoint содержал `node_modules` (symlink), изменения вне `src/` и `tests/`

- **Причина (исправлено):** для проверок сервис создаёт в копии ссылку `node_modules` на подготовленные зависимости. Правило `node_modules/` на symlink не действует, поэтому ссылка с абсолютным путём попадала в снимки и checkpoint.
- **Решение:** ссылка — собственность оркестратора: `linkDependencies` пишет `workspace/deps-link.json` (цель, inode, время создания), а `copyTree` исключает её, только пока путь не отслеживается базой и ссылка совпадает с записью. Проекту принадлежащий `node_modules` не исключается и не трогается.

### T76. Проверка: `deps_changed` «not the link the orchestrator made»

- **Причина:** ссылка `node_modules` в копии не совпадает с `deps-link.json`: её удалили и создали заново (даже с той же целью), перенаправили, создал кто-то другой, или процесс упал между созданием ссылки и записью (ограничение, помечено `ponytail:` в `workspace.ts`). Такая ссылка считается файлом проекта и входит в дерево.
- **Решение:** ничего не удаляется автоматически. Если ссылка лишняя — удалить её вручную в копии: следующая проверка создаст свою и запишет владение.

### T77. C1: `paused(limit_reached)` до финального ревью, хотя этап принят и checkpoint создан

- **Наблюдалось (реальная серия 2026-09-24):** первый план лида — три этапа, этап 1 «Inspect conventions» (только чтение). Сервис принимает этап только при пройденных обязательных проверках цели (`accept`, `all`), а без `src/clamp.mjs` они падают. Ревью `accept` при упавших проверках не принимается и возвращает этап исполнителю. Исполнитель корректно повторил осмотр без изменений: дерево то же, проверки не перезапускались (ключ актуальности). Лид запросил `replan`, план v2 из одного этапа прошёл проверки и был принят, checkpoint создан. Но 8 ходов (Codex 5, Claude 3) закончились раньше финального ревью.
- **Причина:** (1) лиду не сказано, что каждый этап должен проходить все обязательные проверки цели, поэтому этап «только осмотр» принять невозможно; (2) лимит `turns: 8` рассчитан на путь без `replan` (план, ход, ревью, финальное ревью плюс один возврат).
- **Решение (исправлено, контракт Р6 §5.3):** `buildTask` сообщает правила принятия этапа, запрет этапа без результата, компактный план, обязательное финальное ревью и бюджет из состояния сервиса. Повторный `execute` и `replan` получают результаты проверок текущего состояния. Лимит `turns 8` и критерии C1 не менялись. Повторный реальный C1 (03:53) завершился `completed` за 4 вызова.

### T78. В санитизированном отчёте серии остался обрезанный локальный путь

- **Причина:** `refusal()` обрезает текст отказа до 300 символов **до** санитизации (`scrub` заменяет полный путь каталога прогона). Обрезанный путь не совпадает с полным и не заменяется, в `message` остаются префикс scratchpad и имя пользователя.
- **Решение:** в отчёте `evidence/real-series/2026-09-24T03-06-00-556Z-8701ae.json` две подстроки затёрты (`postRedaction`), сырой отчёт хранится вне репозитория; отчёт сохранён как исторический. **Исправлено в коде** (контракт Р6 §5.4): `scrubText` до `clip`, оба написания путей, остаток путей → `<path>`; регрессии с границей обрезки внутри пути, токена и id сессии. Отчёт повторного C1 проверен: локальных путей нет.

### T79. Лид видит «untracked node_modules» в копии

- **Наблюдалось (повторный C1, 2026-09-24):** в замечаниях ревью лид упомянул неотслеживаемую запись `node_modules`. Это служебная ссылка оркестратора: её видно через `git status` копии, потому что `.git` копии про исключение не знает.
- **Влияние:** в снимки и checkpoint она не попадает (X14), на решение лида в этом прогоне не повлияла.
- **Если понадобится:** сказать об этом в задании или добавить путь в `info/exclude` копии. Второе меняет fingerprint `.git` копии и требует отдельного решения.

## Р7: main, IPC и preload

### T80. `deps_unavailable` при создании run

- **Причина:** main берёт подготовленные зависимости только из корня исходного репозитория: `package-lock.json` и собственный каталог `node_modules` (не symlink). Установка зависимостей оркестратором не предусмотрена (Р4).
- **Решение:** установить зависимости в проекте самому (`npm ci`) и создать run снова (с новым `requestId`, либо с тем же — отказ случился до создания run).

### T81. Первая страница истории без `run.created`

- **Наблюдалось (при разработке Р7):** страница «после seq 0» не содержала первую запись.
- **Причина:** журнал нумеруется с 0.
- **Решение:** параметр `fromSeq` включительный; первая страница — `fromSeq = 0`, следующая — `last.seq + 1`.

### T82. После перезапуска run стоит на паузе и ничего не делает

- **Ожидаемо (контракт Р7 §5):** старт приложения не открывает и не продолжает run. Продолжение — явной командой (`resume`, `step`, `recover`) с актуальной `expectedRevision`. После обычного выхода `run.recovered` не пишется: журнал закрыт штатно; после сбоя процесса его допишет Store при открытии.

### T83. Выход приложения задерживается

- **Причина:** `shutdown` останавливает активную операцию каждого run через её `stop()` и ждёт её конца не дольше `stopGraceMs + 1 с` (20 с по умолчанию), затем ставит `paused(user_request)` и закрывает журнал.

### T84. Повтор создания с другим проектом получал `created:false` (ревью Р7)

- **Причина:** повтор сравнивал только цель и только после создания. Одновременные запросы с одним `requestId` делили первую попытку, какими бы они ни были.
- **Решение:** идентичность = `realpath` проекта + нормализованная цель (`requestKey` в цели run); незавершённое создание хранится вместе со своей идентичностью (контракт Р7 §1.1). Регрессии — VALIDATION-MATRIX I11.

### T85. Подписка восстанавливалась после `unwatch` или перезагрузки (ревью Р7)

- **Причина:** обработчик `watch` ждал менеджер, а затем безусловно записывал подписку. `unwatch` или перезагрузка в это время удаляли запись, которой ещё не было, и поздний результат ставил подписку заново; её уже никто не снимал.
- **Решение:** запись создаётся до ожидания; поздний результат сверяется со страницей и записью и освобождается, если отменён. Обработчики окна ставятся один раз (контракт §2.1, I12).

### T86. Последнее событие показывало `active = null`, а `get()` — работающего исполнителя (ревью Р7)

- **Причина:** уведомления шли только после записи журнала. `active` меняется после `turn.intent`/`check.started` и после результата операции, без записи.
- **Решение:** `tick` и уведомление при каждом изменении `active` и `halted`; `seq` остаётся позицией журнала (контракт §2.2, I14).

### T87. Приложение запускало провайдеров без проверенной модели и бюджета (ревью Р7)

- **Причина:** в Р7 модель лида оставалась по умолчанию CLI, у исполнителя не было модели и бюджета, а Claude 2.1.280 допускался из списка кандидатов.
- **Решение:** `APP_PROVIDERS` в main (контракт §1.2): Codex 0.155.1 gpt-6-astra/high, Claude 2.1.281 claude-sonnet-5/$1; другие версии → `unsupported_version`. Argv проверен через путь менеджера (I15).

### T88. Run создавался после выхода приложения (повторное ревью Р7)

- **Причина:** `create` проверял `closing` до `await realpath`. Пока путь читался, попытки ещё не было в `creating`; `shutdown()` завершался, а продолжение `create` создавало run, открывало писателя и запускало агента.
- **Решение:** повторная проверка `closing` после определения идентичности, в одном синхронном участке с регистрацией попытки (контракт Р7 §1.1). Такой запрос получает `shutting_down`. Регрессия — VALIDATION-MATRIX I17.

### T89. Связь не создаётся, карточка лида показывает причину (Р8)

- **Ожидаемо:** main отклоняет связь с собой, не «Codex → Claude», повторную пару и карточки из разных папок проекта (`link_self`, `link_roles`, `link_duplicate`, `link_projects`). Сообщение держится 8 с или до следующего действия. Для другого проекта создайте карточку Claude с той же папкой, что у лида.

### T90. Нет кнопок «Новая цель» и «×» на связи (Р8)

- **Ожидаемо:** пока run связи активен (`preparing`, `running`, `pausing`, `paused`, `stopping`), новая цель и удаление недоступны. Сначала «Стоп» на панели запуска. Удаление связи не удаляет run: их история остаётся в `orchestration:list`.

### T91. После перезагрузки окна карточки агентов не видны (Р8)

- **Причина:** камера после перезагрузки возвращается к HOME; карточки хранятся в main (`<userData>/orchestration/canvas.json`) и стоят там же. Перетащите холст к ним. На миникарте карточки агентов пока не отображаются (ограничение Р8).

### T92. Действие на панели «Нет связи с приложением» (Р8)

- **Причина:** вызов IPC не завершился (транспорт), результат неизвестен. Повторное нажатие отправляет ту же команду с тем же `commandId`, main вернёт записанный результат, если команда уже выполнена.
- **«Состояние запуска изменилось и обновлено»:** команда пришла со старой `revision` (`stale_revision`). Панель обновлена из main; повторите действие, если оно ещё нужно.

### T93. UI smoke: правый клик не открывает меню (Р8)

- **Причина:** в начальном положении камеры HOME занимает почти всё окно 1440×900, и правый клик попадает в неё. Smoke сначала сдвигает холст перетаскиванием пустого места. Для `npm run smoke:orchestration-ui` нужна свежая `npm run build`.

### T94. Run создан, но связь о нём не знает; второй старт создавал второй run (ревью Р8)

- **Причина:** `startOnLink` создавал run, а потом записывал `runId` в `canvas.json`. Сбой записи (`EISDIR`, диск, права) оставлял активный run вне связи; следующий старт проходил проверку занятости и создавал второй.
- **Решение:** упреждающая запись — `requestId` (= `runId`) попадает в `link.runIds` до создания run (контракт §3.1). Сбой этой записи → `store_failed` без run; сбой после создания невозможен. Пустой резерв скрывается и не занимает связь. Регрессии — VALIDATION-MATRIX U15.

### T95. Повтор команды после «нет связи с приложением» выполнял её второй раз (ревью Р8)

- **Причина:** ключ ожидающей команды включал текущую revision. После того как main принял команду и revision выросла, повтор получал новый `commandId`, и main выполнял команду снова (два уточнения).
- **Решение:** ожидающий запрос хранится целиком (`commandId`, `expectedRevision`, payload) до ответа main и переживает перезагрузку окна; повтор отправляет его без изменений, main возвращает записанный ответ (контракт §2, U16). Если на панели жёлтая плашка «результат команды неизвестен» — нажмите «Повторить»: это безопасно.

### T96. Панель запуска не прокручивалась колесом (ревью Р8)

- **Причина:** у панели был только `data-wheel-owner="local"` (жесты указателя). Колесо отдаёт элементу `data-canvas-wheel-priority="local"`, без него колесо уходило холсту.
- **Решение:** атрибут у панели и диалогов оркестрации (U18).

### T97. UI smoke: «menu item … timeout» или «not clickable» (ревью Р8)

- **Причина до исправления:** фиксированные координаты — после панорамирования точка попадала на HOME.
- **Сейчас:** точки выбираются проверкой попадания. «no empty canvas» — в окне нет свободного места под карточку даже после панорамирования; «not clickable» — элемент закрыт другим (смотрите `failure.png` в каталоге снимков). Нужна свежая `npm run build`.

## Р9: сквозные проверки и аварии

### T98. После аварии приложения запуск показан «Выполняется», а восстановить его нельзя (Р9)

- **Симптом:** после сбоя или принудительного завершения CanvasTTY связь и панель показывают «Выполняется», «Сейчас работает: Никто», кнопки «Пауза после хода» и «Стоп»; «Принять результат хода» и «Повторить ход» нет.
- **Причина:** до открытия run `list`/`get` показывали статус из журнала — тот, что был до сбоя. `run.recovered` (и с ним `paused(outcome_unknown)` / `paused(recovered)`) появляется только при открытии командой, а команды восстановления для `running` не предлагались.
- **Решение:** run, который не держит ни один процесс, но журнал оставил его активным или с незавершённой работой, показывается так, как его запишет открытие (`needsRecovery`, контракт Р9 §4). Ничего не пишется и не запускается. После ошибки «Операция не выполнена» проверьте, что открыт только один экземпляр приложения: run, открытый другим процессом, отвечает `writer_locked`.

### T99. «Не удалось загрузить текст: Операция не выполнена (EACCES)» (Р9)

- **Причина:** ошибка файла (права, диск) доходила до интерфейса как errno.
- **Решение:** `orchestration:text` отвечает `text_unreadable` — «Файл текста не читается (нет доступа или ошибка диска)»; `text_missing` и `text_corrupt` — свои сообщения. Проверьте права на `<userData>/orchestration/runs/<runId>/texts/` и нажмите «Повторить».

### T100. E2E: как теряется ответ IPC и почему не через отладчик main (Р9)

- Отладочный порт main (`--inspect`) среда исполнения агента открыть не дала, а в упаковке его закрывает fuse. Вместо него — `CANVASTTY_ORCHESTRATION_TEST_DROP_REPLIES=<каталог>`: файл с именем вида команды (`recover`, `resume`, `stop`, …) заставляет main выполнить команду и потерять ответ один раз. Переменная читается только через `developmentEnv` — упакованная сборка её не видит.
- Если E2E падает на «unknown result shown» — нет свежей `npm run build` (механизм в main) или переменная не дошла до процесса.

### T101. E2E: «every process of the killed application ended by itself» падает (Р9)

- Сначала посмотрите `left`/`strays` в отчёте: какие команды остались. Supervisor завершает группу CLI или песочницу после EOF lifeline (SIGTERM, 5 с, SIGTERM группе, 3 с, SIGKILL), поэтому ожидание — до 30 с.
- Остался процесс CLI, а supervisor мёртв — значит убита вся группа main, а не один pid: это известное ограничение (нет поиска осиротевших процессов при старте), E2E его не проверяет.
- Прерванная проверка не пишет `check.finished`: `not_verified(interrupted)` решается при чтении run (`readRun`/`openRun`); ищите его в состоянии, не в журнале.

## Р10: упакованная сборка

### T102. Packaged smoke: «helper path /private/tmp/…» при явном `--app` (Р10)

- **Причина:** на macOS `/tmp` — ссылка на `/private/tmp`. Приложение сообщает реальный путь supervisor, а скрипт сравнивал его с путём `--app`, переданным через `/tmp`. Проверки хода при этом проходят.
- **Решение:** `smoke-orchestration.mjs` приводит `--app` к `realpath`. Если ошибка повторится, смотрите, не ведёт ли путь к другой сборке (например, в `release/`).

### T103. Какую сборку проверяет packaged smoke (Р10)

- Без `--app` `smoke-orchestration.mjs --packaged` берёт приложение из `release/`, и это может быть старая сборка. `smoke-check-sandbox.mjs --packaged` без `--app` собирает свою во временный каталог.
- Для проверки конкретной сборки передайте `--app <каталог>/mac-arm64/CanvasTTY.app` обоим скриптам и `smoke-packaged-gates.mjs`. Скрипты печатают путь бинаря.

## Реальная серия через UI

### T104. После запусков в домашнем каталоге появились сессии Claude и Codex

- Реальные CLI сами сохраняют сессии: Claude — `~/.claude/projects/<путь рабочей копии в userData>/`, Codex — `~/.codex/sessions/<дата>/rollout-*.jsonl`. Приложение этого не ограничивает (серия 2026-09-24). Удалять их можно средствами самих CLI или вручную; приложение на них не опирается.

### T105. В дереве процессов CanvasTTY есть `codex app-server`, хотя запусков нет

- Это чтение лимитов на HOME (LimitsService), оно идёт при каждом запуске приложения и к оркестрации не относится. Процессы оркестрации — `supervisor.mjs` и всё под ним.


## Р11: наблюдение

### T106. Правый клик по холсту не открывает меню (свежий профиль, рядом с HOME)

- **Причина:** рамка `.home-zone` больше её плиток. Клик по пустому фону внутри рамки считался кликом по HOME, поэтому меню было заблокировано. На свежем профиле камера стоит на HOME, и почти весь видимый холст попадал в эту рамку.
- **Решение:** голый фон `.home-zone` вне режима редактирования HOME считается пустым холстом (`WorkspaceCanvas.tsx`, маршрутизация контекстного меню). Высота меню для прижатия к краю окна увеличена под новые пункты.

## Р12: агенты в окружении пользователя

### T107. «Окружение не готово (shell или CLI)», запуск не стартует

- Приложение один раз на старт запуска выполняет `$SHELL -ilc` в папке проекта (таймаут 15 с) и берёт окружение, как у нового терминала.
- **Причины:**
  - rc-файл ждёт ввода или долго работает (обновления, `nvm use` с загрузкой) — `timeout`;
  - `$SHELL` не задан или не исполняемый — `no_shell`;
  - rc-файл завершает shell с ошибкой — `failed`.
- **Решение:** откройте новый терминал в папке проекта и засеките, сколько он стартует. Уберите интерактивные вопросы из `~/.zshrc` или оберните их в `[[ -o interactive && -t 0 ]]`.

### T108. Готовность: «не найдено в PATH вашего shell», хотя в терминале команда работает

- Проверяется первое слово команды по PATH из login-shell. Алиасы и функции shell здесь не видны: для них пункт показан как «не найдено», с этой оговоркой.
- PATH от хуков приглашения (direnv, precmd, `asdf` через хук) не попадает, если он не экспортирован в rc-файлах.
- **Решение:** впишите полный путь (`/opt/homebrew/bin/php artisan test`) или экспортируйте PATH в `~/.zprofile`/`~/.zshrc`.

### T109. Панель «Ждёт вашего разрешения», агент стоит

- Так и задумано: запрос пришёл от самого CLI по вашим настройкам прав (Claude `defaultMode`/`permissions`, Codex `approval_policy`). CanvasTTY за вас не отвечает, а время хода не идёт.
- **Решение:** ответьте в панели. Чтобы спрашивал реже, меняйте настройки CLI, как для терминала. «Разрешить на сессию» действует до конца сессии CLI этой роли.

### T110. Проверка `not_verified (tree_changed)`

- Команда проверки изменила отслеживаемые файлы. Например, генерирует кэш или снапшоты, которые лежат в git. Результат не относится к дереву, на котором проверка стартовала.
- **Решение:** добавьте генерируемые файлы в `.gitignore` или используйте команду, которая их не пишет.

### T111. «В этой папке уже работает другой запуск» (`folder_busy`)

- В одной папке проекта одновременно работает один запуск, по всем связям. Дождитесь окончания или остановите другой запуск.

### T112. Проверка из команды пользователя запускалась снова и снова (найдено при разработке Р12, исправлено)

- **Причина:** ключ оценки проверки строился с пустым хэшем программы из результата, а ключ снимка — с хэшем shell из реестра. Ключи не совпадали, проверка считалась несделанной.
- **Решение:** пустой хэш результата не подменяет хэш из снимка (`orchestrationService.ts`, `runCheck`). Регресс ловят интеграционные тесты `tests/orchestration-native.test.mjs`.

### T113. UI smoke: `timeout: link chip`

- Карточки иногда встают внахлёст, и перетаскивание порта заканчивается не на той карточке. Это нестабильность раскладки в скрипте, а не отказ связи: повторный прогон проходит (Р12: 1 из 2 прогонов `smoke-orchestration-ui.mjs`).

### T114. E2E: «the source's HEAD, branch, refs, status and working files are unchanged» падает

- С Р12 по умолчанию работа идёт в папке проекта, и исходник меняется по замыслу. E2E этапа 9 проверяет обещание режима копии, поэтому запускает цели с `workMode: "copy"`. Если проверка упала снова, смотрите, не потерян ли этот параметр в `startGoal`.

### T115. Старый запуск (до Р12) работает в ограниченном режиме

- Запуски, созданные без команд проверки (до Р12), продолжают работать с прежними ограничениями (`structured-edit`, Seatbelt, копия). Приложение не переводит их молча и не возобновляет само. Для нового режима создайте новую цель.

## Р13: автопилот, настройки проекта, подготовка среды

### T116. Пауза «нужно ваше действие» (`needs_user_action`)

Автопилот не может сам сделать нужный шаг:
- подготовка упала с ошибкой среды (нет программы, нет прав, нужен пароль или системная установка);
- коммит затронул бы файлы, где были ваши незакоммиченные правки на момент старта.

Что именно нужно, написано в ленте («Проверки» → последняя запись подготовки или «Действие после успеха»). Сделайте это и нажмите «Продолжить». Прогресс сохраняется.

### T117. Пауза «внешний сбой» (`external_failure`)

Проверка или подготовка упали из-за сети или удалённого сервиса (DNS, TLS, 429, 5xx, загрузка пакетов). Одинаковые исправления не повторяются, пока сбой не устранён. Проверьте сеть или сервис и нажмите «Продолжить».

### T118. «Результат действия после успеха не подтверждён» (`finish_unconfirmed`)

Коммит, push или деплой закончились с неизвестным или неподтверждённым результатом. Причины:
- приложение закрылось;
- вы нажали «Стоп»;
- деплой прошёл, а проверка QA упала.

Для коммита и push после перезапуска запускается только проверка: коммит с `CanvasTTY-Run: <id>` и проверенным
содержимым, `git ls-remote`.

Для QA проверка — ваша команда, и CanvasTTY не знает, что она ничего не меняет. Поэтому сначала запуск стоит на
этой паузе, а проверку QA он запустит только после вашего «Продолжить».

Если проверка не подтвердила результат, посмотрите сами:
- `git log --grep "CanvasTTY-Run: <id>"`;
- `git ls-remote <remote> refs/heads/<ветка>`;
- состояние QA.

Потом продолжите. Само действие CanvasTTY повторно не запускает. Если действие упало (деплой вернул ошибку),
кнопка называется «Повторить: <шаг>», и повтор делается только по ней.

### T119. Готовность: «Тесты Laravel пошли бы не в тестовую базу» (блокер или подтверждение)

CanvasTTY смотрит, какую базу тесты возьмут на самом деле:
- закомментированные строки `phpunit.xml` не считаются;
- `<env>` без `force="true"` не перекрывает переменную вашего shell или direnv;
- кэш конфигурации `bootstrap/cache/config.php` игнорирует тестовое окружение.

Уровни:
- **Блокер** — нелокальный сервер базы или кэш конфигурации. Выполните `php artisan config:clear`, если кэш не нужен.
- **Подтверждение** — база из `.env` или окружения, в том числе локальная: локальная тоже может быть рабочей.
  Отметьте, что понимаете, или задайте тестовую базу.
- **Инфо** — база нигде не задана.

Адрес подключения заменяет `DB_*`. Если в окружении или `.env` задан `DB_URL`, `DATABASE_URL` или другой адрес,
который читает `config/database.php`, тесты пойдут по этому адресу, даже если `phpunit.xml` задаёт SQLite. В строке
готовности видно имя переменной и причину, сам адрес и пароль не показываются. Отключите адрес для тестов:
`<env name="DB_URL" value="" force="true"/>` (или то имя, которое показано). Учитывается только подключение из
`'default'`. Если в строке видно «не удалось определить по config/database.php», значит, поле активного подключения
(default, connection, driver, url, host или database) задано конструкцией, которую CanvasTTY не вычисляет. PHP не
выполняется. Задайте тестовое подключение явно в `phpunit.xml`: `DB_CONNECTION` и `DB_DATABASE` с `force="true"`.

Надёжнее всего задать в `phpunit.xml` `<env name="DB_CONNECTION" value="sqlite" force="true"/>` и
`<env name="DB_DATABASE" value=":memory:" force="true"/>`. Та же проверка повторяется при создании запуска и перед продолжением. Если она
не прошла, запуск отклоняется с `test_database_unsafe`, и ничего не запускается. CanvasTTY не подставляет рабочую базу вместо тестовой и не
обещает защиту, когда настройку нельзя определить.

### T120. «.envrc не разрешён»

direnv не разрешил `.envrc` этой папки. Если файл ваш, выполните `direnv allow` в терминале проекта. CanvasTTY сам его не разрешает и без разрешения не применяет.

### T121. «Проверить окружение»: пункт «не подтверждено»

CLI не сообщил этот факт по своему протоколу без хода модели. Например, список скилов Claude приходит только в начале сессии и виден на панели запуска, в «Что сообщили CLI в этом запуске». Это не значит, что скила нет. Отсутствие ограничивающих флагов тоже не доказывает, что всё как в терминале.

### T122. Push отказан: «адрес remote не тот, что вы разрешили»

URL remote изменился после сохранения настроек проекта. Откройте «Настройки проекта» и сохраните их заново: адрес перечитывается из репозитория.

### T123. Запуск отклонён: `access_unsupported`

В настройках проекта выбран режим прав, которого нет в установленной версии CLI. Так бывает, например, после
обновления Claude или Codex. Режимы Claude берутся из его `--help`, режимы Codex — из точно сверенной версии протокола.
CanvasTTY не урезает режим сам. Откройте «Настройки проекта» и выберите режим из списка или «Как в моём терминале».

### T124. Лента: «Режим прав не применён: … выбран X, CLI сообщает Y»

CLI начал сессию не в том режиме, который выбран в настройках проекта. Claude может сам выйти из `auto` (режим
недоступен для плана или модели), а обход прав бывает запрещён его настройками. Действует то, что сообщил CLI.
Для режима «Как в моём терминале» сравнения нет.

### T125. У запроса нет кнопок «До конца запуска» и «Всегда в этом проекте»

CLI требует спрашивать об этом каждый раз. Причины:
- сработало ваше правило `permissions.ask`;
- проверка безопасности Claude;
- Codex не сообщил, какие файлы меняются.

Такое решение CanvasTTY не запоминает и сохранённым не отвечает.

### T126. Пауза «приложение закрылось» (`app_closed`)

Приложение завершилось во время запуска. Ожидавший запрос разрешения относился к старому процессу и снят, следующий
ход спросит снова. Прерванная подготовка среды запустится снова. После перезапуска ничего не начинается само:
нажмите «Продолжить».

### T127. Итог QA: «проверка прошла; версия не подтверждена» и другие исходы версии

CanvasTTY отдельно фиксирует три факта: проверка завершилась успешно, проверка сообщила версию, версия совпала с
ожидаемым коммитом. Версию подтверждает только контракт:
1. в «Настройках проекта» отмечено «Проверка сообщает развёрнутую версию»;
2. команда проверки записывает в файл `$CANVASTTY_QA_RESULT` полный id коммита, который она увидела на стенде
   (например, ответ `/version` стенда). Не `$CANVASTTY_COMMIT`: это ожидаемое значение, а не наблюдаемое.

Исходы:
- «проверка прошла; версия не подтверждена» — контракт не включён. Что команда печатает или упоминает, не важно;
- «проверка сообщила другую версию» — на стенде другой коммит (ещё выкатывается или деплой не применился);
- «…не сообщила версию» — файл пустой;
- «…не идентификатор коммита» — в файле не полный id из 40 или 64 hex.

В последних трёх случаях запуск стоит на паузе. «Продолжить» запускает только проверку, деплой не повторяется.

### T128. После подготовки Laravel в изменениях появился `package-lock.json` (F-1, открыто)

В проекте есть `package.json`, но нет lock-файла JS, и шаг подготовки `npm install` записал новый lock-файл. В коммит
запуска он не попадёт. Если JS-зависимости для тестов не нужны, удалите шаг `npm install` в «Настройках проекта» →
«Дополнительно», а файл удалите или закоммитьте сами.

### T129. «Ход не прошёл проверку протокола CLI» и шаг окончания хода

Раньше: «CLI нарушил протокол». С 2026-09-29 панель запуска и «Лог» показывают, на каком шаге закончился ход (запись
`turn_finished` в activity, поля `endStep`, `stdoutEnd`, `stderrEnd`, миллисекунды и сигналы; без текста вывода):
- `protocol_parse`, `no_terminal_event`, `multiple_terminal_events`, `events_after_terminal` — ошибка в выводе CLI
  или нет финального события;
- `stream_held_until_cleanup` — CLI ответил и вышел, но процесс из его группы (например, MCP-сервер или хук) держал
  вывод, пока его не завершила очистка; `stream_held_abandoned` — вывод держал процесс вне группы;
  `stream_held_capped` — после выхода CLI в вывод продолжал писать другой процесс;
- `relay_failed`, `relay_incomplete`, `stream_unknown`, `held_after_supervisor_exit` — сбой передачи вывода в самом
  приложении, не вина CLI;
- `cleanup_failed` — не подтверждено завершение процессов CLI; `invalid_report` — ответ не прошёл схему.

Потомок, который остаётся после выхода CLI, но не держит вывод (`stdio: 'ignore'`), больше не делает ход сбоем:
очистка завершает его, ход засчитывается, если ответ валиден. Повтор хода после сбоя не гарантирует другой результат:
сначала устраните причину. У записей до 2026-09-29 шага нет — причина их сбоя по журналу не устанавливается.
